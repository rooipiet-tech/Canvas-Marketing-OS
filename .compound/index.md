- L-0001 [conventions] Probe tool/credential availability (gh, docker, admin rights, local interpreter) before freezing a Must-have criterion that depends on live external-CLI/local-execution verification — AND the spec-writer must mechanically translate an unavailable-tool finding into that AC's verify evidence bar at v1, not defer it. (active; strengthened 2026-07-28 after s3-orchestrator hit the same gap despite the finding being documented)
- L-0002 [conventions] GitHub Environments' required-reviewers rule has a `prevent_self_review` flag — self-approval is a config choice (settable false), not an unconditional block; check it via `gh api` before assuming a second identity is needed. (active; corrected 2026-07-23 after user confirmed prevent_self_review=false works fine)
- L-0003 [conventions] A shell variable inside a double-quoted arg passed to a nested interpreter (e.g. python -c "...$id...") gets shell-expanded before the inner interpreter runs — single-quote or heredoc when the literal must not be shell-expanded. (active)
- L-0004 [security] Never generate a secret with `openssl rand -base64` for direct URI embedding — base64's `/+=` breaks URI parsing ~35-40% of the time; use hex or base64url instead. (active)
- L-0005 [conventions] Grep/regex-based spec verify commands cannot catch runtime/semantic bugs (lint failures, unsafe secret encoding) — keep a mandatory post-build multi-lens review distinct from spec verify commands. (active; strengthened 2026-07-31 with a concrete instantiation — a mock output silently violating its own package's schema.json is invisible to a fully-passing verify suite; validate mock outputs against their schema in review)
- L-0006 [architecture] Standing plan-reviewer checklist for IaC/CI builds: explicit workflow triggers, in-VNet verification for private-endpoint resources, bounded polling, explicit credential-flow, resolve-then-JSON gh api pattern, explicit IaC relative-path base dirs. (active)
- L-0007 [known-hard] Azure resource-provider/feature registration (e.g. WorkloadProfiles) is one-time and async, can exceed 10 min on first use — a bounded-poll timeout on the first deploy is expected/retriable, not a build defect; add a fast path for already-registered + print recovery commands on timeout. (known-hard)
- L-0008 [architecture] Design rule: free idempotent preflight steps (e.g. provider registration) live outside approval gates so retries are unattended; only spend-triggering steps sit behind the gate. Split into a separate ungated workflow. (active)
- L-0009 [conventions] GitHub Actions workflow_run cannot reference its own workflow ("cannot listen to itself") — implement retries as in-job bash loops, not self-triggering workflow_run + rerun. Cross-workflow workflow_run (A watching B) is unaffected. (active)
- L-0010 [known-hard] AFEC feature flags for long-GA capabilities (e.g. WorkloadProfiles) can wedge Pending indefinitely and may be vestigial — gate on provider registration + real deploy outcome, not the flag's state. (known-hard)
- L-0011 [security] RBAC-mode Key Vault grants NO data-plane access by default, not even to subscription Owner — human operators need an explicit Key Vault Secrets Officer role assignment (Bicep role assignment or documented az role assignment create command). (active)
- L-0012 [security] publicNetworkAccess=Disabled on Key Vault ignores IP firewall rules entirely (Disabled removes the public endpoint regardless of networkAcls) — human secret-loading needs a temporary Enabled+Deny+IP-allowlist window, restored after; a gated in-VNet secret-loading Container Apps Job would avoid opening the vault at all. (active)
- L-0013 [conventions] A reviewer finding that's really a BUG CLASS (a mechanism reused across call sites, e.g. raw request content leaking into client-facing messages) needs the patch to audit every call site of that mechanism, not just the reported one — single-instance fixes reliably leave siblings for the next round. (active)
- L-0014 [conventions] Local tests (deep repo checkouts, caplog/monkeypatch fixtures) can mask deployment-only bugs: filesystem-depth-assuming path code and startup-configured process state (logging) both "pass" locally while failing at the real shallow-container entrypoint. Test at the actual target layout/entrypoint, not a convenient local one. (active)
- L-0015 [conventions] GOAL text with generic placeholder paths that don't match a repo's real directory conventions needs an explicit locked-decision negotiation before spec-writer freezes touch-scope — resolve at the research stage, not mid-build. (active)

- L-0017 [architecture] Bicep cross-resource references for ordering must be real `module.outputs.x` references, never a separately-computed string that happens to match — a computed-string shortcut used to dodge a cycle removes the ordering guarantee along with the cycle. Resolve real cycles by moving the role-assignment grant into the consumer module (via an `existing` resource reference), not by faking the name. (active)
- L-0018 [architecture] An IaC-defined container app fed by a separate CD pipeline needs an explicit bootstrap path: default the image param to a public placeholder, and have the deploy workflow's preflight resolve it to the resource's current live image (if it exists) on every later run — plan this upfront for any new IaC compute resource whose real image comes from CI, not as a follow-up fix. (active)
- L-0019 [conventions] Two GitHub Actions workflows sharing a trigger (e.g. push to main) where one's job depends on the other's provisioned resources need `workflow_run` chaining (B watches A's completion + success), not independent same-event triggers — a shared push trigger races them. This is a genuine cross-workflow reference, distinct from L-0009's self-reference constraint. (active)
- L-0020 [architecture] A Bicep resource's SystemAssigned identity `principalId` can't be used to grant that same resource's own role assignments in the same deployment if the resource's own successful provisioning depends on that role (e.g. Container App needing AcrPull/KV Secrets User to reach a healthy first revision) — this deadlocks (confirmed live: 20+ min "Operation expired", zero role assignments ever created). Use a UserAssignedIdentity, granted before the dependent resource, instead. (active)
- L-0021 [architecture] A CI step that resolves an Azure resource via unfiltered `list --query "[0].x"` silently picks the wrong one the moment a second resource of that type exists in the RG (confirmed live: an orphaned second ACR got resolved instead of the Bicep-managed one, image pushed fine but the app's pull failed UNAUTHORIZED since its AcrPull/registries[] binding pointed at the other registry). Resolve from a consuming resource's own authoritative live binding instead of an ambient list. (active)
- L-0022 [known-hard] `az containerapp job start` with any Container Argument (`--env-vars`, `--command`, etc.) replaces the ENTIRE container spec, not just the flag passed — confirmed live: `--env-vars QUERY=...` alone fails ContainerAppImageRequired even though the job's Bicep template already has a valid default image, and adding `--image` back still silently drops `command`/other env vars (e.g. DATABASE_URL). Use a full `--yaml` override restating every field instead of bare flags; verified fix live (INSERT + SELECT both Succeeded). (active)
- L-0023 [known-hard] `az containerapp job start --yaml` with a `properties:/template:/containers:`-shaped file (matching `job create`/`update`'s shape) is silently IGNORED — no error, job runs its unmodified persisted template, execution can still report Succeeded. Confirmed via `az rest`: the real `/start` REST body is the bare `StartJobExecutionTemplate` shape (`containers`/`initContainers`, no wrapper) — that shape 400s when the wrapper is present. Bypass the CLI's `--yaml` translation entirely: `az rest POST .../jobs/<job>/start` with a body in the verified bare shape. "Succeeded" status is not proof an override applied — check the execution's own resolved `properties.template` via `az rest GET .../executions/<name>`. Recurred same-day via a different flag (`job create --args '-c' "$CMD"` failed loudly this time — argparse treats `-c` as a new flag, not an --args value) — general fix: scaffold jobs via create/update with NO command override, supply the real per-run command only through `az rest POST .../start`. (active)
- L-0024 [known-hard] `az containerapp job logs show` requires an explicit `--container <name>` even for single-container jobs — omitting it fails fast with a clear CLI usage error (unlike L-0023's silent-failure class). Match the Bicep-declared container `name` (or an explicit `--container-name` set at job create/update time). (active)
- L-0025 [architecture] A hostname in a frozen contract's `servers:` URL or a hardcoded CI env var is a design INTENT, not proof DNS/custom-domain infra backs it — confirmed live: `model-gateway.internal.cmos.dev` had no matching private DNS zone anywhere and the Container App had no customDomains bound, so curl got HTTP_STATUS=000 (no response at all) even though the app itself was healthy and ingress was correctly configured. Resolve the resource's real live FQDN (`properties.configuration.ingress.fqdn`) instead of hardcoding the aspirational one — same principle as L-0021, now for DNS. Add curl's own exit code to smoke scripts (6=DNS, 7=refused, 28=timeout) since HTTP_STATUS alone can't distinguish these. (active)
- L-0026 [conventions] A routing/config table mapping a logical id to a literal external-system identifier (e.g. an Anthropic model id) can be silently wrong forever if every test goes through a mocked/stubbed provider — the stub accepts any string, proving routing logic works but nothing about whether the VALUE is real. `routing.yaml`'s `claude-haiku` had `claude-haiku-3-5-20241022` (transposed from the real `claude-3-5-haiku-20241022`) — traced back to `.loop/plan.md`'s original spec text, an authoring typo no unit test could catch; only the first live upstream call (404 PROVIDER_ERROR) surfaced it. Fixing the transposition wasn't enough: a live `GET /v1/models` call (2026-07-30) showed the OTHER two entries (`claude-opus-4-20250514`, `claude-sonnet-4-20250514`) were ALSO retired — the smoke test only ever exercises the one tier its hardcoded request uses, so verifying one entry doesn't verify its siblings. All three updated from the live response (deliberately conservative picks — claude-opus-4-8/claude-sonnet-4-6, not the newest claude-opus-5/claude-sonnet-5 generation also live on the account — with the newer options noted in routing.yaml for a later eval-backed promotion). A plan document is a hypothesis about external identifiers, not proof — and neither is fixing just the entry that happened to fail first. Implemented the structural fix too: a FastAPI `lifespan` startup check (`main._validate_routing_against_live_models`) calls `GET /v1/models` once per process start and logs one clear `routing_model_retired` line per stale route, covering all tiers on every deploy. (active)
- L-0027 [architecture] CAPSTONE — the full deploy-infra -> deploy-gateway -> live completion -> metering chain is proven end to end.
