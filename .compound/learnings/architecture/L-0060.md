statement: CAPSTONE — the [[L-0048]] 3-part image-bootstrap contract and its [[L-0049]] 4th part (no `registries[]` in the initial create) is no longer "a lesson from an incident" — it has now independently reproduced on the FOURTH new Container App this repo has ever authored (model-gateway — original discovery, then ca-orchestrator, ca-console, and now mcp-web/mcp-buffer/mcp-canva all hit the identical MANIFEST_UNKNOWN-for-`:latest` failure the moment they were first deployed). Every one of those four sessions designed its Container App(s) without this contract, shipped, and only discovered the gap live at deploy-infra time — costing a full incident-diagnosis-and-fix round trip each time, on a bug whose shape is now fully known in advance. This is a STANDING CONTRACT for any future new Container App/Container Apps Job fed by a separately-built image, not a pattern to rediscover per session: (1) the Bicep image param defaults to a public MCR placeholder, never a self-computed `.../<service>:latest`; (2) deploy-infra.yml's preflight resolves it to the resource's CURRENT live image once one exists (apps: check `latestReadyRevisionName`; jobs: check the persisted `template.containers[0].image`, no revision concept), never regressing a running resource back to placeholder; (3) if the resource needs a private-registry pull identity, the Bicep template never declares `registries[]` at all — a separate, gated CI workflow's `az containerapp registry set` / `az containerapp job registry set` is the sole, exclusive, every-run setter; (4) that same gated workflow is the ONLY thing that ever calls `az containerapp update --image` / `az containerapp job update --image`, pinned to a commit SHA, never `:latest`; and its image-build step resolves its target registry from an authoritative deployment/binding record (`az deployment group show -n container-registry`), never an ambient `az acr list [0]` pick.

evidence: Chronologically: model-gateway (L-0018, original discovery of parts 1-2-3) -> ca-orchestrator (L-0048, PR #29, independently re-derived the same 3 parts plus the ACR-resolution fix) -> ca-console (L-0049, same-day, discovered the 4th part — `registries[]` + a co-created identity in one PUT is a confirmed Azure platform limitation, microsoft/azure-container-apps#1467) -> mcp-web/mcp-buffer/mcp-canva (this fix, 2026-07-31): deploy-infra failed provisioning all three with MANIFEST_UNKNOWN for `mcp-{web,buffer,canva}:latest`, the exact same failure signature as ca-orchestrator's, because infra/main.bicep computed those image references directly and none of the images had ever been built — despite L-0048 already being recorded in `.compound/index.md` at the time this session's build was originally planned. Four for four: every session that authored a new Container App without pre-applying this contract hit it live, none caught it at plan-review time.

catch_next_time: A plan or spec that introduces ANY new `Microsoft.App/containerApps` or `Microsoft.App/jobs` resource whose image comes from a separate CI/CD build (not a public/pinned base image with no build step) must include all 4 parts of this contract in the FIRST version of the plan, not as a follow-up fix — this is now a Must-have, not a nice-to-have, for plan-reviewer to enforce at review time: (a) grep the new Bicep module for a self-computed `${...loginServer}/...:latest`-shaped image expression — reject it; (b) grep for a `registries[]` block referencing a `userAssignedIdentityId`/`principalId` created earlier in the SAME deployment — reject it, require the CLI-owned `registry set` pattern instead; (c) confirm the deploy workflow that applies the shared main.bicep template has a matching "preserve live image, bootstrap with placeholder" preflight step for the new resource, threaded into every `what-if`/`create` invocation; (d) confirm exactly one other workflow (gated, `environment: cmos-dev`, SHA-pinned tags) is the sole caller of the CLI image-update command for that resource. Do not accept "we'll fix it if deploy-infra fails" as a plan — the failure is now provably certain, not merely possible. IMPORTANT — for part (b) specifically, when the new resource is a `Microsoft.App/jobs` (not a `containerApps`), see [[L-0061]]: dropping `registries[]` alone reproduced this bug anyway (`IdentityDoesNotExist`) — a job needs the FULLER fix (no `identity` block at all in Bicep, CLI does `job identity assign` then `job registry set`), not the app-level half-measure.
