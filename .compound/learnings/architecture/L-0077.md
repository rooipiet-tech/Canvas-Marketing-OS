statement: An orchestrator/compounder must distinguish a MECHANICAL/ENVIRONMENT halt from a CODE-CORRECTNESS halt using a concrete, checkable signature — not just the SHIPPABLE gate's raw pass_rate — because conflating the two poisons future runs with a false "the code doesn't work" lesson when the code was independently proven correct.

evidence: On the s9-analytics run, 12/35 criteria failed to execute (pass_rate 0.6136, below the 0.90 SHIPPABLE threshold), forcing a mechanical HALT per the letter of the scoring rule. But state.json's halt_diagnostic carried a full evidence_this_is_not_a_correctness_defect list: output-reviewer independently hand-traced the failing SQL/arithmetic logic against every fixture row twice (once per build iteration) and confirmed it correct both times; zero regressions occurred between the two test iterations despite a full defect-fixing patch in between; all 6 review lenses (output-reviewer, risk-security, data-residency, migration, performance, agent-native) signed off clean with zero open blockers or majors; and the failing criteria's designed real-execution venue was the build's own CI job (a postgres:16 service container), never the orchestration sandbox that ran this loop. The stagnation_signal explicitly noted the identical failure signature repeated unchanged across a full patch iteration — proving further build/plan iteration would not have helped, since the constraint was environmental, not a code defect.

catch_next_time: Before recording a halt as a correctness failure, check this 4-part signature: (1) open blocker/major findings across ALL fired reviewers = 0, (2) all reviewer sign_off = true, (3) 100% of failing criteria have failure_class="test" (never "build"/"logic"), each tracing to ONE single confirmed-unavailable dependency, (4) zero regressions between the last two test iterations. If all four hold, classify the halt as environment/tooling, not correctness — the fix target recorded in the diagnostic should be "provision the missing dependency in CI or this sandbox," never "fix the code." Report this distinction explicitly to the user rather than silently treating either a false PASS or an undifferentiated HALT as the outcome.
