statement: A Container App's SystemAssigned identity's `principalId` cannot
be used to grant that same app's own role assignments (e.g. AcrPull, Key
Vault Secrets User) in the same Bicep deployment if the app's first revision
needs those very grants to become healthy. Bicep can only resolve
`app.identity.principalId` once the app's deployment operation reaches a
terminal state, but a Container App's deployment does not reach terminal
state until its first revision goes healthy — so if that revision needs a
role this same deployment is supposed to grant, the deployment deadlocks and
times out ("Operation expired") with the role assignment never created at
all. A UserAssignedIdentity resource has no such lifecycle coupling — its
principalId is available the instant the resource exists — so granting roles
to a UserAssigned identity created and referenced by the app (via
`identity.userAssignedIdentities` and per-secret/per-registry `identity:
<uai.id>`) breaks the cycle entirely.

evidence: gateway.bicep's round-1 fix (L-0017) moved the AcrPull grant into
gateway.bicep itself, referencing `gatewayApp.identity.principalId` — the
same pattern the pre-existing Key Vault Secrets User grant already used.
Deployed for real, the Container App sat in `provisioningState: Failed`
("Failed to provision revision ... Operation expired") for 20+ minutes; its
event stream showed repeated `ACR token exchange endpoint returned error
status: 401`; and `az role assignment list --assignee <principalId>` came
back completely empty — confirming neither role assignment resource had
ever actually been deployed, not just that the grants hadn't propagated yet.
Root cause: both role assignments were waiting on gatewayApp's deployment to
finish, and gatewayApp's revision could never finish without them (AcrPull
to pull any private-registry image; Key Vault Secrets User to resolve the
`anthropic-api-key` secret reference before the container could even
start — this made the deadlock unconditional, independent of which image
was configured). Fixed by adding a `Microsoft.ManagedIdentity/
userAssignedIdentities` resource, granting both roles to its principalId,
and switching the Container App to `identity.type: 'UserAssigned'` with an
explicit `dependsOn` on both role assignments (necessary here since nothing
in the app's params references their outputs, so Bicep would not otherwise
infer the ordering).

catch_next_time: Whenever a Bicep module grants a role assignment to a
resource's own SystemAssigned identity, ask whether that resource's OWN
successful provisioning depends on the granted role (e.g. any managed
resource that must pull an image, resolve a secret, or reach another
Azure service as a precondition of going "healthy" during its own create).
If yes, SystemAssigned + same-module role assignment is a latent deadlock,
not just a slow-propagation risk — switch to a UserAssignedIdentity created
and granted BEFORE the dependent resource instead. Plan-reviewer checklist
item for any new IaC-defined compute resource with in-template RBAC grants
to its own identity: "does this resource's health check require the role
this deployment grants it?"
