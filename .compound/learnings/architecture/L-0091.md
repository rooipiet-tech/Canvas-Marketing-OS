statement: A Container App with TCP-transport ingress (here ca-pgbouncer,
port 6432) is reached by other apps in the same environment by its NAME and
port, not by its `ingress.fqdn`. The generated `<app>.internal.<env>.
azurecontainerapps.io` FQDN resolves to the environment's proxy address, where
nothing answers on the app's TCP port, so every connection hangs rather than
being refused. This refines L-0025: "read the live `ingress.fqdn`, never a
guessed hostname" is right for HTTP apps and wrong for TCP apps. Separately, a
TCP proxy in front of Postgres must itself offer client-side TLS when callers
use `sslmode=require`; PgBouncer's `server_tls_sslmode` only covers its hop to
Postgres.

evidence: deploy-pipeline run 85 failed at the Vault smoke test: ca-vault was
healthy but every database call hung (`asyncpg.create_pool` -> connect ->
`TimeoutError`). Its stored connection string pointed at
`ca-pgbouncer.internal.<env>...:6432` (main.bicep's `pgbouncerFqdn`, one
variable feeding 8 call sites). After the real PgBouncer image was deployed by
hand (the pipeline could not: stage 3 `needs` stage 2, and the Vault smoke test
runs inside stage 2), deploy-pgbouncer run 2 showed PgBouncer healthy and
listening with NO connection logged, and run 3's probe (5s timeouts) showed:
the FQDN resolves to 100.100.0.208 and TCP, pg_isready and psql (with and
without TLS) all time out on 6432; the bare name `ca-pgbouncer` resolves to
`ca-pgbouncer.k8se-apps.svc.cluster.local` (100.100.237.33), connects at once,
and psql then fails with "server does not support SSL, but SSL was required".
A local reproduction (PgBouncer 1.22 + Postgres 16, the real entrypoint.sh)
gave the identical error with the old entrypoint and `SELECT 1` through
PgBouncer over TLS with the fixed one. The Container Apps docs say a TCP app "is
accessible to other container apps in the same environment via its name ... and
exposed port number".

catch_next_time: When a new TCP-transport Container App is wired to callers,
connect to its app NAME (taken from the module's `appName` output, so the Bicep
dependency stays a real reference, L-0017) and prove it from INSIDE the
environment before trusting it: a probe job with short timeouts that tries the
FQDN and the name, DNS, raw TCP, and the exact client (psql with the callers'
sslmode). A silent hang with a healthy replica and an empty app log means the
traffic never reached the app, not that the app is broken. Check each hop's TLS
separately. Capture logs while the job is still Running: the replica is gone
once it stops, and `az containerapp job logs show` then returns only
"Kubernetes error happened". `az containerapp logs show --type system` is JSON
only (`--format text` is rejected). Guarded by
services/orchestrator/tests/test_pgbouncer_is_reached_by_name_with_client_tls.py.
