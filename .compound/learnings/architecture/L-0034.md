statement: `az deployment group what-if` does not return a literal
all-`NoChange` result for a genuinely no-op redeploy of a real, nontrivial
Bicep template — a gate/automation keyed on "what-if reports zero changes"
will not fire, ever, on such a template, even though nothing meaningful
actually changed. Two independent, unrelated causes stack: (1) any
`@secure()` parameter that's regenerated fresh on every run (a rotated
throwaway password, a fresh token) makes what-if report the resource it
feeds as `Modify` every single time, forever, since what-if has no way to
know the new value is "equivalent" to the old one it can't see; (2) Azure's
own what-if engine has real, persistent false-positive `Modify` noise on
several resource types independent of any parameter — observed on
`Microsoft.ServiceBus/.../queues`, `Microsoft.Network/privateEndpoints/.../
privateDnsZoneGroups`, and `Microsoft.Authorization/roleAssignments` — plus
`Ignore` entries for every resource that exists in the resource group but
isn't declared in the template being diffed (other sessions' resources,
auto-created network interfaces for private endpoints, etc.), which is
normal and not itself informative either way.

evidence: Live-verified against `cmos-dev`'s actual current (genuinely
unchanged) state, using the exact live values `deploy-infra.yml`'s own
preflight would compute (current gateway image, a fresh throwaway
password): `az deployment group what-if ... --no-pretty-print -o json
--query "changes[].changeType" | sort | uniq -c` returned 13 `Modify`, 12
`Ignore`, only 14 `NoChange` — zero `Create`/`Delete`. The 13 `Modify`
entries included `psql-cmos-dev` (the fresh-password effect), two
ServiceBus queues, three `privateDnsZoneGroups/default` resources, two
`Microsoft.Authorization/roleAssignments`, and the ContainerApp/managed-
environment/registry resources themselves — none of which reflected any
actual intended change; the deployment's real effect, if applied, would
have been a no-op.

catch_next_time: Never gate CI automation on "what-if returns zero total
changes" for a real template — verify the ACTUAL noise profile live first
(exactly this check: run what-if against current known-unchanged state and
tally `changeType` counts) before assuming what "no changes" looks like.
The workable signal isn't "zero Modify entries" (that will essentially
never be true) but "zero `Create`/`Delete`/`Deploy`/`Unsupported` entries"
— the unambiguous "resource topology changed" signal, distinct from
property-level noise. Even that signal alone is not sufficient on its own:
a genuine, real property-level edit (e.g. bumping a container's CPU/memory
in Bicep) shows up ONLY as `Modify`, identical in kind to the noise above,
so relying on what-if alone would let a real change slip through
unreviewed. Pair it with a second, independent signal that's precise about
the thing that actually matters — whether the triggering commit touched any
infra-defining file at all (`git diff --name-only` against the previous
commit) — and require BOTH before treating a deploy as safe to auto-pass.
Log which signal(s) blocked or allowed the decision on every run, so a
gated (or auto-passed) deploy is self-explanatory without re-deriving this
reasoning from scratch.
