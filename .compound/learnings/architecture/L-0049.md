statement: A Container App's user-assigned identity cannot be both newly attached via `identity.userAssignedIdentities` AND referenced by `registries[].identity` for ACR pull auth in the SAME initial `Microsoft.App/containerApps` create call — this is a confirmed, documented, unresolved Azure platform limitation (microsoft/azure-container-apps#1467), not a Bicep dependency-ordering mistake in the usual [[L-0020]] sense (the identity itself, and its AcrPull role assignment, can be fully created and propagated minutes beforehand — the failure is still instant, ~1-2s, a synchronous validation rejection, not an eventual-consistency race). ARM's error (`IdentityDoesNotExist` / "No managed service identities are associated with resource `<app-name>`") is misleading: it reads like an ordering bug but occurs even when the identity is provably already fully provisioned. Extend the [[L-0048]] 3-part image-bootstrap contract with a 4th part for any NEW Container App that also needs a private-registry pull identity: the Bicep template never declares `registries[]` at all (bootstrap with a public placeholder image needing no registry auth), and the CI deploy workflow's `az containerapp registry set` (Microsoft's own documented reliable workaround) is the sole, exclusive, every-run setter of the ACR-pull identity — mirroring how the image tag itself is already CI-owned, not Bicep-owned.

evidence: ca-console's maiden deploy-infra run failed provisioning with `IdentityDoesNotExist`, duration 1.48s (`az deployment operation group list -g cmos-dev --name console-app`). Live-verified this was NOT a propagation-timing issue: `console-identity` (the identity resource) succeeded at 10:40:29, `container-registry-console` (its AcrPull role assignment, resolving the SAME identity's principalId) succeeded cleanly at 10:40:46 — only 17s later, itself proof the identity was already fully readable by another RP — yet `console-app`'s attempt at 10:44:24 (almost 4 minutes after the identity was created) still failed instantly. Every OTHER container app that deployed cleanly in the same run (gateway, vault, gatekeeper-app, publisher-app) was confirmed (via `az containerapp show`) to be an idempotent re-apply of an app that already existed from a PRIOR deploy, with an identity already attached from that prior deploy — none of them were a genuine first-ever create combining a brand-new `identity.userAssignedIdentities` attachment with a `registries[].identity` reference to that same identity in one PUT. ca-orchestrator's own near-simultaneous first-ever create (also a fresh identity + fresh app) succeeded PAST identity validation (19.47s, failing later on an unrelated missing-image-tag error) — ruling out "any brand-new identity + registries[] combo always fails" as too broad a rule; the precise trigger remains unconfirmed (possibly related to gateway/orchestrator's identity+AcrPull-grant+app all living in ONE nested Bicep deployment vs. console's THREE separate nested module deployments, but this is unconfirmed and not required to apply the fix). WebSearch corroborated: microsoft/azure-container-apps#1467 ("Unable to set Container Identity used for Container Registry Authentication using ARM templates") is this exact, still-open issue; community consensus is `az containerapp registry set` via CLI, post-creation, is the only reliable workaround.

catch_next_time: When a plan or build adds a new Container App that both (a) receives a user-assigned identity for the first time and (b) needs that identity for `registries[].identity` ACR-pull auth, require the registries[] property be OMITTED from Bicep entirely (never even an empty array — an omitted property survives incremental re-deploys untouched, while an explicit `[]` would wipe out whatever the CI-side `az containerapp registry set` step configured). Bootstrap the image param with the standard L-0048 public placeholder so the very first create needs no registry auth of any kind, and add `az containerapp registry set -n <app> -g <rg> --server <acr-login-server> --identity <identity-resource-id>` as its own CI step, run every deploy, immediately before the image-update step (idempotent, safe to repeat). Do not spend time trying to prove/reproduce the exact internal trigger before applying this fix — the documented Microsoft issue and the CLI workaround are sufficient; treat any `registries[].identity` referencing a co-created identity in Bicep as a standing defect at plan-review time, same as [[L-0048]] treats a self-computed `:latest` image reference.
