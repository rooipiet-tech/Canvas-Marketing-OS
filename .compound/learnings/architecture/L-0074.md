statement: A "goes live automatically the moment real credentials exist, no code change needed" dual-mode design (mcp_common/credentials.py's `resolve_secret`/`is_live_mode`/`flag_enabled`, AC-4/AC-6/AC-7) is correct and desirable for real production traffic, but it means ANY caller reaching that code path — including an automated protocol-conformance smoke test whose own contract explicitly says "fixture mode, no live secrets present" and whose sample arguments are deliberately synthetic garbage never meant to reach a real vendor — silently starts making real, uncontrolled vendor API calls the instant an unrelated human errand loads credentials into the same shared environment. The two concerns (test isolation and live-mode-by-default for real traffic) are in direct tension and cannot both be satisfied by a purely environment-global credential-presence switch; they need a request-scoped override layered on top.

evidence: caj-mcp-smoke (deploy-mcp #26 attempt 2, 2026-08-02) failed `test_conformance.py::test_mcp_conformance` for all 3 mcp-* servers on `assert result["structuredContent"]["source"] == "fixture"` — actual value `"live"`. Root cause: `buffer-api-key`/`canva-client-id`/`canva-client-secret` landed in Key Vault via a same-day human credential-loading errand (unrelated to this deploy), and `ca-mcp-web`'s `MCP_WEB_LIVE_MODE` flag was separately set — both are the documented, intended trigger for `resolve_secret`/`flag_enabled` to flip live, with zero code or config changes required by design. The conformance test's own docstring states its contract is "AC-1: MCP protocol conformance ... in fixture mode ... with no live secrets present," using synthetic arguments (`SYNTH-TEMPLATE-0001`, `example.com/synthetic`) — meaning this smoke run had just made real Buffer/Canva API calls with fake data from an unattended CI/CD gate, with no prior deliberate sign-off that doing so was safe (a POPIA/permission-register concern the operator flagged before any fix was proposed). Loosening the test's assertion to accept `'live'` (the "cheap pass" option) would have stopped verifying the actual AC-1 contract and done nothing about the uncontrolled live vendor calls.

catch_next_time: (a) When designing a dual-mode (fixture/live) system gated purely by ambient credential/flag presence, decide UP FRONT whether every caller that can reach that code path is meant to follow the ambient switch, or whether some callers (protocol/conformance smoke tests, synthetic health checks) need a way to opt out regardless of ambient state — retrofitting this after a live incident (as here) is more expensive than designing it in from the start. (b) The fix is a request-scoped override (here: a `contextvars.ContextVar` set from an inbound HTTP header for the duration of one request, reset via context manager/try-finally — never a permanent server-side env var, which would defeat the "goes live the moment creds exist" property for real traffic), not a test-assertion change — an assertion change papering over unverified/unsafe live side effects is never the right fix even when it's the smallest diff. (c) A test whose own docstring states an explicit environmental precondition ("with no live secrets present") is documenting an INVARIANT the test needs enforced, not just describing incidental circumstances at authoring time — when that invariant can be violated by state the test doesn't control (ambient Key Vault contents, set by an unrelated human/process), the test's plumbing (here: its HTTP client factory) needs to actively enforce the invariant per-request, not assume the environment will cooperate. (d) Before shipping any fix here, reproduce the EXACT failing condition locally (real-shaped creds + live-mode flag both set) and confirm the fix holds under it — a fix validated only against the "no creds" default case would not have caught a regression in the override logic itself.

FOLLOW-UP (2026-08-02, same day, live — escalation 8, deploy-mcp #27): the request-scoped override above works exactly as designed for mcp-buffer/mcp-canva, but mcp-web's `fetch_url` tool has a SECOND ordering-sensitive guard — `check_allowlist()` (AC-17's SSRF egress allow-list), which ran unconditionally BEFORE the fixture-mode check in the tool's own body, not inside `mcp_common`'s shared credential-resolution layer this learning's fix touched. `force_fixture_mode()` was correctly active, but `fetch_url()` never got as far as checking it — `check_allowlist()` raised first, rejecting the conformance test's synthetic `example.com` argument because `ca-mcp-web`'s LIVE `MCP_WEB_ALLOWLIST` had already diverged from the code's own example.com-inclusive default. Root design point: AC-17's real guarantee is "no network call reaches a non-allow-listed host" — a guarantee that is vacuously already satisfied in fixture mode (no network call ever happens there regardless of the URL), so gating on it before the fixture check added a fragile coupling (the fixture's synthetic host must also happen to be on whatever the LIVE allow-list currently contains) with zero actual security benefit. Confirmed safe to reorder by reading `test_web_allowlist.py`'s own AC-17 test suite: both its tests explicitly set `MCP_WEB_LIVE_MODE=true` — fixture mode was never actually exercised against this guard, so there was no existing contract requiring it to run there.

catch_next_time (additional): (e) A request-scoped mode override implemented at a SHARED layer (here: `mcp_common.credentials`) does not automatically make every consumer's business logic respect it — audit every code path between "the override is set" and "the override is checked" for OTHER guards/validations that might run first and short-circuit before the override's check point is ever reached. A fix at the shared layer is necessary but not sufficient when individual consumers have their own pre-checks. (f) When a guard's docstring says "runs before X, in every mode" (here: "before any network access ... in both fixture and live mode"), verify that claim against that guard's OWN test suite before assuming it's an enforced contract — if every existing test for that guard only ever exercises it under one of the modes, the "in both modes" part of the docstring is unverified/aspirational, not proven, and safe to revisit. (g) A validation/security guard whose sole purpose is protecting a specific downstream action (here: the one real network GET) should be ordered immediately before that action, not before other unrelated branches (e.g. the fixture short-circuit) that never reach it — order guards by what they actually protect, not by textual convention ("validate arguments first, always").
