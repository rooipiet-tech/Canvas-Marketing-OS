statement: CAPSTONE — the full deploy-infra -> deploy-gateway -> live
completion -> metering chain is now proven end to end, live, against real
Azure infrastructure and the real Anthropic API. This is the last link: every
prior link in the chain (Bicep provisioning, image build/push/pull, managed
identity + RBAC, DNS/ingress, secret resolution, routing, the actual
provider call, and now metering) has independently failed at least once
during this build and been fixed forward with live evidence, not assumption.
The specific bug that closed this final link was NOT in the gateway or the
database — the gateway's metering was already correct, synchronous, and
correctly attributed. It was a CI *log-parsing* bug (an anchored regex
against a JSON-wrapped CLI output format), the same class of "the fix is in
the tooling, not the system under test" surprise this build has hit
repeatedly (L-0021's ACR list, L-0023's `--yaml` shape, L-0025's hardcoded
hostname). Diagnosing the CI script before the application code — reading
the actual raw log bytes rather than trusting a summary — is what kept this
from becoming a wrong fix to a working gateway.

evidence: Live diagnosis in order, per the four checks requested: (1)
`ca-model-gateway`'s own structured log line
`{"event":"completion","agent_run_id":"3fe73e53-...","status_code":200,...}`
confirmed the completion was served cleanly, no error anywhere in the
window. (2) The gateway's DB/secret wiring was never in question — it had
already been proven live by this same request succeeding. (3) Checked
whether metering races the response: `completion.py` `await`s
`metering.record_completion_costs(...)` synchronously, INLINE, before
constructing the response dict — no async gap exists for the assert to
race. (4) `az rest GET` on the failed cost-check job's own execution
confirmed the exact submitted query
(`select count(*) from costs where agent_run_id = '3fe73e53-...'`) —
correct attribution. The actual count, fetched via Log Analytics
(`ContainerAppConsoleLogs_CL`), was `3` (not 0) — `metering.py` writes
three unit-typed rows (`usd`/`tokens`/`ms`) per completion by design.
`deploy-gateway.yml`'s own parse,
`az containerapp job logs show ... | grep -Eo '^[0-9]+$'`, could never
match: that CLI's raw stdout is one JSON object per line
(`{"TimeStamp":"...","Log":"3"}`), never a bare digit-only line, so the
`^$`-anchored pattern silently produced an empty `$COUNT` on a completely
correct database. Separately, verifying the "must log loudly, must never
fail the completion" requirement found a REAL gap: `completion.py` had no
error handling around the metering write at all — a genuine DB failure
would have propagated to a 500 for an already-successful, already-paid-for
completion. Fixed both: the CI parse (extract the JSON envelope's `.Log`
field via `jq`, then search it unanchored) and the gateway (wrap the
metering write in try/except, log a structured `metering_write_failed`
ERROR, omit `cost_id` from the response rather than failing it —
contract-safe, since `cost_id` isn't in `CompletionResponse.required`).

catch_next_time: When a "the assert says X failed" report reaches the
integration/system-under-test's OWN application logs first and finds no
error there, treat the CI tooling itself as the prime suspect before the
system it's testing — this build's track record is now 4-for-4 on that
exact pattern (L-0021, L-0023, L-0025, and this one). Specifically: any
parse of `az containerapp job logs show` output must account for its raw
format being one JSON object per line
(`{"TimeStamp":...,"Log":"<content>"}`), never bare text — an ANCHORED
pattern (`^...$`) against that stream will never match; extract `.Log` via
`jq` first, then search unanchored. Separately and more generally: every
write that happens AFTER a request's real, valuable work is already done
(metering, audit logging, analytics) needs an explicit availability-first
review — "if this specific write throws, does the caller lose a result
they already earned?" — and a bare `await` with no try/except around a
post-success side-effect is the default failure mode to check for, not an
edge case to assume someone already handled.
