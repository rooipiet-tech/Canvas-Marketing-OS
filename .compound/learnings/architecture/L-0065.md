statement: A required Bicep parameter with no default that is sourced from a `${{ secrets.* }}` value scoped to a GitHub Environment (e.g. `environment: cmos-dev`) is invisible, by design, to any *ungated* job that also deploys the same template — GitHub Environment secrets are only injected into jobs that declare that `environment:`, and an ungated `what-if` preflight job (the established pattern: free/idempotent validation runs outside the approval gate so retries are unattended) deliberately has no `environment:` at all. Every workflow that independently redeploys a shared multi-module template (not just the template's "owning" workflow) needs its own copy of the same explicit-placeholder-for-what-if / real-secret-with-fallback-for-real-deploy pattern for every such parameter — adding the parameter to the template and to ONE workflow is not sufficient; every OTHER workflow that also deploys that template needs the identical treatment, or it breaks the moment that parameter stops having a safe Bicep-level default (by design, per AUTH-003-class requirements that some parameters MUST stay required).

evidence: `infra/main.bicep`'s `consoleClientId` parameter has no default (frozen `AUTH-003` requirement — App Registration client IDs are never allowed a guessable/fake default that could accidentally authenticate against nothing, and Easy Auth's own fail-closed behavior against an invalid placeholder is the desired Phase-1 state, not a gap to paper over). `deploy-infra.yml` (the template's primary owner) correctly threads a placeholder through its own ungated `what-if` job and the real `${{ secrets.CONSOLE_ENTRA_CLIENT_ID || placeholder }}` through its gated `deploy` job. `deploy-governance.yml` — a SEPARATE, sibling-owned workflow that also runs `az deployment group create --template-file infra/main.bicep` (redeploying the entire shared template, not just its own governance modules, per its own documented concurrency-group reasoning) — was never updated when `consoleClientId` was added, and its ungated `what-if` job failed outright: `ERROR: Missing input parameters: consoleClientId`, live-confirmed 2026-08-01, despite the parameter's real value existing correctly in the `cmos-dev` environment secret the whole time — the secret was simply out of scope for that ungated job by design, not missing or misconfigured.

RECURRENCE (2026-08-01, later same day, live production incident): this learning's own `catch_next_time` — "treat 'which other workflows deploy this same shared template' as a standing checklist item... the same way L-0048 treats image-parameter bootstrapping as a checklist item" — was never actually applied to the SEVEN `*ContainerImage` params (gateway/orchestrator/console/mcpWeb/mcpBuffer/mcpCanva/mcpSmoke) sitting in the exact same shared template. `deploy-governance.yml` only ever resolved-and-passed `gatewayContainerImage`; the other 6 were silently OMITTED from its `az deployment group create` call, so Bicep fell back to each param's own bootstrap-placeholder default on EVERY governance deploy. Confirmed live via direct `az containerapp` queries: `ca-orchestrator`'s ACTUAL active/Ready revision (`ca-orchestrator--rdfghqjvmgaioq`) was genuinely running the real orchestrator image, but the APP-LEVEL `properties.template.containers[0].image` field (which `deploy-infra.yml`'s own preflight trusts as "current") had been reset to the bootstrap placeholder by `deploy-governance.yml`'s prior real deploy — causing the NEXT `deploy-infra` run to "preserve" the placeholder into a brand-new, broken revision that never became Ready (`healthState: Unhealthy`, `runningState: ActivationFailed`, log: a Go-style "Listening on :80..." from the helloworld placeholder, not the Python orchestrator app at all). The bug pattern is identical to the `consoleClientId` incident down to the mechanism (an omitted parameter falling back to an unsafe default in a sibling workflow deploying the same shared template) — only the specific parameter class (image, not secret) differed, and this specific instance was never checked even though the CATCH_NEXT_TIME for the secret-shaped version was already written down.

catch_next_time: When adding a new required (no-default) Bicep parameter sourced from an environment-scoped secret to a shared template like `infra/main.bicep`, grep every workflow file for `--template-file infra/main.bicep` (or the equivalent shared template path) — not just the one workflow being edited — and add the identical two-tier treatment to each: the ungated/preflight job gets an explicit, clearly-commented placeholder value (never omitted, never a Bicep default that would defeat the "must stay required" intent); the gated/real-deploy job (the only job with `environment:` access to the real secret) gets `${{ secrets.X || placeholder }}` with the same fallback, so it degrades gracefully pre-bootstrap and picks up the real value automatically the moment the secret is set, matching the template's own three-phase-bootstrap semantics. THE SAME CHECKLIST APPLIES TO EVERY `*ContainerImage`-shaped parameter in the shared template, not just secret-shaped ones — grep the shared template for ALL `param ... string = 'mcr.microsoft.com/...placeholder'`-shaped image params (or any param with a "preserve current, else bootstrap" intent) and confirm EVERY workflow that independently deploys that template resolves-and-passes ALL of them, not just the ones that workflow's own author happened to remember or that broke loudly enough to notice. When writing a NEW "which params does this sibling workflow need" checklist, enumerate params by grepping the template itself (`grep '^param' main.bicep`), not by copying whatever the workflow currently happens to pass — an incomplete workflow doesn't self-report its own gaps.
