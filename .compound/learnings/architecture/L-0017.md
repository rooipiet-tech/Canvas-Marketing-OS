statement: In Bicep, cross-resource references for ordering must be real
`module.outputs.x` references, never a separately-computed string that
happens to match. A computed-string shortcut used to dodge an apparent
circular dependency removes the *ordering guarantee* along with the cycle —
ARM will happily provision the dependent resource before the one it
actually needs to exist.

evidence: gateway.bicep took the ACR login server as a string computed
independently in main.bicep (`'${containerRegistryName}.azurecr.io'`)
instead of `containerRegistry.outputs.loginServer`, specifically to avoid a
genuine two-way cycle (the registry module took the gateway's
managed-identity principalId as an input for its AcrPull grant). With no
real dependency in either direction between the two modules, ARM had no
ordering guarantee, provisioned the Container App before the registry
existed, and deploy-infra #10 failed with "failed to resolve registry ...
no such host" — the registry's own DNS record didn't exist yet.

catch_next_time: When a plan or diff introduces two Bicep modules that both
seem to need something from each other, look for the actual cycle: it is
almost always one-directional in practice (one module's role-assignment
grant needing the other's principalId), and the fix is to move that grant
INTO the module that needs to give itself access — pull the target resource
in via an `existing` reference and create the role assignment locally,
mirroring however the same file already handles Key Vault access if it does.
Never resolve an apparent cycle by replacing an output reference with an
independently-computed value that merely happens to match; that only hides
the missing ordering guarantee until a fresh environment (or a
resource-group-wide redeploy) exposes it. When reviewing IaC, treat "this
module takes a name as a plain string param instead of a sibling module's
output" as a checklist item worth asking why, not assuming it's cosmetic.
