statement: "Never declare registries[] on a new Microsoft.App/jobs resource" (L-0049/L-0061) is NOT a universal rule — it's specific to a genuinely fresh user-assigned identity racing its own propagation within the SAME deployment operation. Reusing a long-established identity (already used successfully by other resources across prior deployments) with identity.userAssignedIdentities + registries[] together, in the same create call, is a different, empirically-working pattern — and the two failure modes have distinguishable error signatures.

evidence: A new Container Apps Job (caj-loop-e2e-smoke) omitted registries[] entirely, citing L-0049/L-0061 as justification (mirroring mcp-smoke-job.bicep's pattern). It failed on FIRST DEPLOY with `InvalidParameterValueInContainerTemplate` / `UNAUTHORIZED` on the `image` field — ARM validates a container template's image pullability at create time, and with NO registries[] block at all, it attempts an anonymous pull against the private ACR, which 401s. This is a DIFFERENT error than L-0061's `IdentityDoesNotExist` (which fires when the identity ITSELF isn't yet visible to the resource provider). The fix (adding registries[] back, referencing the SAME long-established id-orchestrator identity already used successfully by modules/orchestrator/smoke-test-job.bicep and ca-orchestrator/ca-gatekeeper across prior sessions) mirrors that already-working sibling module exactly.

catch_next_time: When a new Container Apps Job/App needs ACR pull auth via an ALREADY-EXISTING, already-propagated identity (not one created in the same deployment operation), declare `identity.userAssignedIdentities` + `registries[]` together in the initial create call — this is safe and is the simplest, lowest-risk pattern (matches [[L-0021]]/[[L-0048]]'s general preference for fewer moving parts). Reserve the 2-step post-create `job identity assign` + `job registry set` workaround (L-0061's fix) specifically for a identity that is itself newly created in the SAME `az deployment group create` operation as the job that references it. If a maiden-deploy fails, read the ERROR CODE to tell the two failure modes apart: `IdentityDoesNotExist` -> identity-propagation race (L-0061's fix applies); `InvalidParameterValueInContainerTemplate`/`UNAUTHORIZED` on the image field -> missing registries[] entirely (this learning's fix applies, don't reach for the heavier 2-step workaround by pattern-matching on a superficially similar-looking prior incident without checking which error you actually have).
