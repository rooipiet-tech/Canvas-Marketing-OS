statement: Container Apps built-in auth (`Microsoft.App/containerApps/authConfigs` with an Entra ID/Azure AD identity provider) can gate a single externally-reachable route while sibling Container Apps in the same environment stay internal-only — achieved by physically splitting the authenticated surface into its own dedicated Container App (own ingress `external:true` + its own `authConfigs`), not by mixing per-route auth or external/internal routes within one app.

evidence: In the S4 governance build, the Gatekeeper service needed exactly one human-facing, Entra-ID-gated approval-action endpoint while its gate-check/decisions API had to stay internal-only. The design physically split this into two Container Apps: `gatekeeper-app.bicep` (`external:false`, no auth config) and `gatekeeper-approval-app.bicep` (`external:true`, with an `authConfigs` child resource requiring an Azure AD identity provider). The acceptance criterion for this (AC-30) explicitly verified that exactly one governance Container App has `external:true` and that same app carries the `authConfigs` resource.

catch_next_time: When only one HTTP surface in a multi-service Container Apps deployment needs to be internet-reachable and Entra-ID-gated, physically separate it into its own Container App rather than mixing routes/auth within one app. Verify via grep that exactly one Container App resource has `external:true` and that same app carries an `authConfigs` resource.
