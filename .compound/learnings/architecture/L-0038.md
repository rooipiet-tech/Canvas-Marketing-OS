statement: A researcher's plausible-sounding inference about how to satisfy a goal (e.g. reading a "signed, versioned, tag-loadable artefact" requirement as implying an OCI image pushed to a shared container registry) must not be frozen into the spec unchallenged — domain-expert must check the inferred implementation shape against the goal's literal wording and the actual existence of any referenced infra/resources before it becomes an acceptance criterion.
evidence: In the s6-registry build, the researcher inferred the registry artefact should be an OCI image pushed to the platform's shared ACR (since one ACR ruling exists cross-session). Domain-expert (constraint C7) explicitly reversed this: the goal's literal text only requires signed+versioned+byte-identical+tag-addressable, and infra/modules/container-registry.bicep didn't exist in the repo at spec-freeze time (it has since been added by another session for the gateway build) — the OCI/ACR reading was the researcher's own inference, not goal text. Spec.json's out_of_scope list confirms this was excluded before the spec was frozen.
catch_next_time: When a researcher's findings propose a specific technical shape (file format, deployment target, protocol, shared resource) to satisfy a goal, domain-expert must explicitly test that shape against the goal's literal text and verify any referenced prerequisite infra/resources actually exist before allowing it into frozen spec acceptance criteria.
