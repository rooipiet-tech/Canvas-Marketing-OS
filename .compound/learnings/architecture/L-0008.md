statement: Free, idempotent preflight steps (e.g. Azure resource-provider/feature registration) must live outside approval gates so their retries are unattended; only spend-triggering steps sit behind the gate.

evidence: The canvas-marketing-os-foundation deploy pipeline originally ran provider/feature registration inside the same gated deploy-infra.yml pipeline as the real (spend-triggering) deploy. After a real WorkloadProfiles registration timeout (see L-0007), the registration logic was split into its own standalone, ungated workflow (azure-provider-registration.yml) with a self-referential workflow_run trigger that auto-retries up to 2 times via `gh run rerun --failed`. deploy-infra.yml's `what-if` job now starts only once that workflow succeeds (via workflow_run), and only its `deploy` job (the actual `az deployment group create`) remains behind the cmos-dev required-reviewers gate. This means registration retries never wait on human approval, while spend-triggering deploys still do.

catch_next_time: When designing a CI/CD pipeline that mixes free/idempotent preflight operations (provider registration, idempotent resource-group creation, read-only checks) with a spend-triggering or otherwise approval-gated action, put the free/idempotent operations in a separate job or workflow with no `environment:` gate and no dependency on human approval to retry. Only place the actual spend-triggering/high-blast-radius step behind the approval gate. If a preflight step can legitimately take a long time to converge (e.g. async cloud registration), give it a fast path (skip work if already done) plus a generous bound, and consider a bounded self-retry (e.g. workflow_run + run_attempt guard) so transient failures resolve themselves without waking a human, while the approval-gated step still requires one.
