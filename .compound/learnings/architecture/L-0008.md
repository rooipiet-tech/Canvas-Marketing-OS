statement: Free, idempotent preflight steps (e.g. Azure resource-provider/feature registration) must live outside approval gates so their retries are unattended; only spend-triggering steps sit behind the gate.

evidence: The canvas-marketing-os-foundation deploy pipeline originally ran provider/feature registration inside the same gated deploy-infra.yml pipeline as the real (spend-triggering) deploy. After a real WorkloadProfiles registration timeout (see L-0007), the registration logic was split into its own standalone, ungated workflow (azure-provider-registration.yml). deploy-infra.yml's `what-if` job now starts only once that workflow succeeds (via a cross-workflow `workflow_run` trigger — deploy-infra.yml watching azure-provider-registration.yml, which is a different workflow, not self-reference), and only its `deploy` job (the actual `az deployment group create`) remains behind the cmos-dev required-reviewers gate. This means registration retries never wait on human approval, while spend-triggering deploys still do. (An initial design used a self-referential `workflow_run` + `gh run rerun` auto-retry inside azure-provider-registration.yml itself; GitHub rejected this at validation — see L-0009 — so retries there are implemented as in-job bash loops instead, which does not change this learning's core rule.)

catch_next_time: When designing a CI/CD pipeline that mixes free/idempotent preflight operations (provider registration, idempotent resource-group creation, read-only checks) with a spend-triggering or otherwise approval-gated action, put the free/idempotent operations in a separate job or workflow with no `environment:` gate and no dependency on human approval to retry. Only place the actual spend-triggering/high-blast-radius step behind the approval gate. If a preflight step can legitimately take a long time to converge (e.g. async cloud registration), give it a fast path (skip work if already done) plus a generous bound, and retry transient failures with in-job bash loops (see L-0009 — do not use a self-referential workflow_run for this) so failures resolve themselves without waking a human, while the approval-gated step still requires one.
