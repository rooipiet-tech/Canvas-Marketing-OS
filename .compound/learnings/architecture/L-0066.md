statement: Code that passes every local/CI-executed test suite can still be non-deployable, because local tests exercise application logic, not the actual deployment/install-packaging mechanism (hand-maintained BUNDLE_MANIFEST.txt/Bicep loadTextContent bundles, a Bicep-hardcoded single-file migration loader, Bicep env-var wiring for a container's outbound client URLs, or a service's requirements.txt vs. its pyproject.toml) — the identical bug class recurred at least 9 times across one build and its PR-review cycle.

evidence: (1) functions/ dir staging fixed during rebase reconciliation citing L-0062/L-0063 precedent. (2) risk-security RS-01 (blocker): services/gatekeeper and services/publisher's BUNDLE_MANIFEST.txt never got 5 new files added -> real deployed image ImportError-crash-loops; scripts/verify_governance_bundle_reconstruction.py only runs on workflow_dispatch/workflow_run, never on pull_request. (3) migration lens F-1 (blocker): infra/main.bicep's orchestratorMigrationSql loadTextContent loads only 0001_orchestrator_init.sql, never 0002/0003, even though the new code depends on both at runtime; CI tests pass only because conftest.py applies migrations/*.sql via a glob that masks the production wiring gap. (4) agent-native F1 + performance PERF-04 (blocker): all 4 of orchestrator's client base-URL resolvers fall through to an uncached `az containerapp show` subprocess shell-out with zero Bicep env-var wiring, and the image never installs azure-cli, so resolution silently returns None in the real container. (5) POST-MERGE, PR review round: mechanical telemetry adoption across ~10 services added `opentelemetry-api` to every service's pyproject.toml, but 5 of those services (gatekeeper, publisher, registry, model-gateway, vault) install their REAL runtime dependencies from a separate requirements.txt — the file their Dockerfile/CI job actually installs from — which never got the same addition. (6) SAME PR REVIEW ROUND, a SECOND layer beneath (5): fixing `opentelemetry-api` in registry's requirements.txt only got the CI job one step further before hitting `ModuleNotFoundError: No module named 'telemetry_lib'` — registry, model-gateway, vault, AND (see correction below) gatekeeper/publisher ALL import the shared `telemetry_lib` wrapper package (services/telemetry-lib) directly, not just raw opentelemetry. telemetry_lib is a local sibling package published to no index, so no requirements.txt can ever express it. (7) CORRECTION, live production incident (2026-08-01, POST-MERGE): (6)'s own claim that "gatekeeper/publisher use raw opentelemetry and were genuinely fully fixed by (5) alone" was ITSELF WRONG — the verification grep used (`grep -n "^from\|^import" ... | grep -i telemetry_lib`) was anchored to line-start (`^`), which matches only TOP-LEVEL imports and silently misses a LAZY import indented inside a function body. Gatekeeper's and publisher's `emit_span()` both did `from telemetry_lib import start_span` as the FIRST LINE of the function (4-space indented, invisible to that grep). Every single live POST /gate-check request 500'd with the identical `ModuleNotFoundError: No module named 'telemetry_lib'`, undetected through: the entire original build+review+patch cycle, `verify-governance-bundle`'s CI check (which only tests IMPORT of `main.py`, and this import is lazy/inside a function, never triggered at module-import time), and the one local test that WOULD have caught it (`test_gate_check_endpoint_still_reachable_with_telemetry_wrapping`) being SKIPPED everywhere (needs a live Postgres, unavailable in every sandboxed run) — only surfacing when a human operator ran the real live smoke test against the real deployed service. Root architectural fix (not just a workaround): governance-bundle services (gatekeeper, publisher — raw-file-copy deployment, no `pip install -e` mechanism for local sibling packages at all, unlike Docker-image-built services) cannot depend on telemetry_lib as an import AT ALL, ever — the correct design was always to inline the ~15 lines of span-attribute logic they actually need, not to import a package their deployment model structurally cannot supply.

catch_next_time: (a) A grep-based "does this file import X" check must NOT anchor to line-start (`^from`/`^import`) — match indented imports too (`\bfrom X import\b` unanchored, or better, use `python -c "import ast"` to walk the real import graph) — an anchored grep silently missing a lazy/deferred import is a FALSE NEGATIVE that reads as "verified clean" when it verified nothing. (b) Before any service adopts a shared library, classify its deployment mechanism FIRST: does it build a Docker image (pip install -e a local sibling package works) or is it a raw bundle/file-copy deployment (a local sibling package can NEVER be installed — the library's logic must be inlined/duplicated, not imported, no matter how "mechanical" the adoption is meant to be) — this determines the entire adoption strategy, not just which requirements.txt entry to add. (c) Add a pull_request-triggered CI check that, for every service deployed via a hand-maintained bundle/manifest OR a requirements.txt distinct from pyproject.toml, diffs the packages/files the service's code ACTUALLY imports (via AST, not line-anchored grep) against what its REAL install-time manifest declares, and fails on any mismatch — including lazy imports. (d) When a change touches N services mechanically, enumerate up front which of the N install from pyproject.toml (safe) vs. a separate requirements.txt/bundle-manifest (needs its own, separately-verified edit, and possibly a structurally different fix if a non-PyPI sibling package is involved) — do not assume all N share one convention. (e) After fixing a ModuleNotFoundError, re-run the EXACT failing check (not just a static grep) before declaring it fixed — a passing local test suite with the crashing test SKIPPED is not evidence of a fix.

RECURRENCE #3 (2026-08-02, live production incident, caj-loop-e2e-smoke #8 attempt 2): this time in ca-orchestrator itself — a genuinely Docker-image-built service (not a bundle-deployed one like (7)'s gatekeeper/publisher), where `pip install -e` a local sibling package DOES structurally work, and console/Dockerfile already proves the correct pattern (`COPY services/telemetry-lib` + `pip install` it from a repo-root build context). orchestrator/dispatch.py does a module-level `from telemetry_lib import set_span_attribute` (line 40, NOT lazy — (a)'s AST-import-check would have caught this one easily, but no such check was ever built per (c)). orchestrator/pyproject.toml's own header comment claimed telemetry-lib was "installed as a separate `pip install -e services/telemetry-lib` step... mirrors console/pyproject.toml's identical convention" — but that step was never actually added to services/orchestrator/Dockerfile or .github/workflows/orchestrator-image.yml; the comment described an aspiration, not a real step, and nothing ever checked the claim against the actual Dockerfile. Confirmed live via Log Analytics (`ContainerAppConsoleLogs_CL` queried directly with `az monitor log-analytics query`, using the already-installed `log-analytics` CLI extension — the `containerapp` extension's `az extension add` was broken in the working sandbox, `pip._vendor.pyproject_hooks._impl.BackendUnavailable: Cannot import 'maturin'`, because az's bundled Python (3.14.5) has no prebuilt wheel for one of the extension's transitive deps and pip fell back to an sdist build that needs a Rust toolchain via maturin — installing maturin into az's bundled Python unblocked `az extension add` too, but Log Analytics was the faster, no-install path and is the generally better tool for querying a specific execution's/time-window's logs since it supports real KQL filtering instead of piping a raw stream through jq): every one of 23 decomposed heartbeat tasks failed identically (`task_handling_failed`, `error: "No module named 'telemetry_lib'"`), and because /health and GET /runs/{task_ref} never import dispatch.py, the app kept responding 200 the whole time — the smoke job's 40-attempt poll just saw "0/7 stages terminal" forever instead of any error, reading as a hang rather than a crash.

catch_next_time (additional, beyond the 5 parts above): (f) A pyproject.toml/README comment claiming "X is installed via a separate step, see <file>" is a claim, not a fact — before trusting it, open the referenced file and confirm the step actually exists; an aspirational comment that describes work which was never done is indistinguishable from a true one by reading the comment alone. (g) When multiple services in a repo adopt the same sibling-package convention (console, orchestrator, ...), verify EACH service's actual Dockerfile independently — "service X already does this correctly" is not evidence that service Y (which merely intends to follow the same convention) actually does. (h) When `az extension add` fails with a pip/build error in a Windows sandbox, check whether Log Analytics (`az monitor log-analytics query` via the `log-analytics` extension, if already installed) can answer the same question first — it's typically faster to get working and gives real query filtering (KQL) rather than a raw log stream requiring separate parsing, and avoids debugging az's own bundled-Python packaging problems entirely, which are orthogonal to the actual production incident being investigated.

RECURRENCE #4 (2026-08-02, same day, live — caj-mcp-smoke, immediately after mcp-web/mcp-buffer/mcp-canva's first-ever successful image build, PR #50): a THIRD Docker-built adoption site with the identical gap, this time affecting 3 services at once because they share one library. `mcp_common/telemetry.py`'s `open_tool_call_span()` — called unconditionally on every POST /mcp request by `mcp_common/protocol.py`'s `MCPServer.build_router` (line ~124, not wrapped in the caller's own try/except) — does an unguarded `from telemetry_lib import start_span` as its first line, exactly like (7)'s gatekeeper/publisher bug. None of mcp-web/mcp-buffer/mcp-canva/Dockerfile.smoke ever staged or installed services/telemetry-lib. This one was caught BEFORE it hit live production traffic, at caj-mcp-smoke's own conformance test (which HTTP-calls the real deployed servers, per `conftest.py`'s `mcp_client_factory` reading a `*_BASE_URL` env var and building a real `httpx.Client` against it) — but only surfaced as a downstream symptom: pytest died at COLLECTION first, on a completely separate, unrelated gap (`tests/test_telemetry_wiring.py` imports `opentelemetry.sdk.trace.TracerProvider` for its own in-memory-exporter test fixture, and `opentelemetry-sdk` was never in `mcp/requirements-test.txt` — only `opentelemetry-api`, transitively via `mcp_common`'s own pyproject.toml dependency, was ever installed). Fixing the collection-time `opentelemetry.sdk` gap ALONE would have let the `mcp_conformance`-marked test actually run and immediately hit the telemetry_lib gap as a live 500 from the real servers — two independently-missing dependencies stacked in the same file, the same "layer beneath the first fix" shape as (6).

catch_next_time (additional): (i) When a fix surfaces via a collection-time ImportError, do not stop at making collection succeed — trace what the test(s) that collection was blocking actually DO at runtime, and check whether they exercise a second, different unverified dependency (per (b), classify EVERY sibling-package call site the test path touches, not just the one whose absence happens to crash first / loudest). (j) A shared library used by N services (here: mcp_common by mcp-web/mcp-buffer/mcp-canva) multiplies a single missing-dependency bug by N — when auditing one service's adoption of a shared library, check every OTHER service that imports the same shared library too, in the same pass, not as a separate follow-up. (k) `mcp/`'s test suite (`mcp/tests/test_telemetry_wiring.py` and friends) has no `pull_request`-triggered CI job at all in this repo (confirmed: `ci.yml` has zero `mcp`-named jobs) — this entire telemetry-wiring path was unexercised by CI through 3 merged PRs (the original adoption, PR #47, PR #49) and was only ever going to be caught live, which is exactly what happened. Adding an `mcp-tests` CI job (mirroring `console-tests`'/`orchestrator-test`'s `pip install -e services/telemetry-lib -e mcp/common ...` pattern) would catch this class before merge; noted here as a gap, not fixed in the same PR as the live incident (kept that PR minimal per this repo's established pattern of one fix per PR).
