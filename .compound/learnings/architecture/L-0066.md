statement: Code that passes every local/CI-executed test suite can still be non-deployable, because local tests exercise application logic, not the actual deployment/install-packaging mechanism (hand-maintained BUNDLE_MANIFEST.txt/Bicep loadTextContent bundles, a Bicep-hardcoded single-file migration loader, Bicep env-var wiring for a container's outbound client URLs, or a service's requirements.txt vs. its pyproject.toml) — the identical bug class recurred at least 9 times across one build and its PR-review cycle.

evidence: (1) functions/ dir staging fixed during rebase reconciliation citing L-0062/L-0063 precedent. (2) risk-security RS-01 (blocker): services/gatekeeper and services/publisher's BUNDLE_MANIFEST.txt never got 5 new files added -> real deployed image ImportError-crash-loops; scripts/verify_governance_bundle_reconstruction.py only runs on workflow_dispatch/workflow_run, never on pull_request. (3) migration lens F-1 (blocker): infra/main.bicep's orchestratorMigrationSql loadTextContent loads only 0001_orchestrator_init.sql, never 0002/0003, even though the new code depends on both at runtime; CI tests pass only because conftest.py applies migrations/*.sql via a glob that masks the production wiring gap. (4) agent-native F1 + performance PERF-04 (blocker): all 4 of orchestrator's client base-URL resolvers fall through to an uncached `az containerapp show` subprocess shell-out with zero Bicep env-var wiring, and the image never installs azure-cli, so resolution silently returns None in the real container. (5) POST-MERGE, PR review round: mechanical telemetry adoption across ~10 services added `opentelemetry-api` to every service's pyproject.toml, but 5 of those services (gatekeeper, publisher, registry, model-gateway, vault) install their REAL runtime dependencies from a separate requirements.txt — the file their Dockerfile/CI job actually installs from — which never got the same addition. Two instances were caught by CI (verify-governance-bundle, registry); model-gateway and vault's identical gap was NOT caught by any PR check (no pull_request-triggered test job exists for those services at all) and was only found by proactively auditing every telemetry-adopting service's requirements.txt after the first two failures, not by a systemic check. console and 3 mcp-* servers were correctly unaffected (they install via pyproject.toml editable-install / a shared mcp_common base that already declared it) — proving the fix must be scoped to "whichever manifest this specific service's real install path reads," not applied uniformly. (6) SAME PR REVIEW ROUND, a SECOND layer beneath (5): fixing `opentelemetry-api` in registry's requirements.txt only got the CI job one step further before hitting `ModuleNotFoundError: No module named 'telemetry_lib'` — registry, model-gateway, and vault's telemetry_wiring.py import the shared `telemetry_lib` wrapper package (services/telemetry-lib) directly, not just raw opentelemetry (unlike gatekeeper/publisher, which use raw opentelemetry and were genuinely fully fixed by (5) alone). telemetry_lib is a local sibling package published to no index, so no version of requirements.txt can ever express it — it needs its own explicit `pip install -e services/telemetry-lib`-shaped step, and for model-gateway/vault (narrow Docker build contexts that can't reach a sibling services/ directory) an entire staging step mirroring the existing contracts-staging pattern. A single fix for "this package is missing" can be incomplete if the same failure has more than one distinct cause layered underneath it — the CI re-run after the first fix is what surfaced the second.

catch_next_time: Add a pull_request-triggered CI check (not just workflow_dispatch/workflow_run) that, for every service deployed via a hand-maintained bundle/manifest OR a requirements.txt distinct from pyproject.toml, diffs the set of packages/files the service's own code imports/requires against what its REAL install-time manifest declares — BUNDLE_MANIFEST.txt / Bicep loadTextContent var list / Bicep-hardcoded migration file list / requirements.txt vs. pyproject.toml dependency lists — and fails on any mismatch. When a change touches N services mechanically (e.g. "add telemetry to every Wave-1 service"), enumerate up front which of the N install from pyproject.toml (via `pip install -e .`, safe) vs. a separate requirements.txt (needs its own, separately-verified edit) — do not assume all N services share one dependency-declaration convention, AND check whether the shared code being adopted itself has its own non-PyPI sibling-package dependency (like telemetry_lib) that needs a second, structurally different fix (an explicit editable-install step, possibly a build-context staging step) beyond just adding one missing PyPI package name. After fixing a ModuleNotFoundError, re-run the exact failing check before declaring it fixed — don't assume the first missing-module error is the only one on that path. This generalizes L-0062's CONTRACTS_DIR sweep-test from "files a call site reads" to "whatever a service's OWN real install mechanism supplies" — make it a standing plan-review checklist item, not something re-discovered per-service by CI failures or a manual audit.
