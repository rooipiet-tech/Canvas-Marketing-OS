statement: A pattern-based security/compliance control (here: model-gateway's `full-name-like` redaction regex, `\b[A-Z][a-z]+\s+[A-Z][a-z]+\b` — any two consecutive Title-Case words) that scans EVERY message role including `system` will false-positive on ordinary developer-authored prompt text, because business/product/place names in natural English routinely match a "two capitalized words" shape. When the false-positive rate is high enough, it doesn't just annoy one caller — it can make an entire code path structurally non-functional in every context (proof-circuit smoke AND real production), and the fact that a symptom reproduces identically across N independently-verified, unrelated fixes to an EARLIER stage is itself the signal that the bug has moved to a later, different stage, not that stage N's fixes were wrong.

evidence: Escalations 9-12 (deploy-loop-e2e-smoke, 2026-08-01 through -03) each found and fixed a genuinely different, real bug in `get_or_create_campaign()`'s Vault taxonomy call (env vars, missing field, wrong UUID shape, wrong UUID value) — see [[L-0065]] and [[L-0075]]. The top-line symptom ("1/7 stages terminal") never moved across all four fixes. Escalation 13 confirmed, by reading the poll script's own `TERMINAL_STATES = {"completed", "failed"}` and the real per-run logs, that "1/7" means "exactly one of 7 stages has ANY resolved status, success or failure" — not "stage 1 keeps failing." After PR #58 (escalation 12's fix) landed, run #19's logs showed ZERO campaign/Vault-taxonomy errors — campaign creation now succeeds cleanly — and a completely new, different blocker: `model-gateway` returning `REDACTION_BLOCKED` for a `full-name-like` match, on EVERY call any of functions 09/42/02 make, because their own static system-prompt text (`prompt.md`) and `fetch_sources.yaml`'s `topic` string contain ordinary Title-Case product/place names ("Market Intelligence", "Brand Steward", "South African", "Microsoft Fabric") that trip the same two-consecutive-capitalized-word pattern meant to catch person/client names. `contracts/model-gateway/redaction-rules.yaml` (the pattern itself) is one of this repo's 9 hash-guarded frozen contract files; `redaction.py` (the scanner, not frozen) explicitly documented scanning every role including `system` as deliberate. This is a genuine security-policy question, not a code bug — flagged to the user rather than resolved unilaterally, per this session's "escalate contract conflicts and genuine rulings" boundary. Ruling: exempt `system`-role content from the scan, since `system` is the universal LLM-API convention for developer/operator instructions (never end-user/ingested data), confirmed for every current caller by reading orchestrator's own `gateway_client.py` (`system_prompt` is always `_read_prompt()`'s static file output).

catch_next_time: (a) When a design-driven "N/7"-style summary metric is central to diagnosing an escalation, read its EXACT computation (not just its name) early — "terminal" can mean "resolved" (success-or-failure) rather than "failed," and conflating the two wastes rounds chasing the wrong stage. (b) A symptom that reproduces byte-identically across multiple independently-verified real fixes to the SAME function is not evidence those fixes were wrong or that there's a 5th bug in that same function — it can mean the bug has already moved past that function into a DIFFERENT one, and the unchanged top-line summary is simply not granular enough to show it; re-derive what the summary metric actually measures before assuming you're still debugging the same code path. (c) A broad regex-based PII/security pattern applied uniformly across ALL message roles will false-positive on ordinary business English at a rate proportional to how much natural-language content (product names, section headers, demonyms) flows through that role — before shipping such a pattern, consider whether developer-authored/static content (system prompts, code comments, templates) needs a different scan boundary than dynamic/ingested content, since the two have structurally different PII risk profiles. (d) A frozen contract file's own stated scan-scope intent can be narrowed at the IMPLEMENTATION layer (not the frozen file itself) when doing so doesn't weaken the actual protection the contract exists to provide — but this determination is a genuine ruling (security-relevant, cross-cutting), not something to decide unilaterally; presenting concrete options with tradeoffs (exempt a role vs. rewrite content vs. loosen the frozen pattern) and getting an explicit decision is the right move, matching how this session already handled the escalation-7 fixture-mode dual-mode ruling. (e) When exempting a role/scope from a security scanner, verify the exemption's safety by reading every CURRENT caller's actual construction of that role's content (not just assuming the API convention holds) — and add tests proving the exemption is scoped narrowly: the same content under the exempted role passes, the identical content under a non-exempted role still blocks, and a blocking message elsewhere in the same request still blocks even when an exempted message is also present.
