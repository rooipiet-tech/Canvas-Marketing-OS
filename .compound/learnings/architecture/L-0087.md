statement: Two related pitfalls hit fixing TD-07 (worker.py's admitted
"a handler that partially wrote to Vault before failing is not guaranteed
idempotent on retry"). (1) An idempotency mechanism that keys off "a fresh
client instance per call" (an ordinal counter living on VaultClientExt,
reset in `__init__`) is correct in production — every dispatch.py handler
really does open a brand-new `with build_vault_client() as vault:` per
invocation — but is invisibly fragile: a test double that (correctly)
shares ONE instance across a handler's two retry attempts, to model Vault
as a persistent remote service rather than re-fake it from scratch, breaks
the counter silently (it keeps incrementing across attempts instead of
restarting), producing a DIFFERENT idempotency key on the retry and
defeating the whole dedup. (2) Fixing "duplicate agent_run row" alone does
not fix "duplicate model charge" — that half of TD-07 required tracing
into a SEPARATE already-resolved item (TD-06, model-gateway's task_ref
idempotency cache) and discovering the orchestrator's own gateway client
never actually sent `task_ref` in its payload, so a fully-built,
fully-tested server-side cache was dormant for 100% of real orchestrator
traffic.

evidence: `VaultClientExt.create_agent_run_idempotent`'s ordinal counter
(`self._agent_run_ordinal`, keyed by task_id) is reset in `__init__` only
at first; `tests/test_dispatch_retry.py`'s new retry test uses
`patch_dispatch_clients(monkeypatch, shared_vault=vault,
shared_gateway=gateway)` — deliberately ONE FakeVaultClient instance
across both the original attempt and the retry, matching how the existing
`shared_vault` convention already models "a real Vault deployment
persists data between handler calls." With only an `__init__` reset, this
test failed: `len(vault._agent_runs) == 2` instead of 1, because the
SAME instance's ordinal dict kept climbing (1, then 2) instead of
restarting at 1 for the retry's own first call. Fixed by moving/adding
the reset to `__enter__` instead (`with build_vault_client() as vault:`
calls `__enter__` on every invocation in production, and the test's
monkeypatched factory calls it too, even when it returns the same
underlying object) — the same fix landed in `VaultClientExt.__enter__`
and both `FakeVaultClient.__enter__` copies (`tests/fakes.py` and
`tests/test_dispatch_qa_retry_loop.py`'s private copy).

Separately: `services/model-gateway/caching.py`'s `get_or_compute` has
always contained `if not task_ref: return await compute(), False` — no
task_ref, no caching, ever — and `completion.py` reads `payload.get(
"task_ref")` straight off the wire. But
`orchestrator/clients/gateway_client.py::OrchestratorGatewayClient.complete`
never had a `task_ref` parameter at all, in any call site, so every real
completion the orchestrator ever issued computed fresh regardless of
retries — TD-06's fix ("Resolved... a retried task never double-spends")
was true of model-gateway in isolation but never actually engaged for
production traffic. Wiring `task_ref` through `_complete_and_meter`
(defaulting to the now-retry-stable `agent_run_id`) is what makes the
already-shipped cache do anything.

catch_next_time: (1) When an idempotency/ordinal/counter mechanism's
correctness depends on "a fresh object per logical unit of work," write
that assumption into a test that deliberately violates object-freshness
(reuses one instance across the retry) rather than only testing with
fresh objects each time — a fresh-instance test can't distinguish "reset
in `__init__`" from "reset in `__enter__`," and only the latter is robust
to a caller (production OR a test double modeling a persistent backend)
that reuses the instance. Prefer resetting per-`with`-block
(`__enter__`) over per-construction (`__init__`) for exactly this reason.
(2) Before declaring a "prevent duplicate charge on retry" fix complete,
trace the FULL path from the retried call site to the actual
charge-preventing mechanism and confirm every field that mechanism keys
on is actually populated on the wire — a previously-"Resolved" TD entry
for the mechanism itself is not proof the caller in front of it was ever
wired to use it; grep the caller's own payload-construction code for the
literal field name the cache/dedup layer reads.
