statement: A shared connection-pooling proxy (PgBouncer, or any similar L4 intermediary) placed in front of a database that OTHER services already smoke-test through deploy-infra.yml's own `deploy` job creates a bootstrap-ordering hazard beyond the well-established L-0048/L-0060 contract: L-0048/L-0060 guarantee the NEW app's own placeholder image doesn't break ITS OWN smoke test, but say nothing about every OTHER app whose smoke test now transitively depends on the new proxy being fully functional. Those other apps' smoke tests run inside the SAME deploy-infra.yml job that first creates the proxy (via Bicep) — there is no hook point for a separate image-deploy workflow to run in between "Bicep creates the proxy on the bootstrap placeholder" and "deploy-infra's own job immediately exercises DB connectivity through it" within a single workflow run. On a maiden deploy this is not preventable within deploy-infra.yml alone; it has to be absorbed by the deploy-PIPELINE's stage ordering (the proxy's own image-deploy workflow must run as an early, separate pipeline stage before deploy-infra is expected to fully succeed) and accepted as a second-pipeline-run bootstrap, the same way ca-orchestrator's own smoke test already requires a second run after orchestrator-image.yml sets its real image.

evidence: Building TD-12's fix (docs/architecture/09-technical-debt.md), the first draft of ca-pgbouncer followed the L-0048/L-0060 contract in full (placeholder default, deploy-infra preflight preserves live image, no `registries[]`, a separate `deploy-pgbouncer.yml`) — correct for ca-pgbouncer's OWN hypothetical smoke test, but ca-pgbouncer has no smoke test of its own inside deploy-infra.yml at all. What it actually gates is the vault secret-writer job's Key Vault write, the governance smoke-test job, and the orchestrator migration/smoke-test job — all of which ALREADY run inside deploy-infra.yml's `deploy-gated`/`deploy-autopass` steps, all of which would silently try to connect through a hello-world placeholder container that doesn't speak the Postgres wire protocol at all, on the very first deploy. Caught before landing by tracing where governanceDatabaseUrl/gateway's postgresFqdn/vault's secret-writer DATABASE_URL actually get consumed downstream, not by testing a live deploy (no live Azure environment reachable from this session).

catch_next_time: When a plan or build inserts a new shared intermediary (proxy, cache, gateway) between an existing resource and OTHER resources that already have live smoke/verification steps depending on that existing resource, trace every downstream consumer's OWN verification step — not just the new intermediary's — before deciding image-bootstrap sequencing is solved. If any downstream verification step runs inside the SAME workflow job that first provisions the intermediary (rather than a separably-orderable later stage), the intermediary's real-image deploy must be pulled forward into its own EARLY pipeline stage (before that shared job, not chained off its completion) — and the maiden-deploy exception (first full pipeline run partially fails, a second succeeds) must be stated in the pipeline's own header comment, matching the existing precedent for ca-orchestrator, rather than assumed to be a solved problem because the 4-part L-0048/L-0060 checklist was followed.
