statement: A hostname written into a frozen contract (e.g. an OpenAPI
`servers:` URL) or a CI workflow's env var describes an INTENDED address,
not a guarantee that DNS/custom-domain infra actually backs it. If nothing
in Bicep ever creates a matching private DNS zone or binds a custom domain
to the resource, the hostname resolves to nothing — and a CI step that
hardcodes it instead of reading the resource's actual assigned FQDN will
fail with a connection-level error (curl `HTTP_STATUS=000`, no response
body at all) that looks superficially like a network/firewall problem but
is really "this hostname was never real."

evidence: `deploy-gateway.yml`'s in-VNet smoke test hardcoded
`GATEWAY_URL: https://model-gateway.internal.cmos.dev` — the exact URL
documented as the gateway's canonical server in
`contracts/model-gateway/openapi.yaml`. Live diagnosis ruled out the app
(`runningStatus: Running`, latest revision `Healthy`, clean startup logs, no
crash-looping) and the ingress config (internal, `targetPort` 8000 matching
the app's own Uvicorn bind) before checking DNS: `az network private-dns
zone list -g cmos-dev` showed zones only for blob/postgres/vaultcore private
endpoints — nothing for `cmos.dev` or `internal.cmos.dev` — and
`properties.configuration.ingress.customDomains` on the Container App was
`null`. The app's real, live FQDN was
`ca-model-gateway.internal.<env-unique-id>.<region>.azurecontainerapps.io`,
resolved dynamically the same way `L-0021` already fixed the ACR
login-server lookup.

catch_next_time: A hostname appearing in a frozen contract's documented
`servers:`/base-URL field is a DESIGN intent, not live infrastructure —
before a CI step calls it, confirm something in Bicep actually provisions a
matching private DNS zone (VNet-linked) or custom domain binding. If
nothing does, the CI step must resolve the resource's real assigned FQDN
live (`az containerapp show --query
properties.configuration.ingress.fqdn`) rather than hardcoding the
documented aspirational one — same principle as L-0021, now confirmed to
apply to DNS/hostnames as well as registry names. `HTTP_STATUS=000` from
curl with no response file written is a strong signal to check DNS/
connectivity before anything app-level; add curl's own exit code
(`$?` — 6=DNS failure, 7=refused/unreachable, 28=timeout) to any smoke-test
script from the start, since the bare HTTP status code alone cannot
distinguish these.
