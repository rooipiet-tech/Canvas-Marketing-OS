statement: A Container App's Bicep must keep declaring `registries[]` on every
redeploy once a private-registry image is live. The deploy is an ARM PUT, so
omitting `registries[]` strips the registry configuration; the revision it
creates cannot pull its image, sits in Activating with an empty log, and never
becomes Ready. In Single revision mode the previous Ready revision is then
never deactivated, and with it still serving, anything that rotates per deploy
(here the Postgres admin password, baked into PgBouncer's userlist at container
start) is answered by the STALE replica. L-0049's "drop registries[]" is a
rule for the maiden deploy only; derive the block from the image
(`startsWith(image, registryServer)`) so the placeholder bootstrap stays clean.
Supplements L-0071 and refines L-0085.

evidence: deploy-pipeline run 90: all 8 asyncpg logins through ca-pgbouncer
failed with "SASL authentication failed" while all 8 direct to Postgres
succeeded (same password, same runner), and the old replica's own console log
(ca-pgbouncer--0000003, created by a manual deploy-pgbouncer run) showed
"cmosadmin ... password authentication failed" at the exact millisecond of each
probe attempt. The revision this deploy created (ca-pgbouncer--ryq547ijkyfpt2)
had 100% traffic on paper but was Activating with healthState None for 9
minutes and no log; run 89's revision looked the same. The stored and live
passwords matched (both 64 chars), which is what ruled out a mismatch and
pointed at WHICH replica answered. Every earlier "fix" (manual
deploy-pgbouncer dispatch, then re-run) was undone by the next Bicep deploy.

catch_next_time: When a database login fails although the credentials provably
match, find out which replica answered before touching credentials: list EVERY
revision's state/traffic and read each active revision's own console log, and
correlate log timestamps with the probe's attempts. A revision that is
Activating for minutes with no log never started its container; read the
system log for the pull error. After any Bicep deploy of a CI-built-image app,
wait for the latest revision to be Ready and fail loudly with ground truth if it
is not (deploy-infra.yml now does this for ca-pgbouncer), and deactivate stale
active revisions. NOT yet applied to ca-publisher, ca-gatekeeper,
ca-gatekeeper-approval, ca-console or mcp-*: they omit `registries[]` too, so a
full deploy leaves each without registry config until its own deploy workflow
re-sets it. Guarded for ca-pgbouncer by
services/orchestrator/tests/test_pgbouncer_pulls_its_image_and_is_waited_on.py.
