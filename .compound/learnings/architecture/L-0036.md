statement: L-0021's fix ("resolve an Azure resource from a consuming
resource's own authoritative live binding, not an ambient list") has a
blind spot when the consuming resource itself is the thing being migrated
onto the new shared resource: its live binding still legitimately points
at the OLD resource until a separate IaC deploy actually repoints it, so
reading it back at push/build time just re-targets the old resource and
never migrates anything — the fix looks applied but is a no-op. When the
thing being resolved is itself mid-migration, resolve from the shared
resource's OWN IaC deployment record (e.g. a Bicep module's `name:` via
`az deployment group show -g <rg> -n <module-name> --query
properties.outputs.<x>.value`) instead of any single consumer's binding —
this is authoritative regardless of which consumers have migrated yet, and
avoids inventing a new coupling to some OTHER already-migrated consumer
just to borrow a working binding.

evidence: `vault-image.yml` originally resolved its push target with `az
acr list -g cmos-dev --query "[0].name"` (the same order-dependent
anti-pattern L-0021 fixed for `deploy-gateway.yml`). The naive L-0021-style
fix would read `ca-vault`'s own `properties.configuration.registries[0]
.server` — but `ca-vault` was provisioned against the orphaned
pre-convention `acrcmosdev...` registry (a session-local copy of
`container-registry.bicep` since dropped in favor of main's canonical
module on rebase), and that live binding does not change until
`deploy-infra.yml` actually redeploys `infra/modules/vault/main.bicep`
with its `acrLoginServer` param repointed at the canonical
`containerRegistry` module. Reading `ca-vault`'s binding at push time,
before that redeploy, would have kept pushing to the old registry forever
— an apparently-fixed workflow that never actually migrates anything, with
no error to signal it. Fixed by resolving from the `container-registry`
module's own deployment (`az deployment group show -g cmos-dev -n
container-registry --query properties.outputs.loginServer.value`) — stable
regardless of which of its consumers (gateway, vault, or a future service)
have already been repointed at it.

catch_next_time: When applying L-0021's "resolve from an authoritative
binding" fix to a resource resolution step, ask: is the consumer I'm about
to read the binding from itself the thing currently being migrated onto
the target? If yes, its current binding is stale by construction and
reading it is a no-op disguised as a fix — resolve one level up, from the
shared target resource's own IaC deployment record, instead. Plan-reviewer
checklist item for any ACR/shared-resource migration: verify the
resolution step's source can never be the same resource whose binding is
being changed by the migration itself.
