statement: [[L-0049]]'s fix (drop `registries[]` from Bicep, attach the ACR-pull identity via CLI post-create) is necessary but NOT sufficient for a `Microsoft.App/jobs` resource — a one-shot Container Apps Job apparently cannot have ANY user-assigned identity newly attached via `identity.userAssignedIdentities` in its own initial create call at all, independent of whether `registries[].identity` also references it. `Microsoft.App/jobs` is stricter than `Microsoft.App/containerApps` for the same underlying platform limitation (microsoft/azure-container-apps#1467). Extend the fix for any new one-shot Job that needs a private-registry pull identity: the Bicep template declares NO `identity` block whatsoever (not even attaching the identity alone, unlike an app where attaching-without-registries[] is fine) — the job is created with zero managed identity. A separate, gated CI step then runs the full 2-command Microsoft workaround, in order: `az containerapp job identity assign --user-assigned <id>` (attach), immediately followed by `az containerapp job registry set --server <acr> --identity <id>` (configure ACR pull auth using the identity just attached). Both are idempotent and safe to repeat every deploy.

evidence: mcp-smoke-job.bicep's round-1 fix (this repo, same day) removed `registries[]` only — matching container-app.bicep's fix, which worked cleanly for all 3 mcp-* Container Apps in the same deploy. caj-mcp-smoke still failed provisioning with `IdentityDoesNotExist` on the very next deploy-infra run, with the identical `identity.userAssignedIdentities` block (reusing id-mcp-web, already fully provisioned and AcrPull-granted minutes earlier — ruling out a propagation-timing race, same as [[L-0049]]'s own console evidence) still present in the job's initial create. Removing that block entirely and moving identity attachment to a CI-owned `job identity assign` step (run before `job registry set`) was the fix that actually worked. Note: ca-orchestrator's own smoke-test-job module (infra/modules/orchestrator/smoke-test-job.bicep) STILL has a fresh identity + `registries[]` combination in its initial create and is reported to have deployed clean — this is not counter-evidence that jobs are unaffected in general, since that module was authored and last verified before this discovery; it should be re-tested (or preemptively fixed) rather than treated as proof jobs are safe with this combination.

catch_next_time: When a plan or build adds a new `Microsoft.App/jobs` resource that needs a private-registry pull identity (not just a `Microsoft.App/containerApps` resource — see [[L-0049]]/[[L-0060]] for the app-level version of this contract), require: (1) no `identity` property at all in the job's Bicep resource declaration; (2) the deploy workflow's gated step runs `az containerapp job identity assign --user-assigned <identity-resource-id>` BEFORE `az containerapp job registry set --server <acr> --identity <identity-resource-id>` — two distinct CLI calls, not one; (3) treat any existing job template that skips straight to `registries[]`-removal-only (the app-level fix) as unverified for jobs specifically until it has actually been redeployed clean after this fix — do not assume an app-level fix transfers to a job of the same identity/registry shape without re-testing.
