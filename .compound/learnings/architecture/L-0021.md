statement: When a CI workflow resolves an Azure resource by an unfiltered
"list and take index 0" query (e.g. `az acr list -g <rg> --query "[0].x"`)
instead of a specific name or another resource's authoritative binding, it
silently picks the WRONG resource the moment a second resource of that type
exists in the same resource group — with no error, because the query
succeeds and returns a plausible-looking value. This is different from (and
compounds) L-0017's lesson: L-0017 was about Bicep ordering needing a real
output reference instead of a computed string; this is about a CI *shell*
script needing the same discipline — resolve against the consuming
resource's own live, already-correct binding, never against an ambient list
that assumes uniqueness.

evidence: `deploy-gateway.yml`'s "Resolve the shared ACR login server" step
used `az acr list -g cmos-dev --query "[0].loginServer" -o tsv`. Live `az acr
list` showed TWO registries in `cmos-dev`: the Bicep-managed canonical one
(`acrcmosshared<uniqueString>`, the only one `gateway.bicep` grants `AcrPull`
to and binds into `ca-model-gateway`'s `registries[]`) and an orphaned legacy
one (`acrcmosdev<uniqueString>`, not declared anywhere in `infra/`, already
holding stale `model-gateway`/`vault` repos from before the "shared ACR"
naming convention was adopted). The `[0]` index resolved to the orphan.
`docker push` to it succeeded (no credential problem — ACR push only needs
the pusher's own `az acr login`, unrelated to the app's pull identity), so
the build-and-push job showed green; the subsequent `az containerapp update
--image <orphan-registry>/...` then failed with `UNAUTHORIZED` on
`GET .../v2/model-gateway/manifests/... scope=repository:model-gateway:pull`,
because `ca-model-gateway`'s identity had `AcrPull` and a `registries[]`
credential configured only for the OTHER (canonical) registry — the orphan
had no binding for the app at all. A public placeholder image had masked
this for every prior deploy, since it needs no registry credential.

catch_next_time: Whenever a CI step resolves "the" instance of an Azure
resource type via `az <service> list --query "[0].x"` (or equivalent), ask:
could this resource group ever hold more than one? If any other resource
already has an authoritative reference to the correct one (a role
assignment, a `registries[]`/`secrets[]` binding, an IaC module output),
resolve from THAT reference instead of an ambient list — it can't drift out
of sync with what actually works, and it fails loudly (empty result) rather
than silently picking a plausible-but-wrong sibling. Plan-reviewer checklist
item for any new CI step doing `list --query "[0]"` against a resource type
that isn't provably singleton-per-RG: "is there a consuming resource whose
own live config already points at the right one?"
