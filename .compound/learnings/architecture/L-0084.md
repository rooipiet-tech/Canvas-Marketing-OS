statement: A caller module that constructs its own `httpx.Client` per call
(rather than sharing one built at process-startup from validated config)
can carry a real network dependency with NO Bicep wiring for its base URL
at all, and this ships silently — every unit test mocks `http_client`
directly (respx/`httpx.MockTransport`), so the "no live base URL configured"
path never gets exercised, and the app's own fail-closed exception
(`VaultLookupError`/`VaultWriteError`) looks, from a passing test suite, like
correct behaviour rather than a permanently-tripped production circuit
breaker.

evidence: Auditing every real Vault caller while fixing TD-03 (Vault API
authentication) found that `infra/modules/governance/publisher-app.bicep`
had no `vaultApiUrl`/`VAULT_API_URL` param or env var at all — confirmed
by reading the file in full and cross-checking every `az containerapp
update --set-env-vars`/`--set-env-vars` step across
deploy-infra.yml/deploy-governance.yml for an out-of-band grant that also
didn't exist. `app/vault_lookup.vault_base_url()` and
`app/vault_adapter.write_gate_decision()` both read
`os.environ.get("VAULT_API_URL")` and fail closed
(`VaultLookupError`/`VaultWriteError`, "VAULT_API_URL is not configured")
when it's unset — meaning TD-02's own fix ("for every accepted publish,
append a real `gate_decisions` row") has likely been failing on every real
publish in the live `cae-cmos-dev` deploy, invisibly, because
`tests/test_vault_adapter.py`/`tests/test_vault_lookup.py` inject
`http_client` directly and never exercise the "resolve from env, unset"
branch end-to-end against the real Bicep template.

catch_next_time: When a service reaches another service ONLY via a
`base_url`/token resolved from `os.environ` (never a shared, app-startup-
validated client), a review of that mechanism must independently verify
the CONSUMING service's own Bicep/container-app definition actually
declares the env var — not just that the reading code has a sensible
fail-closed default. Grep the producing service's client module for every
`os.environ.get(...)` name, then grep every consumer's `*.bicep` file (and
any `--set-env-vars` escape hatch in deploy workflows) for that same
literal name; a hit in the code with no hit in Bicep is exactly this bug
class, and it will not show up in a green test suite because tests
correctly bypass real env resolution via an injectable client.
