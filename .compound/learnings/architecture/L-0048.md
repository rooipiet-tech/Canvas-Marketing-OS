statement: A new Container App whose real image comes from a separate CI/CD pipeline (not baked into IaC) needs the same three-part bootstrap contract every prior instance of this class in this repo eventually converged on: (1) the Bicep image param defaults to a public placeholder, never a self-computed `.../<service>:latest`, (2) the deploy workflow's preflight resolves it to the app's CURRENT live image once one exists, never regressing a running app back to placeholder, and (3) a SEPARATE gated workflow is the only thing that ever calls `az containerapp update --image`, pinned to a commit SHA — and the image-build workflow must resolve its target registry from an authoritative deployment/binding record, never an ambient `az acr list [0]` pick, or the whole contract is moot because the image lands in the wrong place.

evidence: On 2026-07-31, ca-orchestrator's maiden deploy-infra run failed with `MANIFEST_UNKNOWN` for `orchestrator:latest` — not because the image workflow never ran (it had, successfully, minutes after merge), but because it resolved the ACR via `az acr list -g cmos-dev --query "[0].name"` (the exact L-0021 anti-pattern) and pushed to the orphaned pre-convention `acrcmosdev...` registry while `infra/main.bicep` unconditionally computed `${containerRegistry.outputs.loginServer}/orchestrator:latest` against the canonical `acrcmosshared...` one, which had zero orchestrator tags in it. This is the third independent instance of this exact bootstrap gap in this repo: L-0018 (model-gateway, original discovery — placeholder param + preserve-live preflight + separate deploy-gateway.yml), the same-day deploy-console.yml maiden-deploy race (concurrency-group + bounded-existence-poll half of the contract), and vault-image.yml already carrying the ACR-resolution half of the fix (`az deployment group show -n container-registry`) without the placeholder-bootstrap half (vault's main.bicep still hardcodes `vaultImageTag = 'latest'` unconditionally — works today only because vault's canonical-registry tag has existed since its first successful deploy, a latent version of the same gap, not yet triggered).

catch_next_time: When a plan or build adds a new Container App fed by CI-built images, require all three parts together at plan-review time, not as a follow-up fix: (1) the Bicep image param defaults to `mcr.microsoft.com/azuredocs/containerapps-helloworld:latest`, (2) deploy-infra.yml gets a "preserve live image, bootstrap with placeholder" preflight step (checking `latestReadyRevisionName` + current image) threaded into every `az deployment group create`/`what-if` call for that param, and (3) the image-build workflow resolves its registry via `az deployment group show -g <rg> -n container-registry --query properties.outputs.loginServer.value` (never `az acr list [0]`) and — in a job gated behind the same `environment: cmos-dev` approval and joined to the shared `cmos-dev-deploy` concurrency group — is the sole caller of `az containerapp update --image <registry>/<service>:<commit-sha>`. Treat any new `:latest`-tagged image reference computed inside Bicep as a standing defect (see [[L-0021]], [[L-0036]]), not a style nit.
