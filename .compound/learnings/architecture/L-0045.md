statement: For any build whose goal describes a service that "consumes", "processes", or "dispatches from" a live queue/event source, a plan that only implements an invokable decompose/transform function (with no long-lived consumer loop wired into the deployed process's startup) is architecturally incomplete even if every literal spec-verify command would pass — this is exactly the class of gap a plan-reviewer pass exists to catch.

evidence: On the s3-orchestrator run, plan v1's main.py exposed only GET /health and GET /status with nothing in the deployed app ever consuming the Service Bus event/task queues — a real heartbeat fired by a Logic App would have sat unread forever. Plan v1's own smoke test called decompose() locally and compared its output to itself, proving nothing about the live app's actual behavior. Every one of the 36 spec.json verify commands would still have passed against this design (none literally required a live consume-loop). The plan-reviewer's "revise" verdict caught this and forced a re-plan (v2) adding a long-lived asyncio worker loop spawned from FastAPI's lifespan, plus a redesigned smoke test that polls the live app's actual output instead of self-comparing.

catch_next_time: When a build's goal says a service "consumes", "processes", or "dispatches from" a queue/event source, the plan-reviewer must explicitly check the plan for a long-running consumption/dispatch loop wired into the deployed process's actual startup path — reject and require a re-plan if the only evidence of "consumption" is a locally-invoked function tested by comparing its own output to itself, rather than a live queue-polling loop that a smoke test can observe consuming real messages.
