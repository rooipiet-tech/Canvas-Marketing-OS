statement: `deploy-infra` rolls ca-vault onto its new image **before** it runs the Vault schema migration, so a change that adds a column AND the code writing it goes live against a database that does not yet have that column for roughly 30-45 seconds. The ordering is not an oversight and cannot simply be reversed — it is forced by the rotated Postgres password and the VNet-only Key Vault. Until that design changes, adding a Vault column is a two-deploy expand/contract operation, enforced by `scripts/check_schema_code_ordering.py`.

evidence: `.github/workflows/deploy-infra.yml` runs `az deployment group create` (line ~589) and only then `az containerapp job start -n caj-vault-migrate` (line ~605). `infra/main.bicep` declares `param vaultDeployToken string = utcNow()` and passes it to `infra/modules/vault/container-app.bicep`, which builds `revisionSuffix: 'r${uniqueString(deployToken)}'` — so every deploy creates a new ca-vault revision, and with `activeRevisionsMode: 'Single'` that revision takes 100% of traffic as soon as it is Ready. The ARM deployment that starts the new revision is the same one that must complete before the migration job can run.

Measured on deploy-infra run 33654559138: `az deployment group create` finished at 16:31:47 and caj-vault-migrate had not reported Succeeded until after 16:32:31.

Reproduced locally rather than inferred: a Postgres 16 cluster with the pre-change `contracts/vault-schema/schema.sql` applied, the vault served from the post-change tree (fastapi 0.140.13 / starlette 1.6.0, python 3.12), then `POST /opportunity-cards` — `asyncpg.exceptions.UndefinedColumnError: column "pillar" of relation "opportunity_cards" does not exist`, surfacing as HTTP 500. Applying the four `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` statements against the live pool and re-POSTing then returned a normal 422 FK error, confirming the pool recovers on its own and that stale asyncpg prepared statements are NOT part of this failure.

The real instance was PR #123 (`b2814bd`), which added `pillar`, `so_what`, `source_url` and `confidence` to `contracts/vault-schema/schema.sql` and the matching four `FieldSpec` entries to `services/vault/vault/models.py` in one change.

Why the ordering cannot simply be reversed — all three verified in the tree: (a) `deploy-infra.yml`'s "Generate fresh Postgres admin password" step mints a new password with `openssl rand -hex 32` on **every** run, and it only becomes live when ARM applies it; (b) `caj-vault-migrate`'s own `DATABASE_URL` secret is built from that same `administratorLoginPassword` parameter, and its schema arrives through the template as `main.bicep`'s `loadTextContent` feeding `migrationJob`'s `schemaSql` param, so the job cannot carry the new schema until the template has deployed; (c) Key Vault has public network access Disabled (L-0012), so CI cannot read a previously stored password instead of minting one. Migration-after-rollout is therefore a consequence of the VNet-isolation design.

catch_next_time: Adding a column to the Vault is two deploys, never one: land and deploy the `contracts/vault-schema/schema.sql` change on its own, then land the `services/vault/vault/models.py` change. `scripts/check_schema_code_ordering.py` fails CI on the combined form and passes both halves — it was proved against `b2814bd` itself (fails) and against a reconstructed two-commit split of that same change (both pass).

Do not "fix" this by reversing the deploy steps or by narrowing the window with an extra revision restart; neither addresses (a)-(c) above. The root fix is to stop regenerating the Postgres admin password on every deploy — which additionally removes the forced revision roll on every service, every deploy — and that requires a way for CI to obtain the existing credential with Key Vault closed to the public network. That is a deliberate credential-handling change, not a workflow tweak.

Generalises beyond the Vault: any service in this repo whose schema ships inside `infra/main.bicep` and whose app rolls in the same `az deployment group create` has the same shape. `caj-orchestrator-migrate` runs after `az deployment group create` too.
