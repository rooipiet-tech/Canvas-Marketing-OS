statement: Two distinct pitfalls in the same acquire-check-act-release protocol around a session-scoped Postgres advisory lock (`pg_advisory_lock`), both hit building the same fix. (1) The lock must be released on EVERY return path, including the "nothing to do" path, not just success/failure of the work it guards — returning a pooled connection without unlocking first leaves the lock permanently held by that connection's session, and a future caller who acquires the SAME key on a DIFFERENT pooled connection blocks forever. (2) `pg_advisory_unlock` is session-scoped and NOT transactional — it takes effect the instant it runs, not when the surrounding transaction commits. If a write and the unlock are issued inside the same `with conn:`/transaction block, the unlock can execute (and wake a waiter) BEFORE that block's implicit commit makes the write visible, so the waiter can see a cache miss and redo the work the lock existed to deduplicate. A write that must be visible to whoever the unlock wakes has to be committed in its own block, strictly before the unlock statement is even sent.

evidence: `services/model-gateway/caching.py`'s `PostgresCache` (TD-06's fix for cross-replica task_ref idempotency) acquires `pg_advisory_lock(hashtextextended(task_ref, 0))`, checks the `completions` table, and either (a) returns a cache hit immediately, or (b) becomes the owner, awaits `compute()`, then stores the result and unlocks. (1) The initial implementation unlocked correctly on both the owner-success path (`_store_and_release`) and the owner-failure path (`_release_without_storing`) — but NOT on the cache-hit path (`_acquire_and_check`), which returned the cached row without ever calling `pg_advisory_unlock`. Every cache hit therefore leaked its lock into the pool. This was not caught by the first pass of tests because a low-concurrency test process tends to have `ThreadedConnectionPool.getconn()` hand back the just-released connection to the very next caller, which makes a session's own re-acquisition of a key it already holds succeed instantly (Postgres advisory locks are per-session-reentrant) — masking the bug. It was only caught by a test that opened a SEPARATE, pool-bypassing connection and called `pg_try_advisory_lock` (non-blocking) on the same key after a cache hit, asserting it could actually be acquired. (2) After that fix, `_store_and_release` still ran the `INSERT INTO completions ...` and `SELECT pg_advisory_unlock(...)` inside the SAME `with conn:` block. Passed locally 100+ times in a row, then failed in real CI (GitHub Actions) with `assert 2 == 1` on `test_identical_task_ref_across_two_sessions_calls_compute_once`: the waiter's blocked `pg_advisory_lock` returned right after the unlock ran, queried `completions` before the preceding INSERT's transaction had actually committed, saw no row, and called `compute()` itself. Confirmed as the root cause (not a CI flake) by reverting the eventual fix and running the local test 40x: 2/40 failures with the unlock inside the same block as the INSERT, 0/40 after splitting the INSERT into its own committed `with conn:` block ahead of a second block containing only the unlock.

catch_next_time: When reviewing or writing any acquire-check-act-release protocol around a session-scoped lock (Postgres advisory locks, or any similar primitive tied to a connection/session rather than a transaction), (1) enumerate every return path out of the guarded block BEFORE trusting the happy-path tests, and confirm each one releases the lock — do not trust a same-process test with a small connection pool to catch a leaked lock, since pool reuse can hand the same session back to the next caller and make a reentrant re-acquisition look like success; verify with a lock-state check from a connection that deliberately bypasses the pool (e.g. `pg_try_advisory_lock` from a fresh, independent connection). (2) Never issue a non-transactional release (an advisory unlock, or anything else session-scoped) in the same transaction block as a write whose visibility the release is meant to signal — commit the write in its own block first, THEN release, so anything woken by the release is guaranteed to see it. A local test suite alone is not proof against this: the race window can be too narrow to hit on fast local hardware/loopback Postgres and still fire reliably on a slower or differently-scheduled CI runner — treat a local pass as inconclusive for lock/commit-ordering claims specifically, and reason about the statement order directly rather than trusting green local runs.
