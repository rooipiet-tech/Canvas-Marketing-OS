statement: A session-scoped Postgres advisory lock (`pg_advisory_lock`) that is acquired to gate a check-then-act sequence must be released on EVERY return path out of that sequence, including the "nothing to do" path — not just the success and failure paths of the work it guards. Returning a pooled connection to a `ThreadedConnectionPool` without first calling `pg_advisory_unlock` does not release the lock: the lock stays held by that connection's Postgres session for as long as the connection lives in the pool (often indefinitely), and any future caller who acquires the SAME key on a DIFFERENT pooled connection blocks forever, since nothing will ever unlock it.

evidence: `services/model-gateway/caching.py`'s `PostgresCache` (TD-06's fix for cross-replica task_ref idempotency) acquires `pg_advisory_lock(hashtextextended(task_ref, 0))`, checks the `completions` table, and either (a) returns a cache hit immediately, or (b) becomes the owner, awaits `compute()`, then stores the result and unlocks. The initial implementation unlocked correctly on both the owner-success path (`_store_and_release`) and the owner-failure path (`_release_without_storing`) — but NOT on the cache-hit path (`_acquire_and_check`), which returned the cached row without ever calling `pg_advisory_unlock`. Every cache hit therefore leaked its lock into the pool. This was not caught by the first pass of tests because a low-concurrency test process tends to have `ThreadedConnectionPool.getconn()` hand back the just-released connection to the very next caller, which makes a session's own re-acquisition of a key it already holds succeed instantly (Postgres advisory locks are per-session-reentrant) — masking the bug. It was only caught by a test that opened a SEPARATE, pool-bypassing connection and called `pg_try_advisory_lock` (non-blocking) on the same key after a cache hit, asserting it could actually be acquired.

catch_next_time: When reviewing or writing any acquire-check-act-release protocol around a session-scoped lock (Postgres advisory locks, or any similar primitive tied to a connection/session rather than a transaction), enumerate every return path out of the guarded block BEFORE trusting the happy-path tests, and confirm each one releases the lock. Do not trust a same-process test with a small connection pool to catch a leaked lock — pool reuse can hand the SAME session back to the next caller, making a reentrant re-acquisition look like success. Verify with a lock-state check from a connection that deliberately bypasses the pool (e.g. `pg_try_advisory_lock` from a fresh, independent connection) rather than only asserting on `get_or_compute`'s return value.
