statement: Azure Container Apps Jobs does not mark a job EXECUTION "Failed" just because its single replica's container crashed immediately (e.g. `exec: "python": executable file not found in $PATH`) — the execution stays reported as "Running" until the job's own `replicaTimeout` fully elapses, at which point it transitions via a `DeadlineExceeded` system event. A CI poll with a shorter budget than `replicaTimeout` will time out reporting a false "still Running" for a failure that actually happened in seconds.

evidence: On 2026-07-31, `caj-orchestrator-smoke-test-e7e7956`'s container was created, pulled its image, and was terminated with exit code 1 (`ContainerCreateFailure`, OCI runtime error) within 13 seconds — confirmed via `ContainerAppSystemLogs_CL` (`az rest POST https://api.loganalytics.io/v1/workspaces/<id>/query`, not `az containerapp job logs show`, since the failure was pre-exec and produced zero console output). The job's `replicaTimeout` was 900s; deploy-infra.yml's poll budget was 40×15s=600s. The poll exhausted its budget reporting `status = Running` on every attempt, then failed with a generic "did not reach Succeeded" message that gave no hint the container had actually died 587 seconds earlier. `az containerapp job execution list --query "[0].properties.status"` alone cannot distinguish "genuinely still working" from "crashed instantly, waiting out the clock" — both report `Running`.

catch_next_time: (1) Never trust a bare job-execution `status` poll to mean "still making progress" — if a poll's budget is anywhere near or shorter than the job's `replicaTimeout`, add a mid-poll diagnostic checkpoint (e.g. every N attempts) that pulls independent signal: the job's own system-log events via Log Analytics (`ContainerAppSystemLogs_CL`, filtered `JobName_s`), or any other observable precondition specific to what the job is supposed to do. (2) When a job's precondition for success is knowable BEFORE starting it (e.g. "the image it will run must not be a placeholder with no interpreter for the command it runs"), check that precondition and fail in under a second with a clear diagnostic — never start (and then poll) a job already known to be doomed. (3) `az containerapp job logs show` queries console-stream output only; a pre-exec container-create failure produces none — `ContainerAppSystemLogs_CL`/`ContainerAppSystemLogs` (the `_CL` custom-log variant, not the built-in table, was the one actually receiving data in this workspace — verify which is live via the `Usage` table's `DataType` breakdown before assuming either) is where `ContainerCreateFailure`/`DeadlineExceeded` events actually land.
