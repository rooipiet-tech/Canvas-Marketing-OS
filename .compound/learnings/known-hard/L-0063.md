statement: Azure Container Apps ingress (internal OR external) terminates TLS and 301-redirects a plain `http://` request to the same URL over `https://`, even for internal-only ingress with no custom domain/certificate configured — a managed certificate for the environment's internal default domain is issued automatically. Any HTTP client hitting an internal Container App FQDN must use `https://` (or explicitly follow redirects); `httpx` — unlike `requests` — does NOT follow redirects by default, so a bare `httpx.get(url)` against an `http://` internal FQDN gets an `HTTPStatusError` on every single call, forever, never reaching the actual endpoint.

evidence: On 2026-07-31, `caj-orchestrator-smoke-test-tdituuf` ran the full 20-attempt/300s poll budget failing every attempt with `Redirect response '301 Moved Permanently' for url 'http://ca-orchestrator.internal...azurecontainerapps.io/status'`. Cross-checked evidence proved the underlying pipeline was completely healthy the entire time: the synthetic heartbeat published successfully, `ca-orchestrator`'s own console logs showed `heartbeat_decomposed` (task_count=20) and all 20 `task_completed` events within 12 seconds of the heartbeat landing, and Service Bus RBAC/queue names were unchanged and correct (already verified in a prior round). The smoke test's own `httpx.get(status_url, timeout=10.0)` (no `follow_redirects=True`) was the entire failure — it never once reached `/status` to see the results that were there the whole time. `infra/main.bicep`'s `orchestratorStatusUrl` had used `http://` while two sibling services in the same file (`gatekeeperApiBaseUrl`, `vaultBaseUrl`) already used `https://` for the identical `${...outputs.internalFqdn}` pattern — the inconsistency was introduced fresh in orchestrator's own build, not inherited from precedent.

catch_next_time: Any Bicep-computed URL built from a Container App's `internalFqdn`/`fqdn` output must use `https://`, never `http://` — grep new IaC for `'http://${.*Fqdn` before merging. Any Python `httpx.get`/`httpx.Client` call against an internal service URL should pass `follow_redirects=True` explicitly as defense-in-depth (httpx's default is the opposite of `requests`' — an easy, silent surprise for anyone used to `requests`). When a smoke/health-check poll fails identically on every single attempt with the SAME error for the SAME reason (not a flaky mix of statuses), suspect the poll's own request mechanics before the system under test — cross-check the target process's own logs for the actual business-logic outcome before assuming the pipeline itself is broken.
