statement: Azure resource-provider/feature registration (e.g. `az feature register` for `Microsoft.App/WorkloadProfiles`, or the subsequent `az provider register`) is a one-time, asynchronous operation whose first-time propagation time is not a fixed SLA and can exceed 10 minutes on a cold subscription/feature combination. A bounded poll timing out on this is expected, retriable behavior — not a code or build defect — and re-running the same idempotent registration/poll steps (or the whole workflow) continues correctly once Azure finishes propagating.

evidence: The canvas-marketing-os-foundation deploy-infra.yml's WorkloadProfiles preflight poll (20 attempts x 30s = 10min bound, from plan v2's F5 fix) hit exactly this: the real deploy run timed out with the feature still `Pending`, not `Registered`. Recovery was simply to wait for `az feature show ... --query properties.state` to report `Registered`, run `az provider register --namespace Microsoft.App --wait` to propagate it, then re-run the failed jobs — no code change was needed.

catch_next_time: When a plan/build includes a bounded poll on any first-time Azure resource-provider/feature registration, (1) do not treat a poll timeout on the FIRST real deploy attempt as a build failure requiring a code fix — classify it as an expected, retriable environmental condition; (2) design the registration step to have a fast path that skips the poll entirely when the provider/feature is already Registered (so subsequent runs after the first successful registration are fast); (3) have the timeout's failure message print the exact manual recovery commands (check state, re-register, re-run) so a human doesn't have to reconstruct them; (4) do not increase the bound indefinitely to "solve" this — a bounded poll with a clear, actionable failure message and safe re-run idempotency is the correct design, not an unbounded wait.
