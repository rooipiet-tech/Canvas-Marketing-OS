statement: GitHub Environments' required-reviewers protection rule cannot be self-approved by the same account that triggered the deployment — a cost-governance gate built around a single-identity required-reviewer will pause indefinitely with no way to complete verification of the gated deploy in a single-account session.

evidence: On the canvas-marketing-os-foundation run, the only resolvable reviewer identity (the repo owner) was also the account that would trigger real deploys via push-to-main. The user was asked mid-plan how to resolve this and explicitly chose "Proceed, verify later" — building the gate correctly but accepting that SUCCESS-criteria depending on a real gated deploy completing might remain unverified for the session.

catch_next_time: When a spec/plan locks a required-reviewers cost gate as a Must-have, require a second, distinct reviewer identity (a teammate, bot account, or team) to be named at spec time — or explicitly split the criterion into two separately-verifiable claims: "the gate exists and is configured correctly" (structurally verifiable any time) vs. "a real gated deploy completed" (only verifiable once a second approver identity exists).
