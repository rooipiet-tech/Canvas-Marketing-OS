statement: Classic Microsoft Teams incoming webhooks (O365 Connectors) are retired (disabled May 2026, confirmed via the Microsoft 365 Developer Blog retirement notice and Message Center MC1181996 — high confidence); the successor is Workflows (Power Automate)-based webhooks accepting Adaptive Cards. Native in-card button postback is *believed* to require a registered Teams Bot (Bot Framework) — this second part is medium-confidence only (secondary sources, no canonical primary doc found as of this run) and should be re-verified via a direct Microsoft Learn/Bot Framework doc fetch before being relied on as settled. Until then, default Approve/Reject affordances to Adaptive Card `Action.OpenUrl` deep-links, never `Action.Submit`/`Action.Execute`, and re-check the Bot Framework requirement if a future spec leans on exact in-card postback semantics.

evidence: In the S4 governance build, the GOAL asked for "Teams incoming-webhook channel... Approve/Reject actions." Domain-expert research (live web search) found the classic connector-based webhook mechanism retired, and the achievable substitute — Workflows-based webhook + Adaptive Card with `Action.OpenUrl` deep-links to an authenticated external endpoint — was adopted (AC-04/AC-23), tested by `test_card_uses_openurl_not_submit_action`.

catch_next_time: When a spec calls for "Teams webhook with clickable approve/reject buttons," check current Teams webhook retirement status first (classic connector webhooks are gone) and default the design to Workflows-based webhook + Adaptive Card + `Action.OpenUrl` deep links. Treat the Bot-Framework-for-native-postback claim as unconfirmed until independently re-verified against a primary Microsoft doc.
