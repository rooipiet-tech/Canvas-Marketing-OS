statement: `az containerapp job start --yaml <file>` does not validate that
the YAML's top-level shape matches what the underlying ARM `/start` action
actually accepts (`StartJobExecutionTemplate`: `containers`/`initContainers`
at the top level, no `properties`/`template` wrapper). Passing the
`properties: / template: / containers:` shape used by `job create`/`job
update` — the natural shape to guess, since it's what every other
`containerapp`/`job` resource command accepts — is silently ignored: the CLI
issues the start with no error, the job runs its unmodified PERSISTED
template instead of the intended override, and the execution can still
report `Succeeded`, because a job's Bicep-default query/command is often
itself valid and harmless. Nothing about the visible outcome (exit code,
execution status) distinguishes "override applied" from "override silently
dropped." This is a strictly worse failure mode than L-0022's `--env-vars`
bug, which at least errored loudly (`ContainerAppImageRequired`) — this one
looks identical to success.

evidence: `deploy-gateway.yml`'s "Seed a real agent_run" step (built per
L-0022's `--yaml`-override fix) reported `Succeeded` in CI, but the actual
`agent_run_id` parse then failed at the NEXT step (`job logs show` missing
`--container`) before anything checked the query result content. Live
diagnosis of the underlying execution via `az rest GET
.../jobs/caj-vault-query/executions/<name>?api-version=2024-03-01` showed
`properties.template.containers[0].env` held the job's Bicep-default
table-listing query, not the SEED_QUERY the workflow had submitted — despite
the `job start --yaml` call itself exiting 0. Confirmed root cause directly:
POSTing the same `properties: / template: / containers:` YAML content (as
JSON) straight to `POST
.../jobs/caj-vault-query/start?api-version=2024-03-01` via `az rest`
returned `400 Bad Request: "Unknown properties template in
StartJobExecutionTemplate are not supported"` — proving the REST body type
has no such wrapper. POSTing the BARE shape (`{"containers": [...]}`)
instead returned `200` with an execution name, and `az rest GET` on that
execution confirmed the override query was actually used and the execution
succeeded for real. This also means L-0022's own "verified live" evidence
(execution status `Succeeded` for an INSERT and a SELECT) was not, by
itself, proof the override had applied — it was consistent with either
outcome, and the earlier verification did not check the execution's
resolved template content the way this round's diagnosis did.

catch_next_time: For `az containerapp job start` with any override content,
skip the CLI's `--yaml`/Container-Argument translation entirely and call
`az rest --method post --url
".../subscriptions/{subscriptionId}/resourceGroups/<rg>/providers/Microsoft.App/jobs/<job>/start?api-version=2024-03-01"
--body @file.json` with a body built directly in the REST action's own shape
(`containers`/`initContainers`, no wrapper) — `{subscriptionId}` in the URL
resolves via the CLI's current login context, no extra lookup needed. More
generally: an execution reporting `Succeeded` after an override is NOT
evidence the override applied if the job's default behavior is also a valid
no-op/success case — verify by reading the execution's OWN resolved
`properties.template` (`az rest GET .../executions/<name>`), not just its
`properties.status`, whenever a CLI override path is new or unverified. This
generalizes past this one job: any `az ... start --yaml`-style "trigger with
an inline override" command is worth asking "does this action's REST body
type actually match what I'm handing the CLI, or am I assuming the shape
from a sibling `create`/`update` command?"

recurrence 2026-07-30: hit the SAME class one call site over, via a
DIFFERENT CLI path — `caj-gateway-smoke`'s `job create`/`update --command
/bin/sh --args '-c' "$SMOKE_CMD"` failed loudly this time
(`ERROR: unrecognized arguments: -c STATUS=$(curl ...`), because argparse's
`nargs='+'` for `--args` stops consuming values the instant it sees a token
starting with `-` — `-c` looks like a new flag, so it and everything after
fall through as unrecognized positional args. Loud failure this time, not
silent, but same underlying cause: a CLI flag-based path trying to carry an
arbitrary multi-word shell command can't be trusted, whether the flag is
`--yaml`, `--args`, or `--env-vars` (L-0022). General fix pattern that now
applies uniformly across all three `caj-*` job-invocation call sites in
`deploy-gateway.yml`: use `job create`/`update` ONLY to scaffold the job
resource itself (trigger type, environment, resources, a name/image that
may never actually run) with NO command/args/env override at creation time,
then supply the real per-run command/query exclusively through `az rest
POST .../start` with a JSON-array command and `jq --arg`-escaped values —
never via any CLI flag whose value is an arbitrary multi-word string.
