statement: A GitHub Actions job authenticating `anthropics/claude-code-action` via a
metered `ANTHROPIC_API_KEY` fails silently and misleadingly once the account's
monthly API budget cap is reached: the SDK still initializes ("Claude Code
initialized"), burns real wall-clock time (observed 367ms to ~174s across
different runs), and then returns
`{"type":"result","subtype":"success","is_error":true,"total_cost_usd":0,"modelUsage":{}}`
-- a `subtype: "success"` alongside `is_error: true`, zero recorded cost, and
empty usage. The action's default output redaction ("full output hidden for
security") hides whatever real error text the SDK produced, so the job logs
alone give no hint that it is a budget/billing issue rather than a bug in the
prompt, the skill, or the workflow YAML. This broke every claude-code-action
workflow in this repo (`claude-review` AND `claude-system-audit`)
simultaneously and silently for six days (2026-09-04 13:55 UTC through
2026-09-10). Raising the budget cap is not durable on its own: a manual
increase let one scheduled run succeed, then the identical failure recurred
within roughly a day, because the account was still running the DAILY
cadence against a still-metered key (~$8-12/run) rather than the intended
weekly cadence with subscription auth -- the raise bought a day, not a fix.

evidence: Reviewed workflow run history for `claude-review.yml` and
`claude-system-audit.yml`. Run 64 (claude-review, 2026-09-04 13:36 UTC)
succeeded normally; run 65 (2026-09-04 13:55 UTC) and every run after it --
across both workflows, across different models (`claude-sonnet-5` and
`claude-opus-5[1m]`), across different audit lenses and different PRs --
failed with the identical `is_error:true`/`$0`-cost/empty-`modelUsage`
signature. A `workflow_dispatch` diagnostic with `show_full_output: true`
failed to capture the real error because the action independently refuses to
exchange its OIDC token for an app token when the dispatching ref's workflow
file differs from the default branch's copy -- a separate anti-tampering
guard, not the underlying bug, and it silently reports the step as `success`
while skipping Claude entirely. Root cause (monthly `ANTHROPIC_API_KEY`
budget cap reached) was confirmed by the account owner directly. After the
owner manually raised the budget, `claude-system-audit` run #13
(2026-09-14) succeeded, but run #14 (2026-09-15) and run #15 (2026-09-16)
failed with the exact same signature -- because the fix that would have
stopped the daily metered burn (a cadence revert + a switch to
`claude_code_oauth_token`) had been prepared on a feature branch but never
actually reached `main`: its PR had already merged its ORIGINAL (problem-
causing) content days earlier, and every subsequent commit pushed to that
same branch, assumed to still be tracked by an open PR, was silently
orphaned -- see the companion process learning this incident also produced
(git history, not a live PR check, is what confirmed this).

catch_next_time: When every claude-code-action step across multiple
unrelated workflows starts failing at the same moment with `is_error:true`,
`total_cost_usd:0`, and empty `modelUsage` -- regardless of duration, model,
or prompt -- suspect account-level billing/budget/auth before touching the
workflow YAML, the skill, or the prompt. To get the actual error text out of
a redacted run, `show_full_output: true` (or GitHub's debug re-run) only
works when the workflow file being executed is byte-identical to the default
branch's copy -- a diagnostic edit made on a feature/PR branch silently
no-ops instead of running Claude, and itself reports `conclusion: success`.
Raising a metered budget cap treats the symptom, not the cause, for a
recurring scheduled job -- confirm the intended run cadence is actually live
on `main` (not stuck on a stale schedule from an unmerged fix) before
trusting that a raised cap will hold. To remove the budget-cap failure mode
entirely for the metered work itself, authenticate via `claude_code_oauth_token`
(minted from a Claude subscription with `claude setup-token`) instead of a
metered `anthropic_api_key`; a separate, low-traffic `ANTHROPIC_API_KEY` can
still be kept for a cheap, non-generating call (e.g. a `GET
/v1/models/{id}` liveness probe) without reintroducing the risk.
