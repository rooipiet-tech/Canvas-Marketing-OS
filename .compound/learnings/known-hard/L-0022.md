statement: `az containerapp job start` does NOT patch a single field onto the
job template's existing container — passing ANY "Container Argument"
(`--env-vars`, `--command`, `--cpu`, `--memory`, `--args`,
`--container-name`) switches the CLI into an override mode that constructs a
brand-new container spec from scratch, silently dropping every field not
explicitly re-supplied (image, command, other env vars) even though the
job's own Bicep-defined template already has a perfectly valid default for
all of them. `--env-vars QUERY=...` alone fails outright with
`ERROR (ContainerAppImageRequired)`; adding `--image` back still silently
drops `command` and any other env var (e.g. a `DATABASE_URL` secretRef),
leaving a container that runs the bare image entrypoint instead of the
intended command. This is a CLI invocation gotcha, not a Bicep gap — do not
"fix" it by adding more Bicep template properties; the template was already
correct.

evidence: `deploy-gateway.yml`'s "Seed a real agent_run" step called
`az containerapp job start -n caj-vault-query --env-vars QUERY="$SEED_QUERY"`
and failed with `ERROR (ContainerAppImageRequired) Container with name
'caj-vault-query' must have an 'Image' property specified` — even though
`az containerapp job show -n caj-vault-query --query
properties.template.containers` confirmed the live template already had
`image: postgres:16` (matching `vault-query-job.bicep`'s
`image: 'postgres:16'` default, unchanged). Reproduced live: adding
`--image postgres:16` alongside `--env-vars` made the start call succeed,
but the resulting execution's `properties.template.containers[0]` (visible
via `az containerapp job execution list`) had NO `command` field at all and
only the one env var passed (`QUERY`) — `DATABASE_URL` was gone — so the
container just ran `postgres:16`'s default entrypoint and the execution
failed for a different, more confusing reason (no psql invocation at all).
Fixed by building a full `--yaml` override per invocation, restating image +
command + both env vars (only the `QUERY` value differs run to run);
verified live against `cmos-dev` twice — a real `INSERT ... RETURNING id`
seed and a follow-up `SELECT` confirming the inserted row both completed
with job execution status `Succeeded` through the `--yaml` path, vs.
`Failed` through `--image`+`--env-vars`.

catch_next_time: Before debugging a Container Apps Job's Bicep template in
response to a "must have an Image property" or similarly-missing-field
error at job-start time, first run `az containerapp job show --query
properties.template.containers` to check whether the template already has a
valid default — if it does, the bug is almost certainly in how `job start`
is being invoked, not in Bicep. Any CI step (or documented human runbook
command) that calls `az containerapp job start` with `--env-vars` or any
other Container Argument needs a full `--yaml` override, not a bare flag —
verify this by checking the resulting execution's own
`properties.template.containers` (via `az containerapp job execution list`)
for the fields you expect (image, command, every env var), not just the
job's start-time exit code.
