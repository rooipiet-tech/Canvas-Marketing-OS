statement: GitHub Environments' required-reviewers protection rule has a `prevent_self_review` flag (set via the environment's deployment-protection-rule config, e.g. through `gh api`). When `true`, the account that triggered a deployment cannot approve its own gated run; when `false` (as it can validly be configured), self-approval is explicitly allowed. This is a configuration choice, not an unconditional GitHub platform restriction — an earlier version of this learning wrongly treated self-approval as categorically blocked for any single-identity repo.

evidence: On the canvas-marketing-os-foundation run, reviewers (plan-reviewer, output-reviewer, agent-native) all assumed self-approval was unconditionally blocked when only one reviewer identity existed, and the user was asked to resolve it as if it were a hard limitation. The user later confirmed they had configured the `cmos-dev` environment's required-reviewers rule with `prevent_self_review=false` via `gh api`, meaning the sole repo-owner identity CAN approve their own gated deploys — no second identity was needed. The original "self-approval is always blocked" claim was an unverified assumption, not a checked platform fact.

catch_next_time: When a spec/plan locks a required-reviewers cost gate as a Must-have and only one reviewer identity is available, do not assume self-approval is blocked — check (or explicitly set) the `prevent_self_review` field on the environment's required-reviewers protection rule via `gh api repos/{owner}/{repo}/environments/{name}` before concluding a second identity is required. Only escalate to "needs a second approver" if `prevent_self_review` is (or must be) `true` for the given governance intent.
