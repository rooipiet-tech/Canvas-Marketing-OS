statement: Embedding a shell variable inside a double-quoted string that is itself passed as a literal argument to another language's interpreter (e.g. `python -c "...['$id']..."` inside bash) lets the outer shell expand the variable before the inner interpreter ever sees it, silently producing an empty/wrong literal and guaranteeing failure independent of the code under test.

evidence: GOV-001's original verify command in the canvas-marketing-os-foundation spec had exactly this bug — bash expanded `$id` to empty before Python ran, guaranteeing a KeyError against any valid JSON Schema regardless of build quality. Caught by the plan-reviewer before any code was written; fixed via single-quoted `python -c '...'` with escaped inner double-quotes so `$id` passed through literally.

catch_next_time: When authoring or reviewing any verify command that embeds a nested-language literal (Python/SQL/JSON key names, regex containing `$`) inside a shell string, check whether that literal must NOT be shell-expanded. If so, require single-quoting the outer shell argument (or a heredoc) instead of double-quoting. Treat this as a standing plan-reviewer/spec-reviewer checklist item whenever a verify command mixes shell and another language's syntax.
