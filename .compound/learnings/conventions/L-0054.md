statement: When a spec depends on prerequisite PRs still open/unmerged at freeze
time, it's viable to build against the PR branches' real file content (via
`git show <remote-branch>:<path>`) as the de-facto target format rather than
inventing a shape or waiting — but the actual PR-open action must be gated on a
fresh rebase + re-verification against the real merged tooling, and the spec's own
amendment mechanism must absorb a mid-session merge event (dropping any
temp/scratch scaffolding) rather than shipping it as if the prerequisite were still
unmerged.

evidence: PR#6 (session/s6-registry) and PR#7 (session/s3-orchestrator) were both
open/unmerged/conflicting at spec-freeze; the build used git-show to read their
content without merging (per explicit user instruction "do not wait"). Both merged
mid-session, discovered independently by the plan-reviewer (`git merge-base
--is-ancestor`) and the orchestrator (fresh `git fetch`+`git rebase`). Spec was
amended v3 to drop temp-worktree scaffolding for direct in-repo tooling, and AC-39
became a real pre-PR rebase+re-verify gate per the user's explicit condition.

catch_next_time: Orchestrator — before opening a PR, run `git fetch && git
merge-base --is-ancestor <prereq-branch> origin/main` for every prerequisite
branch named in spec.json's constraints; if any newly merged mid-session, amend
the spec to replace git-show/scratch-worktree scaffolding with direct in-repo
tooling, then re-run the full verify sweep against the rebased tree before opening
the PR — never open on the stale (pre-merge) assumption.
