statement: A GitHub branch-protection `required_status_checks` list (e.g.
`lint`, `validate-contracts`) is only satisfiable if some workflow actually
posts a check run with that exact job name on `pull_request` events. This
repo's `ci.yml` defined jobs named `lint` and `validate-contracts` and both
were configured as required checks in branch protection — but the workflow's
only triggers were `push: {branches: [main]}` and `workflow_dispatch`, with
no `pull_request` trigger at all. The effect isn't merely "path-filtered PRs
don't get checks" (the symptom first observed) — it's that literally zero
PRs, regardless of what they touch, ever get a `lint`/`validate-contracts`
check run, because the workflow never fires on `pull_request` in the first
place. Every PR against `main` was permanently unmergeable through normal
branch protection, requiring `gh pr merge --admin` every single time.

evidence: `gh api repos/.../branches/main/protection --jq
'.required_status_checks'` returned `contexts: ["lint",
"validate-contracts"]`. `grep -rl pull_request .github/workflows/` returned
no files in the entire repo. PR #19 (deploy-infra autopass gate, touching
only `.github/workflows/deploy-infra.yml` and `.compound/**`) sat at
`mergeStateStatus: BLOCKED` / `mergeable: MERGEABLE` with `gh pr checks 19`
reporting "no checks reported on the branch" — not failing, not pending,
just absent — confirming the checks were never even scheduled, not merely
skipped by a path filter.

catch_next_time: When a PR sits BLOCKED with MERGEABLE=true and `gh pr
checks` reports zero checks (not pending, not failing — genuinely absent),
check whether the required check's source workflow has a `pull_request`
trigger at all before assuming a `paths:` filter is the culprit — an absent
trigger and a mismatched path filter look identical from the PR side (no
check ever posts) but need different fixes. Fix: add `pull_request:
{branches: [main]}` alongside the existing `push` trigger so required jobs
always run on every PR (a required-skip / conditional-path pattern is only
needed if you want to selectively skip expensive jobs on unrelated changes
— unconditional-always-run is simpler and was what was needed here, since
`lint`/`validate-contracts`/`migration-test` are all fast and repo-wide
anyway). Verify by opening a real PR and confirming `gh pr checks <n>` shows
running/queued entries, not just that the YAML parses.
