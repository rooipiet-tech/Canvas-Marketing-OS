statement: A workflow file's own header comment claiming "copied deploy-X.yml's implementation rather than re-deriving it" is a claim about intent, not a guarantee about the result — a step can be silently dropped in the copy, and nothing catches it until the specific failure mode that step existed to prevent actually occurs live. This is the same meta-pattern L-0066's RECURRENCE #3 documents for an aspirational pyproject.toml comment ("installed as a separate step... mirrors console's convention") that described work never actually done — here the vector is a workflow-to-workflow copy instead of a comment-to-file claim, but the failure to verify is identical.

evidence: deploy-mcp.yml's header comment states it was "Rebuilt from scratch... copying deploy-gateway.yml's implementation (the most mature instance of this pattern) rather than re-deriving it." deploy-gateway.yml's build-and-push job calls `az acr login --name "$REGISTRY_NAME"` immediately before its `docker build`/`docker push` steps — `azure/login@v2` (both workflows have this) only authenticates the Azure CLI's own session; it does not configure docker's separate credential store. deploy-mcp.yml's build-and-push job has `azure/login@v2` and `docker/setup-buildx-action@v3` but never calls `az acr login` at all, so every `docker/build-push-action@v6` push attempted anonymously and failed with `failed to fetch anonymous token: ... 401 Unauthorized`. Confirmed live (2026-08-02, caj-loop-e2e-smoke #8 attempt 3): `az acr repository list` on the shared ACR showed only console/model-gateway/orchestrator/vault — mcp-web/mcp-buffer/mcp-canva/mcp-smoke had NEVER had a successful build in this environment's entire history (every prior deploy-mcp run was either this same 401 failure or cancelled by the shared `cmos-dev-deploy` concurrency group). Their Container Apps had been silently running the Bicep bootstrap placeholder (`mcr.microsoft.com/azuredocs/containerapps-helloworld`) since creation — which is what actually caused ca-orchestrator's ingest-signals task to see every `fetch_url` MCP call to mcp-web time out ("The read operation timed out"): mcp-web's real app was never running to answer them, and its `runningState` was `ActivationFailed`. This surfaced as escalation 5 (0/7 proof-circuit stages ever terminal) — a symptom that superficially resembled a network/egress problem, when the actual root cause was one missing auth step in a workflow that had never once succeeded.

catch_next_time: (a) When a workflow's comment claims to mirror/copy a sibling workflow's implementation, diff the two files' auth/setup steps directly (`git diff` or side-by-side read) rather than trusting the claim — the exact list of steps a "mature, working" sibling has (az login, az acr login, staging steps, verification steps) is the real spec; the comment is not. (b) A Container App / Job whose `az acr repository list` shows no matching repository has NEVER been successfully deployed with a real image, full stop — treat this as categorically different from "was reset to placeholder" (L-0065's bug class): the fix is not restoring a prior good state (there isn't one) but getting the build-and-push pipeline to succeed for the first time, which means checking the actual build/push logs of its most recent run, not just re-triggering and hoping. (c) A live symptom that looks like a network/timeout problem (fetch_url_failed, "The read operation timed out") can have a root cause several layers removed from networking — check whether the SERVER on the other end of that call is even running the real application (query its own container logs for its actual startup banner) before investigating timeout tuning, egress rules, or the calling code's retry logic. (d) `docker/build-push-action@v6` (or bare `docker push`) with `push: true` fails LOUDLY on missing auth (401), which is actually the easy case — the dangerous version of this bug class is a silent success that pushes to the wrong place or with degraded auth; always read a "first ever successful run" claim's actual logs rather than inferring success from the job's green checkmark alone, since a green build-and-push run that never got exercised with real push credentials before now would be indistinguishable from one that did.
