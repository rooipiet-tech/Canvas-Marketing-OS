statement: A regression-guard check copied from a prior session's precedent to defend against a specific past bug can be structurally un-failable (providing zero real coverage while looking like a legitimate check) if the mechanism it asserts against can never actually occur given the check's own inputs.

evidence: On the s3-orchestrator run, a builder copied a "$$"-collapse-survival assertion from the pre-existing migration-test CI job (itself inherited from an earlier session, commit 4a3dfa7) into a new orchestrator-test job, without validating whether it could actually fail. The migration lens found it empirically tautological: standard base64-encoded output never contains a literal "$" character, so the sed-based collapse-detection sub-check can never trip for any input, regardless of whether real corruption occurred — even though the round-trip diff check it's bundled with remains legitimate and would catch real encode/decode corruption.

catch_next_time: When adding or copying a regression-guard check that defends against a specific past bug (e.g. a secret-escaping/encoding collapse), verify the check can actually fail by constructing an input that reproduces the original failure mode before trusting it. A check that can never fail given its own inputs (e.g. asserting a substring's absence when that substring is structurally guaranteed absent by the encoding itself) provides false confidence, not real coverage — this applies even to checks inherited from a trusted prior-session precedent, not just ones authored fresh.
