statement: Local pytest/dev runs from a deeply-nested full repo checkout, or from a
test fixture (caplog, monkeypatch, tmp_path), can mask exactly the class of bug that
breaks a real deployment: filesystem-depth-assuming code and startup-configured
process state both "pass" locally while failing at the real entrypoint.

evidence: In the s1-gateway build, path-resolution code using
`Path(__file__).resolve().parents[N]` passed every local test yet raised an
unconditional `IndexError` at real container startup, because `/app/*.py` in the
built image is only 2 directories deep while a repo checkout or pytest's `tmp_path`
are both many levels deep — parents[2] always exists locally and never in the
container. Separately, a production logger that was never configured at process
startup was a silent no-op in a real process, but the shipped test only passed
because pytest's `caplog.set_level` forcibly overrides logging configuration,
masking the exact defect the test was meant to catch.

catch_next_time: For any code that (a) resolves filesystem paths relative to
`__file__`/a deployment root, or (b) depends on process-level state configured once
at startup (logging, env, global singletons), require a test or manual check that
exercises it at the ACTUAL target layout/entrypoint — construct path-resolution
tests from a fixture directory matching the real container's shallow depth (not the
repo's), and verify logging/startup-config output via a fresh subprocess or a direct
`dictConfig`/import check rather than only under a test fixture known to override
the exact thing being tested.
