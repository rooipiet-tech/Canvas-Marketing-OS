statement: Two sessions independently diagnosed the same live failure and built the same fix inside twenty minutes of each other, because neither checked whether the other was already on it. CLAUDE.md already requires probing `git branch -a` and `git log main..<branch>` before building ([[L-0042]], [[L-0055]]); the gap is that the probe feels unnecessary when the work originates from something you watched break yourself. **A failure you personally observed is the case where a sibling is MOST likely to be building the same fix, not least** — you are both reading the same red run.

evidence: `deploy-infra` run 142 failed on `caj-vault-smoke-test` at 16:35 on 2026-09-02. Session `018ad8Pv` committed `835cdb3` "Make deploy-infra print a failed job's log, not the command to fetch it" at 17:04 and merged it as #142. Session `01253MXn` committed `7dd5fab` "Dump the container job's logs on failure, instead of naming the command" at 17:20 and opened #143.

Same six poll-to-Succeeded sites in the same file, same container names read from the same Bicep modules, same two learnings cited (L-0024 for the mandatory `--container`, L-0064 for raw-output-first). The second session found out only when its own PR came back `mergeable_state: "dirty"`.

The duplicate was not free. It consumed a build, a review-quality PR body, and a merge-conflict resolution, and it delayed the one commit on that branch that was NOT duplicated (loop-smoke scan coverage) behind a conflict it had no part in causing.

catch_next_time: Before building a fix for a failure you just watched happen, list open PRs and recent commits on `main` for the file you are about to touch — a sibling reading the same red run is the likeliest author of the same change. Cost: one `list_pull_requests` call. This session ran none between diagnosing run 142 at ~16:45 and pushing at 17:20.

A conflicted PR is also a silent CI stall, which is how this surfaced: GitHub cannot build the test-merge commit for a PR whose `mergeable_state` is `dirty`, so `pull_request`-triggered workflows never start. The symptom is not a red check — it is **no checks at all**, indefinitely. When CI has not appeared minutes after opening a PR, read `mergeable_state` before assuming the runners are busy. "No failed checks" is not "green"; an empty check set usually means nothing ran.

When the duplicate is discovered after the fact, the merged version wins by default. Rewriting six working inline blocks into a shared script is a refactor with no functional gain and a fresh conflict as its cost — the DRY argument ([[L-0013]], [[L-0075]]) justifies choosing a shared mechanism when writing the code, not re-litigating one that already shipped.

open_question: Both implementations resolve the execution with `az containerapp job execution list --query "[0].name"` — the most RECENT execution, not provably the one just polled. Under the concurrent deploys that caused run 142 in the first place, `[0]` can belong to another run and the dumped logs would be confidently wrong. The polling loops have always read `[0].properties.status` the same way, so the shipped fix does not introduce it. `deploy-mcp.yml` shows the correct shape: capture the execution name from `az containerapp job start` and thread it through all six sites.
