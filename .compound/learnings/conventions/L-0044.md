statement: Frozen acceptance-criteria verify commands built from a single raw-byte hash comparison, a case-sensitive single-line grep, or an exact same-line co-location grep are fragile to local checkout/platform/formatting artifacts unrelated to code correctness — this is the inverse failure mode of [[L-0005]] (false failures on correct code, not false passes on broken code).

evidence: On the s3-orchestrator run, three independent instances each required a mid-loop spec amendment: (v3) AC-003's raw-byte hash comparison broke on a Windows checkout with core.autocrlf=true converting line endings, even though `git diff origin/main` proved the files were byte-identical; (v4) AC-025's grep pattern was written in Kubernetes-style lowercase ("readinessProbe", "liveness") against Azure Bicep's actual capitalized enum values ("Readiness", "Liveness"), so a correct, fully-wired implementation failed the check; (v5) AC-032's single-line grep for "json.dumps" co-located with "level"/"event" broke when a comment was legitimately reformatted across multiple lines during an unrelated bugfix patch, even though the underlying structured-logging code was unchanged and correct.

catch_next_time: When writing an automated verify command for a spec AC, prefer asserting the semantic property via multiple independent, formatting/platform-robust signals (e.g. a short script or multiple independent grep checks combined with &&, each checking one signal present anywhere in a file, case-insensitively, not requiring co-location on one line) over a single raw-byte hash comparison, a case-sensitive regex written against an unconfirmed casing convention, or a same-line grep pattern. Before freezing the check, mentally simulate: would this check still pass after a harmless reformat, and does it match the actual target platform's real casing/behavior (not an assumed convention from a different ecosystem)?
