statement: A CI assertion step built on `az ... --query <JMESPath> -o json` must (1) always `echo` the RAW, unfiltered `-o json` output before applying any `--query`/parsing, so a failure's diagnostic trail starts with ground truth instead of an already-filtered (possibly wrongly-filtered) value, and (2) never trust a single hardcoded JMESPath against a CLI command's output shape without having independently dumped that shape first — `az`'s CLI-normalized output frequently does NOT match the raw ARM REST `properties`-wrapped shape a plan/spec author assumes from memory or from a different command family, and different extension/CLI versions can present the same data with different nesting or key casing. Prefer capturing the full raw JSON once, then locating the needed field defensively in Python (try multiple known shapes, compare keys case-insensitively) over layering more JMESPath guesses.

evidence: The console's deploy-console.yml step (g) ("Assert authConfig carries no real client secret") failed with an opaque JSONDecodeError, was fixed (PR #40) by hardening the empty/null handling around `--query "properties.identityProviders.azureActiveDirectory.registration"` — but that fix still trusted the SAME query path, which was itself wrong: live-verified 2026-08-01 that `az containerapp auth show`'s actual output is FLAT (`identityProviders` at the top level, no `properties` wrapper at all), so the query had ALWAYS silently resolved to nothing and printed empty stdout. The operator caught this in about one minute specifically because PR #40's hardening already echoed the raw `-o json` output before attempting to parse it — the raw dump made "the query path doesn't match the actual shape" immediately visible by inspection, rather than requiring a fresh live reproduction from scratch. This is (per the operator) the seventh instance on this one console build of a live "failure" that traced to CI/tooling behavior rather than a genuine defect in the deployed system (see [[L-0027]], [[L-0048]], [[L-0049]] for earlier instances of the same broader class: don't trust the first failure signal to be about the system under test).

catch_next_time: When writing or reviewing any CI step that pipes `az`/similar CLI JSON output through a `--query` JMESPath or a script-level field lookup, require: (a) the step echoes the complete raw `-o json` response (no `--query` applied to the echoed copy) before any filtering, so a future failure's very first diagnostic artifact is ground truth; (b) the JMESPath/lookup path used was verified against an ACTUAL live dump of that exact command in this repo's environment at authoring time, not written from memory of the ARM REST schema or a different CLI subcommand's shape; (c) for any field expected to be structurally stable but whose exact nesting is uncertain (extension-version-dependent, preview API, etc.), do the shape lookup in Python against the raw JSON with 2-3 candidate paths tried in order, rather than a single JMESPath baked into the `az` call itself.
