statement: An acceptance criterion computed as a diff against HEAD (e.g. `git diff <merge-base>..HEAD`) can pass vacuously — trivially, on an empty commit range — when the actual work exists only as staged/uncommitted changes in the working tree/index. The check must be re-run AFTER the work is committed, not just validated against the working tree, or it risks certifying nothing.

evidence: On the s11-content run, the tester flagged that AC-01/AC-02/AC-03's git-diff-based scope-guard checks were passing vacuously because 89 files of real work (5842 insertions) existed only as staged/unstaged changes, not yet committed — `git rev-parse HEAD` equalled `git merge-base origin/main HEAD`, so the diff range under test was empty even though the working tree was fully compliant and complete. Resolved by committing the 89 files (confined exactly to functions/, services/orchestrator/loops/, docs/) and re-running AC-01/02/03 non-vacuously against the real committed diff.

catch_next_time: Before certifying any acceptance criterion that computes a git-diff/git-log range as evidence, confirm the range is non-empty AND that the work under test is actually committed, not merely staged or in the working tree. Re-run the check after commit if there is any doubt — a diff-based check against an empty or uncommitted range can pass by vacuously proving nothing.
