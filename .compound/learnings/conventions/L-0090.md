statement: A GitHub pull request stops tracking new pushes to its head branch
the moment it is merged (or closed) — the PR itself is locked to the commit it
merged at. Continuing to push follow-up commits to that same branch name in
later turns of a long-running session, on the assumption "my designated
branch has an open PR I'm updating," silently produces commits that exist on
the remote branch but are visible in no PR and reach `main` only if someone
separately notices and re-opens one. Nothing about `git push` or a successful
`git log HEAD..origin/branch` check surfaces this — the push succeeds
normally either way.

evidence: Branch `claude/continuous-audit-daily-wft7zr` had its PR (#154)
merged on 2026-09-05 (a 2-file, 2-commit change). This session then pushed
five further commits to that same branch across 2026-09-10 through
2026-09-19 (a cadence revert, an OAuth-token migration for L-0089, a doc
cleanup) — each push reported success, and pre-push divergence checks
(`git log HEAD..origin/branch`) reported clean, because they only compare
against the branch tip, never against PR state. None of that work ever
reached `main`, since #154 had nothing left to merge it through. This was
only discovered when a `merge_pull_request` attempt required first reading
the PR's current state (`pull_request_read`) and #154 came back
`"state":"closed","merged":true` with content matching only the ORIGINAL
2026-09-05 change — five real commits of intended work were sitting
orphaned, invisible unless someone thought to check.

catch_next_time: Before pushing a commit intended to update "the PR for this
branch," and especially after any gap since the branch was last touched
(a new session turn, a scheduled check-in firing hours or days later),
verify the PR is still open — `pull_request_read` (`get`) or equivalent,
checking `state`/`merged` — rather than assuming a prior turn's PR reference
is still valid. A `git push` succeeding, or a divergence check against the
branch tip coming back clean, is NOT evidence the PR is still open; those
checks and PR state are orthogonal. If a designated branch's PR has already
merged, per this repo's own harness convention: don't keep stacking commits
on the merged history — restart the branch from the latest default branch
(`git fetch origin <default> && git checkout -B <branch> origin/<default>`),
rebase or hand-reapply any unmerged follow-up commits onto that fresh base,
force-push, and open a genuinely new PR.
