statement: GitHub Actions `workflow_run` cannot reference its own workflow — a workflow file cannot list itself in a `workflow_run.workflows` trigger ("Workflow 'X' cannot listen to itself" validation error). Retries belong inside the job as loops (bash retry wrappers, bounded polls), not as a self-triggering workflow_run + rerun mechanism. Cross-workflow workflow_run triggers (workflow A watching workflow B's completion) remain valid and unaffected by this restriction.

evidence: azure-provider-registration.yml was originally designed with a self-referential `workflow_run: workflows: ["azure-provider-registration"]` trigger plus an `auto-retry` job calling `gh run rerun --failed`, intended to auto-retry the registration job up to 2 times on failure. GitHub Actions rejected this at validation time with "Workflow 'azure-provider-registration' cannot listen to itself." Fixed by removing the workflow_run trigger and auto-retry job entirely and moving all retry logic (a `retry()` bash wrapper retrying up to 3 attempts per az CLI call, plus the existing fast-path/40-minute-bound poll for WorkloadProfiles) inside the single `register` job. deploy-infra.yml's separate `workflow_run: workflows: ["azure-provider-registration"]` trigger (a DIFFERENT workflow watching this one) remained valid throughout — only self-reference is forbidden.

catch_next_time: When designing a self-retry mechanism for a workflow, do not reach for `workflow_run` pointed at the workflow's own name — GitHub Actions will reject it at validation. Implement retries as in-job bash loops/functions (bounded attempt counts, sleep-and-retry) instead. `workflow_run` is only valid for one workflow observing a DIFFERENT workflow's completion (e.g. a gated deploy workflow watching an ungated preflight workflow succeed) — that cross-workflow pattern is fine and was not the source of this bug.
