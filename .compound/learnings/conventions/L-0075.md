statement: When N sibling methods on the same client share a convention (here: `vault_client_ext.py`'s `_taxonomy()` helper, spread into every `create_*()` method's payload), a method that never adopted the convention can survive completely undetected if it sits behind several EARLIER, unrelated bugs in the only code path that ever reaches it live — each earlier bug's fix just uncovers the next one, one at a time, rather than surfacing all of them together. A local/CI test suite that mocks the client's own transport (as this repo's `test_clients.py` did) verifies the method is *callable*, not that its payload matches what the real deployed service actually requires.

evidence: `services/orchestrator/orchestrator/clients/vault_client_ext.py`'s `get_or_create_campaign()` sent a bare `{"name": run_name}` POST body, while `create_signal()`/`create_brief()`/`create_agent_run()`/`create_asset()` all correctly spread `**_taxonomy(campaign=campaign_id, function_id=function_id)` into theirs. Vault's generic object-taxonomy validation (`vault/routers/objects.py`'s `validate_taxonomy()`, applying uniformly to all 9 object types including `campaigns` — pre-existing, not a regression) rejected the bare payload with `422 taxonomy_field_missing: vertical` the FIRST time this call was ever actually exercised against a real deployed Vault (escalation 10, deploy-loop-e2e-smoke #15, 2026-08-03) — every earlier attempt (escalations 4/5/6/8/9) died at an EARLIER stage in the same call chain (mcp-web never built, telemetry_lib crashes, an unresolved base_url), so this specific gap had zero live exposure across 5 prior escalations despite being present since the taxonomy convention was first introduced. The existing local unit tests (`test_clients.py`) mocked Vault's HTTP transport directly and asserted only `body["name"] == "run-xyz"` — they proved the method sent SOME payload with the right name, never that it matched Vault's real required-field contract.

catch_next_time: (a) When a shared helper/convention exists for constructing N similar payloads (here: `_taxonomy()`), audit EVERY call site that could use it, not just the ones a test suite currently exercises — grep for the target endpoint/table name (`/campaigns`, `/signals`, etc.) across the whole client and confirm each one spreads the shared helper, rather than trusting that "the pattern is established" means every instance follows it. (b) A local test that mocks a client's OWN transport can only validate what the TEST WRITER decided to assert on the request body — it says nothing about whether that body would actually satisfy the real service's contract; when the real service has its own explicit validation (like Vault's `validate_taxonomy()`), the mock-based test's assertions should mirror that contract's actual required fields, not just the one field the test happens to care about. (c) A chain of live escalations that each fix one bug and immediately hit the NEXT bug in the same call path is a sign the code has never been exercised end-to-end against live infrastructure before — expect several rounds, not one; each fix genuinely un-blocks progress even though the symptom (e.g. "0/7" then "1/7" stages terminal) looks superficially similar each time, and diagnosing from real logs each round (never guessing) is what keeps each fix targeted at the ACTUAL next blocker instead of a plausible-sounding guess.

FOLLOW-UP INCIDENT (2026-08-03, same day, escalation 11): the FIX for this exact learning shipped its own instance of the same failure mode it documents. PR #56's `get_or_create_campaign()` fix passed `campaign=run_name` (a string like `"run-<uuid>"`) into `_taxonomy()`, when every sibling `create_*()` method passes `campaign=campaign_id` — the real UUID `get_or_create_campaign()` itself returns, never a formatted name string. Vault's taxonomy `campaign` field is cast straight to SQL `uuid` (`uuid.UUID(str(payload["campaign"]))` in `vault/routers/objects.py`), so it 422'd again — `taxonomy_field_invalid: campaign must be a valid uuid` — this time only surfacing because a THIRD identical "1/7 stages terminal" reproduction (escalations 9/10/11) forced a closer read of the real logs rather than accepting "the fix looked complete." The PR's OWN strengthened test (`test_vault_client_get_or_create_campaign_creates_when_absent`) asserted `body["campaign"] == "run-xyz"` — a bare string — and passed, because the test's expected value was copied from the exact same wrong assumption as the implementation it was checking. A test written by the same person, in the same sitting, as the code it verifies inherits that code's blind spots; asserting "the mock got what I coded" is not the same as asserting "the mock got what the real contract requires."

catch_next_time (additional): (d) When a fix introduces a new required field into a payload, independently verify the field's REQUIRED SHAPE (not just its presence) against the real service's validation code — read the actual cast/parse/type-check the service applies (here, `uuid.UUID(str(payload["campaign"]))`), don't infer the shape from a nearby literal (`run_name`) that merely happens to be in scope and textually plausible. (e) A "strengthened" test written in the same pass as its fix is not independent verification — it verifies internal consistency (code and test agree), not external correctness (code and the real contract agree); prefer asserting a property that would fail for MULTIPLE plausible-but-wrong implementations (e.g. `uuid.UUID(value)` parses, not `value == "some-specific-string-i-picked"`) over asserting equality with a value the test author typed by hand while writing the same fix. (f) Three consecutive identical-looking failures ("1/7 stages terminal") across two supposedly-unrelated, independently-verified fixes is not evidence the symptom is unfixable at the application layer — each fix genuinely was correct and necessary, just for a bug one step further down the SAME call chain; don't let repetition of the surface symptom become a reason to suspect the wrong layer (the poll script, in this case, was correctly ruled out by reading its source directly) before re-reading the real logs for what changed.
