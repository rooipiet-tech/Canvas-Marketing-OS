statement: When two GitHub Actions workflows both fire on the same trigger
(e.g. push to main) and one's job depends on infrastructure the other
provisions, use `workflow_run` to chain them (B watches A's completion)
rather than letting both fire independently on the same event — a shared
`push` trigger races them with no ordering guarantee, and "usually finishes
in time" is not a real guarantee.

evidence: deploy-gateway.yml originally triggered on `push: branches: [main],
paths: [...]`, running in parallel with deploy-infra.yml's own push-triggered
chain (azure-provider-registration -> deploy-infra) on the same merge to
main. Combined with L-0017's ordering bug, this meant deploy-gateway could
attempt to update a Container App that deploy-infra hadn't successfully
provisioned yet (or had left in a bad state). Fixed by switching
deploy-gateway.yml's trigger to `workflow_run: workflows: ["deploy-infra"],
types: [completed]` with an explicit `conclusion == 'success'` check —
correctly distinguished from L-0009's "a workflow cannot reference itself"
constraint, since this is a genuine cross-workflow reference (B watching A),
not self-reference.

catch_next_time: When a plan introduces a new workflow whose job depends on
resources or state a DIFFERENT existing workflow provisions/creates, check
whether both would fire on the same trigger (typically push to main). If so,
chain them via `workflow_run` (the downstream workflow watches the upstream
one's completion, checking `conclusion == 'success'` explicitly since
`workflow_run` fires on every conclusion) instead of letting both listen to
the same event independently. Also add a fail-fast check in the downstream
workflow for the case its dependency is simply absent (e.g. `az <resource>
show || { echo "run <upstream> first"; exit 1; }`) rather than attempting to
imperatively create what the upstream IaC template is supposed to own — this
keeps the IaC template the single source of truth for that resource's shape
even when a CD-style pipeline updates parts of it (like an image tag)
afterward. Remember `workflow_run` cannot filter by `paths:`, so a downstream
workflow chained this way will fire on every successful upstream run, not
just ones that touched files it cares about — accept that tradeoff for
correct ordering, or add an in-job diff check if the extra runs become a
real cost concern.
