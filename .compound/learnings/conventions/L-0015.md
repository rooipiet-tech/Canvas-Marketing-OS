statement: A "persistent, not transient" failure re-occurring across two deploy attempts does not necessarily mean the root cause is new or that a code fix already merged didn't work — it can simply mean no deployment has actually happened since the fix landed. Before diagnosing a repeat failure as a new bug, check the live deployed state's actual configuration (not just execution history/logs) and cross-reference deployment timestamps (`az deployment group list`) against the fix commit's timestamp/branch. Separately: when multiple sessions or agents work on the same repo over time without full visibility into each other's work, they can independently rediscover and fix the identical bug on divergent branches — check whether a fix already exists elsewhere (another branch, a recent commit on the target branch) before authoring a redundant one.

evidence: On the canvas-marketing-os-foundation run, caj-vault-migrate failed twice (2026-07-23T14:34 and T15:07) with the identical `DO $$` → `DO $` dollar-quote collapse error (see L-0012). The second failure was reported as "the migration re-run failed again — persistent, not transient," prompting a fresh diagnosis. `az containerapp job show` (live config) confirmed the deployed job still had the pre-fix command/secrets; `az deployment group list` confirmed the last deploy to cmos-dev (2026-07-23T15:07) predated both the orchestrator's own fix (pushed to session/s0-foundation, never merged) and a second, independently-authored, functionally identical fix that had since landed on main via a different branch/PR (2026-07-28T09:40) — from what appears to be a separate session's work on the same repo. No new bug existed; no new fix was needed. The only missing step was triggering an actual deploy from current main.

catch_next_time: When a "recurring" failure is reported, first check (a) the live resource's actual current configuration via a direct `show`/`get` call (not just execution/run history, which reflects config at trigger-time, not now), and (b) deployment/apply timestamps against the fix's commit and merge timestamps, before concluding the existing fix is insufficient or a new root cause exists. If a fix is already present on the target branch (verified via `git log`/`git show` on the actual deploy branch, not just the working branch), do not author a duplicate — validate the existing fix (compile + what-if against live state) and report that the missing step is deployment execution, not code. When working across a multi-day/multi-session repo, check recent commit history on the target branch before diagnosing, since another party may have already fixed the exact issue independently.
