statement: Frozen spec verify shell commands are code and can themselves contain
bugs independent of whether the built content is correct — e.g. a bracket-glob
character class typo (`[0368]` intended to mean "any digit" but only matching
those 4 literal digits, silently excluding files it should have covered) and a
`cmd && (echo bad && exit 1) || echo OK` idiom that always resolves to the `||`
branch's own exit code (0) regardless of what `cmd` actually found. Both bug
patterns were found independently by different reviewers on different criteria in
the same build.

evidence: Tester and output-reviewer both found: AC-31's original glob
`functions/1[0368]-*` never matched functions/11 or functions/12 (neither digit is
in {0,3,6,8}), silently excluding them from schema validation; AC-18/AC-36's `test
-f X && (echo bad && exit 1) || echo OK` idiom always exits 0 because bash's
`&&`/`||` chain treats the inner `exit 1`'s nonzero status as making the left side
"false", triggering the `||` fallback unconditionally. Both were fixed in
amendment v4 by rewriting to if/then and correcting the glob to `[0-9]`.

catch_next_time: Tester/reviewer — for every verify command with a bracket-glob
character class, manually enumerate which real filenames it does and doesn't
match against the AC's prose intent; for every `X && (...; exit 1) || Y` shell
idiom, mentally flip X's truth value and confirm the reported outcome actually
changes — if it doesn't, the check is structurally unfailable and must be
rewritten as an explicit if/then before the criterion is trusted.
