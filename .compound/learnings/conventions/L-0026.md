statement: A routing/config table that maps a logical id to a literal
upstream identifier string (e.g. `routing.yaml`'s `provider_model` values,
real Anthropic model ids) can carry a wrong literal value indefinitely if
every test exercises it through a stubbed/mocked provider — the stub
accepts whatever string it's handed, so nothing checks the value is a real,
currently-valid upstream identifier. Only an actual live call to the real
upstream API surfaces the mistake, typically as a 404/400 from the
provider, not a routing-layer test failure.

evidence: `services/model-gateway/policy/routing.yaml`'s `claude-haiku`
entry had `provider_model: claude-haiku-3-5-20241022` — the two path
components transposed from the real Anthropic model id
`claude-3-5-haiku-20241022`. `tests/test_routing.py` passed cleanly (its
`stub_provider` records whatever `provider_model` string it's called with,
asserting only that opus/sonnet/haiku resolve to three *distinct* strings,
never that any of them is a real one) — the bug was invisible until the
gateway's first real live call, which returned
`{"error":{"code":"PROVIDER_ERROR","message":"upstream provider returned
HTTP 404"}}` (Anthropic's actual response for an unrecognized model id).
The wrong value traced all the way back to `.loop/plan.md`'s original spec
text, which already had the same transposition — this was an authoring
typo baked in at spec-writing time, not introduced during implementation,
and no unit test in this codebase's mocked-provider architecture could ever
have caught it.

catch_next_time: When a config/data file's values are literal identifiers
owned by an external system (provider model ids, external API endpoint
paths, external resource names), a mocked-provider unit test proves the
ROUTING logic works but proves nothing about whether the literal VALUES are
real — treat that class of correctness as needing either (a) a live
integration/smoke check that actually exercises the real upstream at least
once (which is exactly what this repo's `caj-gateway-smoke` job is for —
this bug was working as intended, just one layer later than the DNS bug
found the same day), or (b) cross-checking literal external-system
identifiers against known-current values at review time, not just trusting
that a plan document specified them correctly. A plan/spec document itself
is not proof a literal string is correct — it's a hypothesis the first real
call either confirms or falsifies.
