statement: A routing/config table that maps a logical id to a literal
upstream identifier string (e.g. `routing.yaml`'s `provider_model` values,
real Anthropic model ids) can carry a wrong literal value indefinitely if
every test exercises it through a stubbed/mocked provider — the stub
accepts whatever string it's handed, so nothing checks the value is a real,
currently-valid upstream identifier. Only an actual live call to the real
upstream API surfaces the mistake, typically as a 404/400 from the
provider, not a routing-layer test failure.

evidence: `services/model-gateway/policy/routing.yaml`'s `claude-haiku`
entry had `provider_model: claude-haiku-3-5-20241022` — the two path
components transposed from the real Anthropic model id
`claude-3-5-haiku-20241022`. `tests/test_routing.py` passed cleanly (its
`stub_provider` records whatever `provider_model` string it's called with,
asserting only that opus/sonnet/haiku resolve to three *distinct* strings,
never that any of them is a real one) — the bug was invisible until the
gateway's first real live call, which returned
`{"error":{"code":"PROVIDER_ERROR","message":"upstream provider returned
HTTP 404"}}` (Anthropic's actual response for an unrecognized model id).
The wrong value traced all the way back to `.loop/plan.md`'s original spec
text, which already had the same transposition — this was an authoring
typo baked in at spec-writing time, not introduced during implementation,
and no unit test in this codebase's mocked-provider architecture could ever
have caught it.

catch_next_time: When a config/data file's values are literal identifiers
owned by an external system (provider model ids, external API endpoint
paths, external resource names), a mocked-provider unit test proves the
ROUTING logic works but proves nothing about whether the literal VALUES are
real — treat that class of correctness as needing either (a) a live
integration/smoke check that actually exercises the real upstream at least
once (which is exactly what this repo's `caj-gateway-smoke` job is for —
this bug was working as intended, just one layer later than the DNS bug
found the same day), or (b) cross-checking literal external-system
identifiers against known-current values at review time, not just trusting
that a plan document specified them correctly. A plan/spec document itself
is not proof a literal string is correct — it's a hypothesis the first real
call either confirms or falsifies.

update 2026-07-30: fixing only the transposed haiku id was NOT enough —
fixing the DNS bug (L-0025) let the smoke test reach the real Anthropic API
for the first time, and the SAME 404-class PROVIDER_ERROR recurred even
with the transposition corrected. A live `GET
https://api.anthropic.com/v1/models` call (run by a human operator with
vault access, since fetching the key requires Key Vault data-plane access
this session's own safety tooling correctly declined to grant itself —
opening the vault's network ACL, or handing a new resource a secret
binding, is exactly the kind of action worth a human in the loop) showed
`claude-opus-4-20250514` and `claude-sonnet-4-20250514` — the OTHER two
entries in the same file, never touched by the first fix — were ALSO
absent from the live model list: genuinely retired, not just "haiku was
special." All three `routing.yaml` entries needed updating from that live
response, not just the one that happened to be exercised by the existing
smoke test's single hardcoded `"model":"claude-haiku"` body. Generalizes
the lesson: verifying ONE entry in a routing/config table live does not
verify its SIBLINGS — the smoke test only ever exercises whichever single
tier its own hardcoded request uses (L-0013's bug-class principle again:
audit every entry the same mechanism touches, not just the one that failed
first). Implemented the structural fix the same round:
`main._validate_routing_against_live_models()`, run once at gateway process
startup via a FastAPI `lifespan` handler, calls
`AnthropicProvider.list_model_ids()` (`GET /v1/models`) once and checks
every `anthropic`-provider route in `routing.yaml` against the live set,
logging one `routing_model_retired` JSON line per stale entry — covering
ALL tiers on every deploy, not just whichever one the smoke test's single
hardcoded request happens to exercise. Deliberately never raises/blocks
startup on a failed or unreachable live check (logs
`routing_model_validation_skipped` instead) — coupling the gateway's own
liveness to a third-party API's momentary availability would trade one
failure mode for a worse one; a loud, structured log line is the entire
point, not a hard start-up gate. Tested directly against the function
(`tests/test_startup_model_validation.py`), not through the existing
`app_client`/`ASGITransport` fixture — that transport never drives FastAPI's
`lifespan` protocol at all (only a real ASGI server like uvicorn does),
which is itself worth knowing before assuming an `on_event`/`lifespan` hook
is covered by an existing app_client-based test.
