statement: Before a spec/plan freezes any Must-have criterion that depends on live verification via an external CLI or local service (gh, docker, a database server, etc.), the spec-writer or plan-reviewer must first probe actual availability in the current sandbox rather than assuming it.

evidence: On the canvas-marketing-os-foundation run, 21/40 acceptance criteria failed with failure_class=test (not build defects) because no `gh` CLI was installed/authenticated anywhere in the sandbox (builder, tester, and orchestrator environments all lacked it), no real Azure deployment existed yet, and no Docker/Postgres was available locally with admin rights to install one. None of this was fixable by further build iteration — it required environment/credential changes only a human could make.

catch_next_time: Run `gh --version && gh auth status`, `docker --version`, and check for admin/install rights BEFORE freezing a criterion that depends on them as a blocker. If unavailable, mark the criterion as verified-by-static-analysis-only with a documented deferred-live-check note, or move it to open_questions for the human — do not let it silently gate shippability as though more build iterations could ever satisfy it.
