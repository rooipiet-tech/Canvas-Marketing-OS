statement: Two distinct ways an audit of this repo produces a CONFIDENTLY WRONG finding, both hit while reverse-engineering the platform for `docs/architecture/`, and both cheap to repeat. (a) **A registry built by a factory is invisible to a grep of its literal keys.** `DISPATCH_TABLE` merges eleven scanner handlers in as a dict spread — `DISPATCH_TABLE = { **SCANNER_HANDLERS, "ingest-signals": ..., ... }` — so a regex over `"task-type":` entries inside the table reports those eleven as unregistered no-ops. (b) **A comment describing intent is evidence of a comment, not of intent.** A `TEMPORARY` marker with a commented-out "revert to this" block is indistinguishable in source from a real defect, and stays that way indefinitely if the revert never comes.

evidence: (a) `services/orchestrator/orchestrator/dispatch.py` defines `SCANNER_TASKS` (task_type -> function_id, profile_id, agent_name), expands it via `_make_scanner_handler` into `SCANNER_HANDLERS`, and spreads that into `DISPATCH_TABLE`. An audit script matching `^\s{4}"([a-z0-9-]+)":` against the table's body returned 28 task_types and declared the eleven S10 scanners unwired. They were wired. The same script had been correct at an earlier commit — the eleven genuinely WERE pass-throughs then (TD-01), and the factory was introduced by the fix — so the method silently went from right to wrong without the script changing. The false result was caught only because the git log showed a commit titled "Bring the first two scanners live", which contradicted the script's output.

(b) `infra/modules/scheduling/weekly-planning-trigger.bicep` carried, from 6 Aug 2026 to 17 Aug 2026: a header saying the daily cadence was "TEMPORARILY switched ... reverting to weekly once the iteration phase is done", and an inline `// TEMPORARY` block preserving the former `frequency: 'Week', weekDays: ['Monday']` config. Both were accurate when written. The revert was never coming — daily was the standing product decision — but nothing in the file said so. An architecture pass read the marker as a defect, filed it as a finding, and costed it as ~7x model overspend against the intended cadence; the accompanying recommendation was to restore the weekly shape, which would have cut content output to one seventh of what the owner wanted. It was withdrawn only after the owner was asked directly.

catch_next_time: (a) Before concluding a `task_type`, route, tool or handler is unregistered, resolve every `**spread`, factory, comprehension and `.update()` feeding the registry — or, better, import the module and read the real dict at runtime rather than pattern-matching its source. A finding of the form "N things are declared but never execute" is high-impact and therefore worth the extra minute of verification; this one drove ~66 commits of remediation work when it was true, and would have been embarrassing had it been published while false.

(b) Treat `TEMPORARY`, `FIXME`, "revert once X" and "for now" as **undated claims about the past**, never as current intent. Confirm with whoever owns the decision before filing one as a defect — particularly when the "fix" would reverse a behaviour that has been running unremarked in production for weeks. The cost asymmetry is stark: asking is a message, acting on a wrong reading changed a live schedule.

(c) When removing such a marker after confirming intent, write the ruling and its date into the file, and say why the revert is not coming. A silently deleted `TEMPORARY` leaves the next reader with no signal at all; the marker at least prompted the question.

(d) An audit method that was correct at commit A can be wrong at commit B without changing — `main` moved 59 commits in one day during this work, and closed the largest finding in the register. Re-verify findings against the current tree before publishing, and record the commit a document was verified against, so a reader can tell how stale it is.
