statement: When a reviewer finding is really a BUG CLASS (a mechanism reused across
multiple call sites — e.g. raw request/error content flowing into a client-facing
message or an audit row) rather than a single site, a patch that fixes only the
reported instance reliably leaves siblings for the next review round to find.

evidence: In the s1-gateway build, the same "raw content leaks into a client-facing
message" class was hit three times across patch rounds: fixing DR-1 (redaction bypass
on non-string message content) introduced DR-3 (jsonschema's default error formatter
echoed the raw offending value in 400 responses); the DR-3 fix's own new validation
code path was itself sound, but two sibling instances of the identical class
(redaction.py's fixture-match audit-row id embedding raw PII, routing.py's
unknown-model error echoing the raw caller-supplied model string) survived untouched
through that round. Only the round-4 patch — which did one explicit, documented,
systematic grep/audit of every error-message-construction site in the service instead
of another single-instance fix — actually closed the class; both output-reviewer's
and data-residency's independent fresh sweeps came back clean afterward.

catch_next_time: When a PATCH-round task is derived from a reviewer finding, check
whether the finding's wording implies a class (mentions "same class", "sibling", a
named pattern, or a mechanism reused in more than one place). If so, require the patch
task to explicitly (1) grep/audit every call site of the same mechanism across the
touched service, not just the reported site, and (2) record a one-line note in the
commit/build log listing what was audited and confirming no further instances — so a
clean fresh-sweep on round 2 becomes the norm, not something only reached after two
rounds of whack-a-mole.
