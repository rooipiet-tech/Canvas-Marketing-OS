statement: A GitHub Actions run stuck in `waiting` for a GH Environment's manual approval gate holds its `concurrency: group:` indefinitely — every subsequently-triggered run sharing that group (including a whole chained deploy sequence off a just-merged PR) gets cancelled with "Canceling since a higher priority waiting request exists," even if the waiting run is stale/abandoned and nobody intends to approve it.

evidence: S8's merge (PR #45) fired the full chained deploy sequence (deploy-infra -> deploy-gateway/deploy-governance/deploy-mcp/deploy-loop-e2e-smoke, all sharing the `cmos-dev-deploy` concurrency group), but every run self-cancelled because two OLD, abandoned runs (deploy-infra from 23 Jul, deploy-mcp from 31 Jul) were still sitting in `waiting` for environment approval, holding the group. Manually rejecting both stale waiting runs was required before the new chain could actually proceed.

catch_next_time: Before merging a PR that fires a chained, concurrency-grouped deploy sequence, check for stale `waiting` runs on that concurrency group (`gh run list --status waiting` or the Environments UI's "Review deployments" list) and reject/clear them first — don't assume a merge will "just work" through the queue. Consider a periodic or pre-merge automated check that flags any `waiting` run older than some threshold (e.g. >1 day) on a shared concurrency group as likely-abandoned, so this doesn't need to be caught manually every time.
