statement: Session touch-scope constraints in this repo's build loop are default-deny but explicitly amendable: when a genuine live-deploy goal conflicts with the declared touch-scope (e.g. wiring new Bicep modules requires editing the shared `infra/main.bicep`), the resolution is a narrow, marked, append-only exception (single insertion-point comment marker) with a verify command asserting zero removed/reordered lines — not a silent scope violation or a silent deferral.

evidence: In the S4 governance build, research/domain analysis flagged (C-9) that Bicep has no module auto-discovery — every module reference is an explicit statement in a parent template — so a real deploy of new `infra/modules/governance` modules mechanically requires editing `infra/main.bicep`, which sat outside the session's initially-stated touch-scope. The user's amendment 1 explicitly authorized a minimal, append-only edit to `infra/main.bicep` at one marked insertion point plus one new workflow file. The corresponding acceptance criterion (AC-14) verified this with `git diff --unified=0 infra/main.bicep | grep '^-' | grep -v '^---'` returning empty, independently re-confirmed by the orchestrator before and after the build, and again after rebasing onto main (see [[L-0028]]).

catch_next_time: When a spec or plan needs to touch a file outside the declared touch-scope because live wiring is genuinely the goal, write it as an explicit amendment naming the exact file, constrain the edit to one marked append-only insertion point, and add a verify command asserting no removed/reordered lines exist outside that marker (`git diff --unified=0 <file> | grep '^-' | grep -v '^---'` is empty).
