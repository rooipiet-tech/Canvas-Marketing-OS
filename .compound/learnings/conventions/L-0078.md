statement: A GOAL's own factual claims about a dependent/sibling service's CURRENT capabilities can be stale or simply wrong and must be verified against that service's actual live code (its real tool count, schema, and fields), not the goal author's memory, before design proceeds. This is distinct from [[L-0038]] (a researcher's own inference going unchallenged) because here the error originates in the GOAL AUTHOR's text itself, not in a researcher's downstream guess.

evidence: The s9-analytics GOAL asserted "Buffer analytics ARE available now via existing buffer-api-key and mcp-buffer (engagement per scheduled post)." The researcher independently read mcp/mcp-buffer/tools.yaml and app/dispatch.py and found exactly 3 tools (list_queue, get_post, create_draft), zero engagement/metrics fields anywhere, and the get_post.json fixture confirmed no metrics data at all. The domain-expert confirmed this ruling and it flowed into the frozen spec (analytics-ingest built its own direct Buffer GraphQL client instead of routing through mcp-buffer). At the spec-approval gate, the user explicitly confirmed for the record: "your mcp-buffer fact-check was correct and my goal text was wrong."

catch_next_time: For every GOAL sentence asserting a dependent/existing service already provides capability X, the researcher must independently grep that service's real tool/schema definitions (not summarize from the goal text) and flag any mismatch explicitly to domain-expert before spec-writer freezes scope around it — treat GOAL prose about sibling-service capabilities as an unverified claim, held to the same evidentiary bar as any other researcher-sourced fact, never taken at face value just because it came from the goal author.
