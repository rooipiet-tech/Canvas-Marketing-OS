statement: A background subagent (e.g. a BUILDER) can be killed mid-run by a
transient provider-side connection error unrelated to its own logic, after having
already written most of its work to the real filesystem. Check actual on-disk
state (git status / directory listing) before deciding how to recover, then
resume the SAME agent via SendMessage to its existing agentId rather than
spawning a fresh one — the resumed agent retains its own transcript context and
completes only the remaining steps without redoing finished work.

evidence: The BUILDER subagent failed mid-session with a "Connection closed
mid-response" API error (a transport failure, not a tool/logic exception). Before
deciding how to proceed, its filesystem output was inspected directly (git
status/ls), confirming most work was already committed to disk. The orchestrator
resumed the same agent via SendMessage (not a new Agent spawn), which picked up
cleanly from its own context and finished the remaining steps.

catch_next_time: Orchestrator — on a subagent failure whose error text indicates a
transport/connection problem (not a tool error or an exception raised by the
agent's own logic), first inspect the real repo state (git status, relevant
file/directory listing) to establish how much work actually survived, then prefer
SendMessage-to-existing-agentId resume over a fresh Agent spawn — a fresh spawn
has no memory of completed work and risks redoing or conflicting with it.
