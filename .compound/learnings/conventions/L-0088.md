statement: `scripts/validate_contracts.py --write-baseline` computes the
written baseline SOLELY from the script's own `FROZEN_FILES` list, not from
the committed baseline file's existing contents — so running it rewrites
`contracts/.frozen-v1.sha256` down to exactly the entries `FROZEN_FILES`
names today, silently dropping any hash line the committed file carries for
a path `FROZEN_FILES` no longer (or never) listed. This is not hypothetical:
the committed `contracts/.frozen-v1.sha256` already carries three such
entries (`orchestrator/loop-definition.schema.json`,
`orchestrator/heartbeat-event.schema.json`,
`orchestrator/dead-letter-alert.schema.json`) that are absent from
`FROZEN_FILES` and have been since at least commit 1f5f1e6 ("Make an
opportunity card readable, and read it") — that commit's own message
documents the gap and deliberately avoided running `--write-baseline` for
exactly this reason, hand-editing the single changed line instead.

evidence: Building TD-14's v2 contract window, `--write-baseline` was run
to establish `contracts/.frozen-v2.sha256` for the new
`gate-token/v2`/`vault-schema/v2` files. It also silently rewrote
`contracts/.frozen-v1.sha256`, and `git diff` showed the three orchestrator
lines above deleted — none of them were touched by this change; they were
just absent from `FROZEN_FILES` and got dropped the instant the flag ran
unconditionally. Caught only because `git status`/`git diff` was checked
before committing, per this repo's own git-safety habits — an agent that
trusted the flag's output and committed directly would have silently
widened the exact hole 1f5f1e6 deliberately left alone, weakening the
breaking-change guard's coverage for three unrelated contract files with no
review signal at all (the script still exits 0 and prints PASS).

catch_next_time: Before running `--write-baseline` for ANY reason, diff the
freshly-written baseline file against its previously-committed version
(`git diff contracts/.frozen-v1.sha256` / `.frozen-v2.sha256`). If the diff
removes any line beyond the one file you intended to touch, restore the
baseline file from git and either (a) hand-edit only the changed file's own
line, matching 1f5f1e6's precedent, or (b) fix `FROZEN_FILES` to include
the missing entries first, as its own separate, reviewed change — never as
a side effect of an unrelated baseline refresh. This generalizes L-0005/
L-0044's family (a verify command can be wrong in both directions) to a
new shape: a "regenerate from source of truth" flag whose source of truth
(a hardcoded list in the script) has already drifted from what it's
regenerating (the committed baseline file) is silently *destructive*, not
just silently wrong — regenerating from a narrower list is data loss, not
a stale-pass.
