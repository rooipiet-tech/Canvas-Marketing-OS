statement: Generating a secret/password with a generic base64 encoder (e.g. `openssl rand -base64 N`) for embedding directly in a URI (e.g. `postgresql://user:PASSWORD@host/db`) is unsafe: base64's alphabet includes `/+=`, which are URI-significant or invalid-unescaped characters and break URI parsing a large fraction of the time (roughly 35-40% per generation for a 32-char string).

evidence: Post-build risk-security review on the canvas-marketing-os-foundation run caught Postgres admin passwords generated via `openssl rand -base64 24` flowing directly into a `postgresql://` DATABASE_URL used by Container Apps Jobs. Not caught by any grep-based spec verify command — only a dedicated security-review lens found it. Fixed by switching to `openssl rand -hex 32` (inherently URL-safe alphabet).

catch_next_time: Whenever a randomly-generated value is concatenated into a structured-syntax string (URI, JSON, shell command), verify its alphabet is compatible with that syntax's reserved characters. Grep for `rand -base64` (or equivalent) feeding into a variable later interpolated into a `://user:PASS@` string, and require hex or base64url-without-padding generation instead.
