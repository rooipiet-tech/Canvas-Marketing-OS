statement: Azure Container Apps built-in authentication (Easy Auth) with a Microsoft Entra ID provider CAN be fully secretless — the App Registration's Federated Identity Credential (FIC), pointing at the Container App's managed identity, is added via a GA (non-preview) Entra Portal/Graph blade, so no client secret is ever created; the "no client secrets" rule should be read as scoped to CI/CD and service-to-service auth (OIDC/managed identity), not as forbidding this narrow interactive-user-login pattern. This is a standing ruling (owner-approved 2026-07-28) that other sessions building Entra-ID-gated Container Apps should inherit.

evidence: Domain-expert research (this session, .loop/domain.md) initially found a real conflict — Microsoft's authentication-entra.md states automatic app-registration creation always stores a client secret, and the bring-your-own-registration path without a secret forces the discouraged OAuth2 implicit grant flow. Orchestrator's follow-up research resolved it: the Azure-Samples/containerapps-builtinauth-bicep sample demonstrates a fully secretless config using a Federated Identity Credential linking the Container App's managed identity to the Entra application (verified via WebFetch of the sample's README, 2026-07-28). The sample's Bicep-driven APP REGISTRATION creation uses the Microsoft Graph Bicep extension, which IS public-preview and requires Graph directory permissions the CI identity in this repo does not have (confirmed live: cmos-github-actions app registration has zero Graph API permissions, zero directory role membership) — but adding a Federated Identity Credential to an ALREADY-EXISTING app registration is a standard GA Entra Portal action (Certificates & secrets > Federated credentials), not gated behind the preview Graph extension. Owner ruling: the console's App Registration is created manually (one-time, human with directory admin rights) per a separate decision (see .loop/domain.md goal_conflicts), and the FIC should be added as part of that same manual step — avoiding both the client secret AND any CI Graph-permission escalation.

catch_next_time: When a future session needs Entra-ID-gated Container Apps auth and hits "no client secrets" as a hard constraint, check first whether the App Registration already exists (Easy Auth secret vs. FIC is decided at App Registration setup time, not at Container App deploy time) — if creating fresh, add a Federated Identity Credential (subject = the Container App's managed identity) instead of a client secret, and treat App Registration + FIC creation as one bundled manual step if the deploying CI identity lacks Microsoft Graph / Entra directory-role permissions (verify via `az ad sp show`/`az rest` on the CI app registration's requiredResourceAccess and memberOf before assuming automation is possible).
