statement: Azure Container Apps resolves `$(...)`-shaped references inside secret/env-var values (to let one env var reference another), and treats `$$` in a value as the escape sequence for a literal `$`. Any text containing `$$` — e.g. PostgreSQL's `DO $$ ... END $$;` dollar-quote syntax — that is stored as a Container Apps secret/env value gets silently collapsed (`$$` → `$`), corrupting the content with no error at deploy time. The corruption only surfaces later, as a runtime failure inside the container (e.g. `psql: syntax error at or near "$"`).

evidence: contracts/vault-schema/schema.sql's three `DO $$ BEGIN ... EXCEPTION WHEN duplicate_object THEN NULL; END $$;` enum-guard blocks were passed into migration-job.bicep's Container Apps Job as a raw secret value (`SCHEMA_SQL` env var, sourced from a `schema-sql` secret). On the first real deploy, the job's execution logs (queried via Log Analytics `ContainerAppConsoleLogs_CL`) showed `psql:/tmp/schema.sql:29: ERROR: syntax error at or near "$"` / `LINE 1: DO $ BEGIN` — every `$$` in the file had been collapsed to a single `$`. CI's disposable-Postgres migration-test job never caught this because it applies `schema.sql` directly to psql from the git checkout, never going through the Container Apps secret/env-var round-trip at all — the exact kind of gap L-0005 already warned about. Fixed by base64-encoding the schema content before storing it as the secret value (base64's alphabet has no `$`) and decoding it in-container (`printf '%s' "$SCHEMA_SQL_B64" | base64 -d > /tmp/schema.sql`) before feeding it to psql. Verified via a local round-trip (encode → decode → diff against source: byte-identical) and a live `az deployment group what-if` (clean in-place update, no destructive changes).

catch_next_time: Never store multi-line text containing `$$`, `$(`, or other shell/templating-significant sequences directly as an Azure Container Apps secret/env value if that text must survive byte-for-byte — base64-encode it first and decode in-container. More generally: any config/secret value that will pass through a platform's own templating/substitution layer (Container Apps' `$(...)` resolution is one instance of a broader class) needs its content audited for that layer's special characters, not just the final shell command's own quoting. And: a CI check that validates a file directly (e.g. applying schema.sql straight from the repo) does NOT validate the actual runtime path if production wraps that same content in an additional transport/storage layer (env var, secret, templated config) — the two paths can silently diverge, so a full pipeline test (or at minimum, a round-trip check of anything passed through such a layer) is needed to catch this class of bug before a real deploy.
