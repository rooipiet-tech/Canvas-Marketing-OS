statement: On Azure Key Vault (and similarly other PaaS resources with the same property), `publicNetworkAccess=Disabled` takes precedence over and effectively ignores any IP-based firewall/network ACL rules — an allow-listed IP in `networkAcls` has no effect while `publicNetworkAccess` is Disabled, because Disabled removes the public endpoint entirely; only a private-endpoint-connected client can reach the vault at all. A human operator working from outside the VNet (e.g. their own laptop) therefore cannot load secrets into a Disabled vault via CLI no matter what IP rules exist, until `publicNetworkAccess` is temporarily set to Enabled with `networkAcls` set to Deny-by-default plus the operator's specific IP allow-listed — and this must be reverted to Disabled once the loading window closes.

evidence: S0's human secret-loading step required temporarily flipping cmos-dev's Key Vault from `publicNetworkAccess=Disabled` to `Enabled` with a Deny-default network ACL plus the operator's specific IP allow-listed, to let secrets be loaded from outside the VNet — then restoring `Disabled` afterward. This confirmed that an IP-allowlist alone, without also flipping `publicNetworkAccess` to Enabled, does not grant access; the two settings are independent gates and both must be right.

catch_next_time: Document the open/close window procedure explicitly in the ops runbook — the exact `az keyvault update --public-network-access Enabled`, `az keyvault network-rule add --ip-address <operator-ip>`, and (after loading) `az keyvault update --public-network-access Disabled` commands — rather than relying on an operator to rediscover this from a confusing connection failure. For Wave-2+, prefer a gated, in-VNet secret-loading Container Apps Job (mirroring this repo's existing caj-vault-migrate/caj-vault-query one-shot job pattern, triggered by an authorized human via `az containerapp job start`) so the vault's public network access never needs to be opened at all, eliminating this temporary-exposure window entirely.
