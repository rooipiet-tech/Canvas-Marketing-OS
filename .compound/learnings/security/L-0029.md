statement: A deploy-time smoke/verification job's own design need for "something to gate-check" can leak into the real product's shared authorization/policy config as a standing bypass, if the smoke test is given its own privileged shortcut entry instead of exercising the product's real approval path.

evidence: In the S4 governance build, a risk-security review (RISK-01) found that `smoke.governance_cycle` — the function_id the deploy-time smoke-test job used to exercise the gate/sign/verify/replay cycle — had been registered at autonomy level 4 (fully-autonomous passthrough) directly in the shared, production `autonomy.yaml` policy file. Any internal caller who learned this function_id could obtain a real Key-Vault-signed, auto-approved gate token for an arbitrary content_hash with zero human approval. Low-impact while the downstream publish path was a stub, but a live governance bypass the moment real write credentials attach. Fixed by removing the standing level-4 entry entirely (it now fails closed at default level 0) and re-architecting the smoke job to pre-seed a real `approval_inbox` row and traverse the genuine level-1 approval path instead — proving the same sign/verify/replay cycle without any standing bypass in the shipped policy.

catch_next_time: Risk-security checklist addition: grep any autonomy/policy/permission config file for function_id or resource identifiers containing "test", "smoke", "check", "debug", etc. Any such entry granting auto-approved or elevated access is a red flag requiring explicit justification. Smoke/verification jobs should seed state (e.g. a pre-approved record) to walk the standard authorization path, never be granted their own bypass entry in the real shipped policy.
