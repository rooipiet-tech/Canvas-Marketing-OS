statement: A committed dev/test key or other "looks like security" construct intended only for non-production fallback use is more safely mitigated when it carries BOTH a static warning (README/docs) AND a runtime signal (e.g. an emitted WARNING) every time the fallback path is actually exercised — static documentation alone does not stop accidental misuse.
evidence: In the s6-registry build (user's own spec amendment, AC-04/AC-05), a repo-committed Ed25519 dev signing key was accepted as non-production fallback material with an env-var-first resolution order. Plan-reviewer finding F5 required signing.py/verify_signature.py to print a runtime stderr WARNING on every actual fallback use, not just a static README note; output-reviewer's final review confirmed both the static and runtime warnings were present as a strength.
catch_next_time: When a spec/plan introduces committed non-production secret/key material intended as a fallback-only default, require both a static doc warning and a runtime-emitted warning/log line on every actual invocation of the fallback path; treat a static-doc-only mitigation as incomplete during review.
