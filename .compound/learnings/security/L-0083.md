statement: `Microsoft.App/containerApps/authConfigs` (Azure Container Apps built-in "Easy Auth") has NO schema field for app-role claim validation, at any API version checked (2022-03-01 through 2024-10-02-preview inclusive). The Azure AD identity provider's `validation` block exposes exactly two authorization primitives: `defaultAuthorizationPolicy` (`allowedApplications` — client app ids; `allowedPrincipals.identities`/`.groups` — object ids and security-group ids) and `jwtClaimChecks` (`allowedClientApplications`, `allowedGroups`). There is no `allowedRoles`/`appRoles` property anywhere. Microsoft's own docs for this exact scenario are explicit that this is by design, not a gap: "The Container Apps authentication layer doesn't perform the [role] validation steps... validate that expected roles are now present in the token" in application code (learn.microsoft.com/azure/container-apps/authentication-entra#configure-client-apps-to-access-your-container-app). A task or ticket asking for "an app-role claim requirement in the authConfig validation block" is asking for something this ARM resource type cannot do — the closest real IaC-level equivalent is a **security-group** claim (`allowedPrincipals.groups`), with the actual app-role-style enforcement necessarily living in application code instead.

evidence: TD-04 (docs/architecture/09-technical-debt.md) and docs/accepted-risks.md's "console Easy Auth authenticates but does not yet authorize by operator" both specified the fix as "app-role claim in the authConfig validation block AND a matching check in require_principal." Fetching the ARM template property-value reference for `Microsoft.App/containerApps/authConfigs` across 9 API versions (2022-01-01-preview through 2024-10-02-preview) via Microsoft Learn confirmed `DefaultAuthorizationPolicy` and `JwtClaimChecks` never gained a roles field; a general Container Apps auth doc search independently surfaced the "doesn't perform the validation steps... in your application code" line for the exact daemon-app-role scenario. Attempting to declare a fictitious `jwtClaimChecks.allowedRoles` (or similar) property would not silently no-op — Bicep type-checks resource properties against the resource type's schema and would fail `bicep build` (this repo's `scripts/validate_bicep.sh` gate) with a real compile error, not a deploy-time surprise.

catch_next_time: When a ticket/spec names "app-role" enforcement specifically for a Container Apps (or App Service) Easy Auth `authConfig`/`authsettingsV2` resource, verify the actual ARM schema for the identity provider's `validation` block before implementing — fetch the current API version's property-value reference (`learn.microsoft.com/azure/templates/microsoft.app/<version>/containerapps/authconfigs`) rather than assuming "app role" and "security group" are interchangeable knobs on the same resource. If the spec's own compensating-controls doc already frames the requirement as "app-role **or** security-group claim" (as docs/accepted-risks.md did here), implement the security-group form at the IaC layer and reserve the actual role-claim check (if one is still wanted) for application code, which is the only place Azure's own docs say it can run. Feed both the IaC-level and code-level checks from the SAME Bicep parameter/env var so they cannot drift apart — the same "duplicate check across the trust boundary" shape as this repo's existing RISK-003 pattern.
