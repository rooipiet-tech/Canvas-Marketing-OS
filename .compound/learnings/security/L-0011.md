statement: A Key Vault deployed with `enableRbacAuthorization: true` grants NO data-plane access to anyone by default — not even the subscription Owner. Azure's Owner role only carries control-plane (management-of-the-resource) permissions; reading or writing secrets requires a separate, explicit data-plane role assignment (e.g. "Key Vault Secrets Officer" or "Key Vault Secrets User") scoped to the vault. Without it, even an Owner gets an authorization-denied error attempting `az keyvault secret set`/`show`.

evidence: During S0's human secret-loading step, the subscription Owner needed an explicit Key Vault Secrets Officer role assignment before any secret could be loaded into cmos-dev's vault. key-vault.bicep sets `enableRbacAuthorization: true` but provisions no `Microsoft.Authorization/roleAssignments` resource — a gap already flagged during post-build risk-security review (SEC-003) but left unfixed at build time since secret population was explicitly out of scope for S0.

catch_next_time: Either (a) add an explicit `Microsoft.Authorization/roleAssignments` resource in Bicep granting Key Vault Secrets Officer to the intended human operator(s)/group as part of the deploy, if the operator identity is known and stable, or (b) if it must remain a manual step, document the exact `az role assignment create --role "Key Vault Secrets Officer" --scope <vault-resource-id> --assignee <principal-id>` command in the credentials/ops runbook so a human doesn't have to rediscover this from an opaque "Forbidden" error. Never assume RBAC-mode Key Vault plus an Owner role is sufficient for data-plane access — it never is; the two planes are always separate.
