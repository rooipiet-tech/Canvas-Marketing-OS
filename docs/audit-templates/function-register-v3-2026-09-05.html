The 129 Function Register

The blueprint of 22 July designed a workforce of 112 marketing agents. Two later revisions added 17 more — a ratification-and-earn-in family and a continuous-discovery family — for 129 rows total. Twenty-eight packages are built, and every one of them now runs. Here is every row, in plain English, and exactly where it stands.

The 28 packages that run

Every agent package in the repository is now reached by a running loop — sent to a model, with real output coming back. They cover 22 of the register's 129 rows, because function 18 alone ships as six vertical packages, and three of the v2/v3 rows (116, 117, 128) went live since this page was last read.

The twelve that used to do nothing

For most of August, twelve of these packages were complete, tested, named in the daily loop's plan — and dead. Their task types were not in the orchestrator's dispatch table, so the loop marked them done and moved on without doing any work. The loop went green either way, which is why it went unnoticed for six weeks.

That is fixed, and so is the follow-on problem this page previously reported: eleven of twelve scan profiles carrying no source URLs. On 4 September an agent researched all twelve profiles from the open web — three probed candidates each, every URL fetched and checked — and Pieter ratified the result in chat (Appendix D PR 5a). Every scan profile now carries real URLs (2 to 8 apiece, across up to 8 distinct domains); functions/_shared/scan-profiles.yaml still refuses to dispatch a profile with none, but none of the twelve is empty any more. Function 128 (Source Discovery & Lifecycle Manager) now owns keeping it that way daily, going forward.

The 4 that drifted

Nobody decided these. The blueprint was never checked into the repository, so the build could not see the numbering it was supposed to follow — and re-derived its own. Four packages ended up filed under a number that belonged to a different function, or to none.

Think of the register as numbered drawers. In each case the right thing was built and put in the wrong drawer — and the drawer it took belongs to something still to be built. This is the one finding from the August audit that is not only still open, but has grown, though one of the four has since been given a proper design home elsewhere.

Two new families, still on paper

v2 added a "Ratification and earn-in" family (rows 113–127) and v3 added "Continuous discovery" (128–129) — 17 rows built around one operating idea: agents author, humans only ratify. All 17 packages exist on disk — prompt, schema, manifest — but as of this page's last read, on 3 September, none of them were wired into a running loop.

That has since changed for three of them, and docs/function-register.md — the committed source of record — has not caught up: it still marks rows 116, 117 and 128 scaffolded. The orchestrator's own DISPATCH_TABLE says otherwise. 116 (Options Composer) and 117 (Approval Inbox Router) went live in Appendix D PR 5, wrapping every Thursday draft into an option card and sweeping the inbox at 07:15 daily. 128 (Source Discovery & Lifecycle Manager) went live in PR 5b and is what actually populated the twelve scan profiles above. The other 14 — including 129 (Web Reach Governor, blocked on choosing a discovery API and crawler vendor) and 123 (Video Capture Kit, dormant until the founder-video approach is ratified) — remain exactly as scaffolded as the register says.
