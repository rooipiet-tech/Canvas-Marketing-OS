Where we actually are

Three PRs are open and none is merged. PR #150 (blueprint v3, Fn 128/129, the card-mechanism scaffolding for continuous discovery) and PR #151 (blueprint v4 itself, the one functional change: bootstrap mode in Fn 128's prompt) are both docs-and-scaffolding — neither wires anything into a running loop. PR #152 (PR 5a, the scan-profile bootstrap) is the one PR in this chain that changes runtime behaviour: it fills all twelve scan profiles' urls, updates the mcp-web allowlist, and adds a validator — but it is not merged, so on main right now, 9 of 12 scan profiles are still empty, confirmed live this session (audit v4 §3). Nothing about the daily loop has changed yet; it changes the moment #152 merges, not before.

The discovery-trigger diagnosis, corrected this pass

la-source-discovery-trigger's Service Bus role assignment exists — PR #150's "missing grant" finding was wrong, caused by an unreliable Azure CLI query that returns empty even for a trigger with 3 consecutive successful runs. The real cause was an RBAC-propagation race 0.35 seconds after the grant's creation, on the trigger's one and only run so far (1 September). The grant was reconfirmed by today's deploy, days ahead of the next scheduled run (Monday). Nothing to fix; the next run should very likely succeed. Full evidence in audit-v4-recount.md §1d.
