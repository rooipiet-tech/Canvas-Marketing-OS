The blueprint, read as one document

Four documents, one design. v1 (22 July) is never edited; v2, v3 and v4 each carry the previous version forward in full and amend it. Read together rather than as a version history, the design today says:

  • 129 specialist functions, 15 in the daily core. v1 defined 112 across nine families. v2 added 15 (113–127) to replace every remaining human-authoring role with an option card a person chooses from. v3/v4 added 2 more (128, 129) to replace hand-managed source configuration with a daily, self-scoring discovery lifecycle.
  • Agents author, humans ratify. The single operating principle underneath v2 onward. No function drafts content, evaluations, foundations or source lists for a human to edit — every human touchpoint is an OptionCard: 2–3 materially distinct options, a recommendation, resolvable evidence, a risk tier, a declared timeout. Autonomy is earned per function from decision telemetry (§G2), never granted by fiat.
  • Downstream is never loosened. Publishing, spend and client-facing claims stay gated at every version. What changes release-to-release is upstream leverage (drafting, evaluating, discovering) and the mechanism ratification runs through — never what a human must personally author.
  • Sources are discovered, not configured [v3/v4]. A signal source is a decision with a lifecycle — discovered, probed, ratified, scored, retired — not a line someone edits once. v4's amendment: the first pass is an agent-researched bootstrap of all twelve scan profiles at once, ratified by the founder in one sitting, not hand-seeded one profile at a time.
  • The audit and the plan are re-run, not amended [v4 ruling]. This document is the result of that ruling: a fresh read of the whole design against the whole build, not a change list.

Full version-by-version amendment history, for anyone who wants it, lives in each document's own Appendix A: docs/blueprint/agentic-marketing-engine-v2.md, -v3.md, -v4.md. This document does not repeat it; it grades the design those four documents jointly specify, as it stands today, against one build.

1

Executive verdict

The governance spine is built well ahead of the design: a signed gate-token approval chain, a fail-closed autonomy policy, a kill switch with a proven sub-5-second propagation bound, per-model cost metering, and a forced-dry-run canary nothing in any blueprint version imagined. The ratification mechanism that is supposed to replace every remaining human-authoring role — the OptionCard contract, the options inbox service, fourteen new function packages — is fully scaffolded and fully unwired: fourteen tests pass in isolation, and not one card has ever reached a real digest. The source-discovery problem this whole v3/v4 chapter exists to fix is diagnosed, researched and ratified, but the fix itself sits in an unmerged pull request, so the daily loop is dead-lettering on empty scan profiles at this exact moment, same as it was in August.

Nothing has ever published through the governed path. That finding is unchanged across every version of this audit and every version of the design: the mechanism that would carry a real post has never carried one.

The ratification model — scaffolded whole, wired nowhere

This is what v2 through v4 actually add to v1, read as one mechanism rather than three separate proposals.

The card contract

contracts/option-card.schema.json defines one universal shape for anything an agent hands a human: 2–3 ranked options, a mandatory recommendation, resolvable evidence, a risk tier, a declared timeout. 33 typed kinds today, three of them (source.promote, source.retire, source.allowlist) added for continuous discovery. The schema, the options-inbox service that builds and routes cards (14 tests, all passing), and the Teams digest renderer all exist — in PR #150, unmerged. Zero cards have ever reached a real approval channel.

Earn-in, not fiat

§G2's promote/demote table (8 rules) makes autonomy a function of decision telemetry — Recommendation Hit Rate, Rejection-All Rate, fabrication rate — never a manually-set level. It is fully specified and nowhere enforced: contracts/vault-schema/schema.sql carries no hit_rate or rejection_code column, confirmed by direct grep this pass. The mechanism this whole model depends on to ever promote a function past its starting level does not exist at the data layer yet.

Continuous discovery v3/v4

The chapter that exists because nine of twelve scan profiles shipped with nothing to read. Fn 128 (discover/probe/ratify/score/retire) and Fn 129 (govern the reach: rate limits, robots.txt, an allowlist rule that auto-widens for reputable domains, injection stripping for the round-21 pattern) are both scaffolded, both registry-validated, both unwired. v4's amendment replaces a slow one-profile-a-day hand-seed with a single agent-researched pass across all twelve profiles at once — researched and ratified by the founder in chat, 4 September, sitting in PR #152, unmerged. Applying it is the highest-leverage single action available right now: see §7, recommendation 1.

Every fetched byte is data, never an instruction

Fn 129's own hard rule, eval-covered by two dedicated golden tasks (a planted authorisation; a fabricated run number plus a "harmless no-op" framing) — both must be stripped and logged without changing the underlying rule-based decision. Not yet exercised against real scraped content: the discovery API and crawler that would fetch it don't exist until a vendor is chosen (Appendix D PR 5c).

Top recommendations

Ranked by impact per unit effort, across the whole design, not one version of it.

  1. Merge #148 → #149 → #150 → #151 → #152, in that order review time only

    Zero new engineering. The scan-profile bootstrap is researched, fetched, ratified by the founder and sitting ready — merging it is what turns "9 of 12 profiles empty, dead-lettering 400+ tasks per three days" into "12 of 12 configured." Nothing else in this document matters more per hour spent.

  2. Registry-driven generic dispatch session

    Unchanged from every prior version of this audit. dispatch.py is a hand-written table that grows ~120 lines per function; wiring the remaining 76 v1 rows the same way adds ~9,000 more lines to a file already split once for being unmanageable. This is the pivot every later PR in the ratification chain assumes has already happened.

  3. Give the operator a brief to read and a button to click small PR

    The console approval inbox is read-only and the runbook instructs a click on a button that doesn't exist. Two changes that turn "a system that runs" into "a system someone uses" — and a precondition for the ratification model ever mattering, since it is entirely a "human clicks a card" mechanism.

  4. Instrument Recommendation Hit Rate before wiring any more ratification functions session, App D PR 1 + 6

    §G2's entire earn-in model depends on a hit_rate/rejection_code column that does not exist yet. Every one of the 17 scaffolded ratification functions is, right now, a function that can never be promoted past its starting autonomy level, because the mechanism that would promote it has nowhere to write.

  5. Calibrate the brand rules against real published output small PR

    86% of Canvas's actual published posts would fail fn 02's own link-shortener rule. The rule or the practice must change; only Pieter can choose, but nobody can choose until the number is on the table — which it now is, across four audit cycles.

  6. Re-authorize canvas-wordpress, resume s13 config → session

    DRIFT-13. Cheapest action that opens an entire designed channel — s13's spec, research and locked decisions are already written.

  7. Fix run-the-loop.md step 4 doc-only

    Still wrong on its most important step, for exactly the reader least able to detect it, four audit cycles later.

  8. Resolve DRIFT-2's vocabulary, not its mechanism small PR

    autonomy.yaml's comments should say "Options" and "Execute approved," matching every blueprint version since v2, rather than the pre-v1 language nobody has updated.

  9. Pick a discovery-API and crawler vendor decision + errand

    Blocks Appendix D PR 5c and therefore the entire back half of the continuous-discovery chapter. The ruling permitting them was made 4 September; the vendor choice was not.

  10. File a real hit_rate/rejection_code schema change alongside, not after, App D PR 1 same PR

    Currently planned as a later addition. It is a precondition for §G2 to mean anything from the moment the card mechanism goes live — folding it into PR 1 avoids shipping a promotion rule with nothing to promote against.

The path from here

One sequence, sized against what has actually landed, not against what any single blueprint version proposed in isolation.

Done bar — thirteen mechanically checkable criteria

  • 1–7 — shape validates; five golden evals minimum; safety suite clean; rubrics lint; registered and signed; reachable from a running loop's dispatch table, provably (a CI test asserts it); exercised live once against cmos-dev.
  • 8 — QA gates at target: measured, not designed — 64.1% / 41.6% as of this pass.
  • 9 — emits a valid OptionCard.
  • 10 — every evidence ref resolves via the vault's atom/asset/decision index.
  • 11 — no default_on_timeout on any downstream (publish/claim/spend) card, ever.
  • 12 — a scan source counts as live only when it carries provisional/ratified_by/ratified_at/review_by metadata and the daily loop has actually fetched from it successfully at least once.
  • 13 — scraped or fetched content is stripped of instruction-shaped text before any prompt sees it, logged with source and offset.

What will go wrong

  • The merge chain doesn't happen in order. #152 references identities #150/#151 create; merging out of order breaks the register's own numbering discipline.
  • The card mechanism ships before the hit_rate schema does. Every function wired against it starts earning autonomy toward a promotion rule with nowhere to record the evidence.
  • The five generic verticals' sources (mining/logistics/manufacturing/construction/FMCG, all sharing one reused source) never get purpose-researched. Fn 128's own yield scoring, once live, is what will surface this — watch for it, don't wait for a complaint.
  • The governed path stays a parallel universe. Unchanged risk since the first version of this audit: building every function in this document changes nothing if Buffer's UI remains the real publishing path.
